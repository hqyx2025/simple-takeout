# 简单外卖答辩全流程演示方案

适用范围：毕业设计现场答辩、录屏讲解。根据 2026 年 10 月 29 日工作区代码与项目说明整理；本文是演示脚本，不代表已经完成本次现场环境验收。登录页近期存在工作区改动，正式彩排应以最终安装的版本为准。

## 一、展示思路：用一笔订单串起三端

建议以“商户准备营业，用户下单，骑手完成配送”为主线。三个角色分别有完整流程，现场按业务发生顺序交叉演示，让老师始终看得懂：这是谁在操作、同一笔订单到了哪一步、操作后另一端发生了什么变化。

**主线顺序：用户注册登录 → 商户登录、维护商品与活动 → 用户选购付款 → 商户接单出餐 → 骑手登录、上线、抢单、取餐送达 → 用户确认评价 → 商户回复评价、查看结算。**

开场可以这样说：

> 我的项目是基于 HarmonyOS NEXT 的外卖系统，包含用户、商户、骑手和平台管理四种角色。今天主要演示前三端，围绕同一笔订单，展示从注册登录、商品经营到支付、配送、评价和结算的完整过程。平台管理在售后等需要平台介入的环节补充展示。

最值得让老师记住的三件事：

1. 三端通过真实服务端数据联动，商品、规格、订单和评价可以相互核对。
2. 下单、付款、送达、确认收货是不同阶段，库存和资金有对应的处理规则。
3. 系统同时考虑正常交易和缺货、退款、配送异常等实际经营问题。

基础资料修改、银行卡管理、全部后台菜单不必逐个点击。把时间留给“操作后有结果、有跨端变化”的功能。

## 二、现场安排与数据准备

### 1. 推荐展示方式

优先用鸿蒙客户端展示用户操作，浏览器独立会话或额外设备分别登录商户、骑手。这样可以突出鸿蒙应用，也能减少反复退出登录的时间。

- 用户：鸿蒙真机或模拟器投屏。
- 商户：网页独立会话，提前打开工作区。
- 骑手：另一独立浏览器会话或额外设备。
- 管理员：仅在售后或配送异常扩展演示时使用。

浏览器使用不同个人资料或不同浏览器隔离身份，不要依赖同一普通窗口中的多个标签页隔离登录态；无痕窗口之间也可能共享会话。若只有一台设备，就按本文顺序退出并登录对应账号，每次切换先说出当前角色。

网页入口：[简单外卖](https://hqyx.website/takeout/)。App 和网页必须连接同一套演示后端，才能展示同一笔订单。现场使用经过彩排的专用演示环境和测试账号，不在公共业务数据上随意操作。

### 2. 账号准备：注册和支付必须分清

| 账号 | 用途 | 提前准备 |
| --- | --- | --- |
| 新普通用户 | 现场注册、首次登录 | 未占用的手机号、可收信邮箱、符合页面规则的密码 |
| 交易演示用户 | 完整下单和余额支付的稳定方案 | 服务端已有测试余额、已设置独立支付密码、可用地址 |
| 商户 | 商品、活动、接单、评价和统计 | 已启用账号、归属正确且已上架的门店 |
| 骑手 | 上线、抢单、取餐、送达 | 已启用骑手档案、有效接单位置和覆盖门店的接单范围 |
| 管理员（可选） | 售后裁决、配送异常、ERP 调整审核 | 已启用账号，使用独立会话 |

**当前公开注册仅创建普通用户。商户、骑手使用平台预先配置的对应身份账号，不在现场演示公开自助注册为商户或骑手。当前手机管理页以账号查看、启停为主，不把“平台开通”讲成已有自助开通按钮。**

新注册用户没有赠送余额，当前也没有可用的演示充值入口。支付演示提前选定以下一种方式：

- **推荐的稳定方式**：现场完成新用户注册、登录，展示新账号初始状态；明确说明“接下来使用已准备测试余额的演示用户完成交易”，再切换交易账号。后续三端一直围绕这一交易账号的新订单展示。
- **同一新账号贯穿方式**：提前验证当前环境的支付宝沙箱、沙箱买家和支付回调可用，新用户直接使用沙箱付款。沙箱用于测试，不是真实人民币收款；不能只凭客户端返回就宣布支付成功。

若答辩要求必须由同一新账号完成注册到收货，应选第二种并提前走通。仅有余额渠道、又没有新账号资金来源时，不能承诺现场用新账号完成全部交易，也不能用前端改余额制造结果。

### 3. 准备一套一眼能认出的业务数据

建议使用“答辩演示店”和“招牌鸡腿饭”作为示例，名称可自行调整：

| 数据 | 建议安排 | 展示目的 |
| --- | --- | --- |
| 门店 | 已上架，有真实图片、地址、配送费和起送价 | 搜索时容易定位，不等待审核 |
| 主商品 | 招牌鸡腿饭，普通份 / 加大份两个规格 | 展示 SKU、价格和库存对应关系 |
| 商品库存 | 提前记录本次购买规格的初始库存，余量充足 | 与下单后的库存变化核对 |
| 营销 | 一个有效折扣活动；优惠券确认满足本店门槛 | 展示服务端计算优惠，避免多活动干扰 |
| 收货地址 | 与门店、骑手接单位置处于覆盖范围内 | 避免超距、抢单大厅看不到订单 |
| 配送方式 | **创建订单前设置为骑手配送** | 让本单进入骑手履约链路 |
| 订单备注 | “少辣，请核对规格” | 在商户端验证信息传递 |
| 评价 | “餐品完整，配送及时”及一张提前准备的图片 | 展示评价与商户回复闭环 |
| 扩展订单 | 一笔送达未超过 48 小时、有可退金额的订单 | 可选售后演示，与主线区分 |

交易前记录用户余额、商户余额、骑手累计配送与收入，以及目标规格库存。现场只比较本单带来的变化；历史数据与其他订单会影响统计总额。商户如果已有售后待偿，后续结算可能先抵扣待偿，主线优先选择无待偿的演示商户。

## 三、推荐的 15 分钟现场顺序

以下时间包含操作和简短讲解。彩排时用实际耗时调整，邮箱验证码与角色切换预留缓冲。

| 时间 | 当前角色 | 操作 | 老师应看到的结果 |
| --- | --- | --- | --- |
| 00:00–00:30 | 项目介绍 | 介绍三端主线 | 知道接下来跟踪同一笔订单 |
| 00:30–03:00 | 用户 | 隐私同意、注册、注册后登录；需要时切换交易账号 | 注册成功后需重新登录，身份与数据明确 |
| 03:00–05:00 | 商户 | 登录、维护商品规格、展示有效活动与骑手配送设置 | 本次购买的商品确实由商户经营 |
| 05:00–08:00 | 用户 | 搜索、选规格、领券、结算、提交订单、支付 | 先待付款，支付后才待接单 |
| 08:00–09:00 | 商户 | 刷新订单、核对规格和备注、接单、出餐 | 本单进入待取餐池 |
| 09:00–11:30 | 骑手 | 登录、检查位置、上线、抢单、取餐、确认送达 | 同一订单完成配送，隐私按阶段显示 |
| 11:30–13:00 | 用户 | 刷新进度、确认收货、发布评价 | 送达与完成有区别，评价保存成功 |
| 13:00–14:00 | 商户 / 骑手 | 商户回复评价、核对结算；骑手刷新收入 | 服务与资金闭环完成 |
| 14:00–15:00 | 技术说明 | 用本单解释事务、托管、幂等与权限 | 将界面操作连接到技术实现 |

**切换角色时只说一句过渡，随后核对订单号、店铺、商品规格。不要声称所有页面实时推送：按当前页面实际情况刷新或重新进入，读取服务端最新状态。**

## 四、用户端全流程：从注册到评价

### U1. 首次进入、注册与登录

1. 首次进入展示隐私同意；已同意的设备不强求重复弹出，不为演示清空整个设备数据。
2. 打开登录页，切换“注册”，填写账号名、邮箱、手机号、密码及确认密码。
3. 按页面要求填写图片中的 5 位校对码，获取 6 位邮箱验证码，再提交注册。校对码会被消费，发送失败后按页面提示更换再试。
4. 展示“注册成功”的反馈。当前实现会返回普通用户登录模式并保留手机号，**不会注册后直接进入首页**；重新输入密码登录。
5. 进入“我的”，展示新用户身份及初始数据。根据提前选择的支付方式，继续该账号，或明确切换交易演示账号。

讲解话术：

> 普通用户可以通过邮箱验证注册。注册成功后需要重新登录，后续购物车、地址和订单都按账号隔离。商户和骑手使用各自已配置的身份账号，登录入口的身份选择不会把普通用户升级成商户。

邮箱密码、验证码和登录密码不作为投屏重点。使用专用演示邮箱，避免显示个人邮件。密码找回与验证码登录留作追问项，不在主线重复走一遍。

### U2. 地址与商品浏览

1. 进入收货地址，展示地图位置与详细门牌分开填写，保存或选择一个覆盖范围内的地址。
2. 搜索演示店，打开店铺详情，展示商户刚刚维护的商品和活动。
3. 打开主商品规格选择，切换普通份与加大份，停留在价格和规格变化处。
4. 选择一个规格加入购物车，核对规格名称、数量和小计。

讲解话术：

> 同一道菜的不同规格分别管理，购物车会保留具体规格。收货地址也同时包含地图位置和门牌，前者用于配送范围校验，后者供实际送餐使用。

收藏、榜单、秒杀入口快速带过即可。主线选择普通多规格商品；秒杀留作扩展，避免营销规则叠加后难以解释。

### U3. 领券、结算与提交订单

1. 领取一张已经确认有效、满足门槛的优惠券。
2. 在结算页核对收货地址、本店商品、配送费、优惠和最终应付，输入演示备注。
3. 如果页面有不可用券，简短展示原因；不要为此临时改变整套购物车。
4. 提交后停在“待付款”页面，展示订单号、金额及支付时限。

讲解话术：

> 优惠由服务端按规则计算，前端展示预估，订单金额以服务端结果为准。提交订单先生成待付款记录并占用相关资源，此时还没有扣余额，也没有进入商户待接单队列。

此处是第一个关键停顿：让老师看清楚“提交订单”与“支付成功”是两次独立操作。默认支付期限为 15 分钟，现场解释超时释放即可，不等待倒计时结束。

### U4. 支付与进度查询

1. 余额方式输入预先设置好的独立支付密码；沙箱方式按彩排路线完成支付，并等待服务端确认。
2. 支付成功后显示“待接单”，记住本单订单号。
3. 商户、骑手操作后，刷新同一订单，依次查看制作、待取餐或配送进度。
4. 若选择助手加分展示，此时问“我的订单到哪了”，核对回复与订单详情。

讲解话术：

> 付款后资金先进入平台托管，商户还没有立即收到货款。接下来切换商户和骑手，继续处理这笔订单。

### U5. 确认收货、评价

1. 骑手送达后，用户刷新看到“已送达，待确认收货”。
2. 点击确认收货，展示“已完成”。
3. 发布评分、文字及图片评价，等待成功反馈。
4. 商户回复后回到评价展示回复内容，时间不足时由商户端展示已回复结果即可。

讲解话术：

> 骑手送达只代表履约交付，用户确认收货才触发这一步结算。订单完成后可以评价，评价能回到商户侧形成服务反馈。

## 五、商户端全流程：从登录经营到结算

商户的操作拆成三个时段穿插在主线中：下单前准备经营、付款后履约、用户确认后查看结果。没有必要为商户再重新生成一笔相同订单。

| 步骤 | 操作路径与动作 | 展示结果 | 建议讲解 |
| --- | --- | --- | --- |
| M1 登录 | 登录页选择商户身份，使用已配置账号登录 | 进入商户工作区，看到自己的门店 | 商户有独立经营入口，服务端校验门店归属 |
| M2 门店 | 商户中心查看门店资料、配送费、起送价、配送方式 | 确认本次使用骑手配送 | 配送方式保存到新订单，修改不影响已有订单 |
| M3 商品 | 商品管理打开目标商品，展示分类、图片、两种规格、库存与上架状态；保存一处有意义的修改 | 用户端刷新可看到修改结果 | 商品管理直接影响用户可购买的内容 |
| M4 营销 | 营销管理展示一个有效折扣活动；时间充足时现场创建并保存 | 用户端结算体现优惠 | 活动有时间与规则，订单保存本次定价快照 |
| M5 接单 | 用户付款后刷新订单，按订单号找到本单，核对规格、数量、备注，点击接单 | 进入制作阶段 | 未付款订单不进入商户待处理队列 |
| M6 出餐 | 点击“出餐完成” | 显示等待骑手，骑手池可找到本单 | 出餐与配送分开，商户不替骑手确认送达 |
| M7 评价 | 用户评价后进入评价管理，回复并保存 | 用户侧能够查看商户回复 | 服务反馈可闭环 |
| M8 统计与结算 | 用户确认后刷新商户账户和经营统计 | 对比余额、净结算和销量 | 营业收款、托管与商户实际净收入口径不同 |

推荐话术：

> 商户端覆盖了商品、营销、接单、出餐和评价。经营统计使用实际订单与净结算，配送费不计入商户货款收入；售后也会影响最终收入。这里我们用刚才的订单核对变化。

现场不要从零填写所有门店资料、上传多张图片和创建所有分类。主线使用已审核上架的门店，展示一处商品修改和保存结果即可。若老师关心开店，可补充打开新建店铺表单、说明平台审核，再回到已准备门店；不把等待审核塞进主线。

## 六、骑手端全流程：从登录上线到配送收入

**骑手是主线中的独立角色，建议至少留出两分钟，完整展示“上线 → 抢单 → 取餐 → 送达”。**

| 步骤 | 现场操作 | 应看到的变化 | 要突出的亮点 |
| --- | --- | --- | --- |
| R1 登录 | 选择骑手身份，以已配置骑手账号登录 | 进入骑手中心 | 身份与普通用户、商户隔离 |
| R2 接单条件 | 展示有效接单位置、接单半径，切换上线 | 显示在线、可抢单 | 在线与地理覆盖共同决定接单资格 |
| R3 找到本单 | 商户出餐后打开抢单大厅并刷新 | 找到相同订单，抢单前收货隐私脱敏 | 订单不是任何骑手在任何位置都可接 |
| R4 抢单 | 点击抢单，进入“我的配送单” | 本单归属当前骑手 | 服务端防止同一订单被重复领取 |
| R5 取餐 | 核对门店和餐品，展示取餐地点入口，点击取餐 | 订单进入配送中，用户端刷新可见 | 抢到订单与实际取餐分别记录 |
| R6 履约工具 | 展示地址复制、联系用户入口 | 履约期间可使用必要联系信息 | 地址与联系方式按履约阶段开放 |
| R7 送达 | 说明演示的是交付操作，点击送达并确认 | 用户看到待确认收货，骑手终态隐藏收货隐私 | 送达有确认，结束后收紧隐私暴露 |
| R8 收入 | 用户确认收货后刷新骑手中心 | 核对累计配送与收入 | 以服务端实际履约、结算结果为准 |

推荐话术：

> 骑手需要上线并设置接单位置。商户出餐后，这笔订单才进入可领取范围。抢单、取餐和送达是不同动作；履约期间可以查看必要地址和联系方式，履约结束后会隐藏收货信息。

现场可以展示拨号入口，但不用实际拨出电话。不宣称存在未经验证的精确收货导航或实时配送倒计时。送达是对演示订单执行交付状态操作，不声称进行了真实线下送餐。

如果抢单大厅没有本单，依次核对：是否支付 → 商户是否接单出餐 → 下单时是否骑手配送 → 骑手是否上线且启用 → 接单位置与半径是否覆盖 → 是否已被其他骑手领取。门店在下单后才改为骑手配送，不会改变这笔订单的配送快照。

## 七、加分展示：按时间只选一到两个

### A. 售后与资金闭环，约 2–3 分钟

推荐优先级最高。它能进一步展示系统对真实业务的理解。

使用提前准备的另一笔有效订单，并明确说“现在切换售后案例”，避免老师把主线订单和售后订单混淆：

1. 用户打开送达未超过 48 小时的订单，申请剩余实付内的部分退款，填写原因、上传图片。
2. 商户打开该单的售后记录，提交文字或图片举证。
3. 管理员核对双方证据和金额后裁决；商户举证不等于拥有退款审批权。
4. 回到用户端看退款记录和原渠道结果，商户端核对净收入或售后承担。

话术：

> 订单确认、评价之后，仍可在送达后 48 小时内申请售后。用户申请、商户举证、平台裁决各有边界；部分退款与全额退款分别处理，系统会继续核对资金与统计。

若老师追问结算后退款，可解释商户承担部分先扣可用余额，不足记待偿，后续结算按先后顺序抵扣，不生成负钱包余额，也不扣回骑手既有收入。不必现场额外制造余额不足案例。

### B. 商户采购与库存 ERP，约 3 分钟

该功能在**网页端“采购与库存”**展示，属于商户经营扩展。对象是餐盒、包装等非食材耗材，与菜品可售库存分开管理。

建议提前准备供应商和“餐盒”物料，现场走一张采购单：

1. 订购 2 箱，每箱 100 只，每箱 30 元，保存草稿并提交、确认采购。
2. 先收货 1 箱，查看库存增加 100 只，已收货应付 30 元，而非整张订货金额 60 元。
3. 再收货 1 箱，核对该单累计收货 200 只、累计应付 60 元。
4. 在隔离演示环境登记一条标明测试用途的线下付款凭证，展示已付 / 未付与台账；说明这是凭证登记，不是钱包转账或真实银行付款。

有时间再展示报损需另一账号审核，以及凭证纠错保留审计。不需要把所有审计菜单都走一遍。

话术：

> 经营侧还管理餐盒等耗材，按实际收货形成应付，支持分批收货、库存台账与付款对账。ERP 拥有独立服务和数据库，订单与资金核心事务仍保留在交易服务内。

不要讲成食材配方管理，也不要演示卖出一份餐品后自动扣减餐盒；当前没有这类自动扣料联动。

### C. 智能助手，约 30–60 秒

在用户端提问“我的订单到哪了”或“余额还有多少”，展示真实查询与页面入口，再与订单、钱包核对。

话术：

> 助手的订单、余额等业务问题由服务端查询真实数据，页面入口由可信规则生成。一般问答在管理员开启并配置模型接口后使用外部模型。

这项适合展示便捷入口与业务数据可信性。不要把规则查询包装成大模型推理，也不宣称助手能自主付款、退款或替用户下单。模型问答未配置或网络不稳定时，保留业务查询即可。

### D. 缺货拒单或配送异常，约 1–2 分钟

二选一，使用独立订单：

- 商户在待接单阶段选择“无法接单”，填写缺货原因并核对具体商品 / 规格，用户查看取消原因与退款。解释商户责任取消会退回仍有效券，已付款用户主动取消的返券规则不同。
- 骑手上报联系不上或地址问题，管理员查看持久记录，再按实际阶段继续、改派或取消。改派限取餐前等规则允许的阶段，不能承诺任意状态改派。

这类演示证明异常处理有责任主体、有记录、有后续动作。现场不主动制造断网或关闭服务。

## 八、怎样把功能演示讲成项目亮点

每个亮点采用“界面证据 → 业务问题 → 技术处理”三句话，不先堆技术名词。

| 亮点 | 现场证据 | 可直接使用的讲解 |
| --- | --- | --- |
| 三端协同 | 同一订单号贯穿付款、接单、抢单、收货 | 三种角色基于同一份服务端订单协作，客户端按权限展示可执行动作 |
| 多规格与库存 | 同菜不同规格、订单规格、对应库存变化 | 规格进入购物车与订单，库存通过数据库条件更新保护；一次正常下单展示业务联动，不能单独证明并发不超卖 |
| 待付款与托管结算 | 提交后待付款、付款后待接单、确认后净结算 | 业务阶段与资金阶段分别管理，避免把下单当付款、把支付金额直接当商户收入 |
| 优惠计算 | 商户活动与用户结算对应 | 服务端统一计算折扣、新客优惠和券，订单保存定价结果，避免前端任意决定价格 |
| 隐私与权限 | 骑手抢单前、履约中、送达后信息差异 | 权限同时取决于身份、订单归属与履约阶段，服务端继续独立校验 |
| 异常闭环 | 用户申请、商户举证、平台裁决、退款历史 | 售后处理覆盖金额、证据、责任与结算结果 |
| 鸿蒙与跨端 | 鸿蒙用户端、网页商户 / 骑手操作同单 | 使用 ArkTS / ArkUI 开发 HarmonyOS NEXT API 26 客户端，网页复用同一业务后端 |
| 经营扩展 | ERP 分批收货、应付、库存台账 | 采购耗材服务独立管理自身数据，交易资金与菜品库存保留本地事务边界 |

技术讲解重点选三项即可：

1. **事务与幂等**：下单的库存、优惠占用和订单写入共同受事务保护；唯一约束与条件更新防止重复建单、重复结算和超卖。按钮防连点只是交互保护。
2. **可靠事件**：业务数据与 Outbox 事件在同一事务保存，后台再投递，失败持久重试、消费幂等。订单核心过程仍采用同步本地事务。
3. **缓存与边界**：Redis 缓存浏览热点数据，使用空值占位、互斥回源和随机过期时间应对不同缓存问题；缓存故障可回源数据库。不要声称所有 Redis 故障都无延迟、所有服务都无限可用。

测试与性能放在问答或一页证据截图中，不在交易过程中翻终端：

- README 记录的 10 月 28 日 GitHub Linux / MySQL / Redis CI 为 711 项全部执行通过；这是该版本的历史验证，不能代替当前工作区或现场版本验收。
- 10 月 27 日本机双 App 历史短测：各 1 CPU / 768 MiB，20 秒、2200 次请求，109.56 RPS、P95 61.32 ms。介绍时必须带测试条件，不能推导线上生产容量或“支持万人并发”。
- 沙箱与 mock 渠道验证不等于真实外部支付、退款联调；debug HAP 构建成功不等于正式签名或应用商店上架。

## 九、彩排、压缩与现场备用方案

### 答辩前至少按正式设备完整走一次

- 从注册验证码开始，检查邮件服务、图片校对码、当前密码规则和注册后登录；演示设备与账号会话也按正式安排使用。
- 确认支付方式。余额支付先设置独立支付密码，保存后按提示重新登录；沙箱先确认回调与主动查单能推进状态。
- 确认门店上架、SKU 可售库存、起送价、优惠有效期、收货地址与骑手覆盖范围；录下初始余额、库存和收入。
- 用一笔完整新订单走通三端，核对金额、订单号、规格、状态、评价和收入，不只检查首页能打开。
- 准备一段本项目真实操作的本地备用录屏，覆盖注册登录到确认收货；准备主线关键截图并脱敏，存放于 `TemporaryCacheStorage/`。
- 彩排会消耗库存、券、余额和新客资格。正式演示前重新准备充足数据；不要依赖彩排后已经失效的新客优惠。

### 如果时间只有 8 分钟

保留注册登录的关键过程，商户登录和商品规格约 1 分钟，用户选购与支付约 2 分钟，商户接单出餐约 30 秒，骑手登录及完整配送约 1 分钟，收货、评价、结算约 1 分钟，其余留给开场与注册。以彩排实测为准，邮件等待过长就切换真实备用录屏。

不展开 ERP、售后分支、模型问答、密码找回和技术压测数据。商户与骑手仍要说明身份并展示登录结果，登录输入可通过录屏压缩，不假装跳过的步骤已经现场执行。

### 常见问题的处理

| 现场情况 | 处理方式 |
| --- | --- |
| 邮箱验证码迟迟未到 | 不连续点击发送；按提示等待或更新校对码，随后切换注册备用录屏和已注册账号，明确说明展示方式 |
| 新用户余额为零 | 按开场约定切换已准备余额的交易账号，或走已彩排的沙箱；不临时寻找不存在的充值入口 |
| 商户没有收到订单 | 先核对是否真正支付成功、账号门店归属与筛选，再刷新；待付款不显示在商户待处理列表是正常规则 |
| 骑手看不到订单 | 按“支付、出餐、配送快照、上线、位置半径、是否被领取”顺序核对 |
| 支付、抢单等操作结果未知 | 先查询原订单或配送单核对，不重复创建订单或更换请求规避结果核对 |
| 余额 / 收入没有预期变化 | 确认用户是否已确认收货、页面是否刷新、商户是否存在待偿；按实际结算口径解释 |
| 网络或服务不可用 | 简短说明现场网络 / 服务问题，切换本地真实录屏与关键截图，不把录像说成现场成功 |

结束话术：

> 刚才通过同一笔订单，演示了用户注册登录、商户经营、用户支付、商户出餐、骑手配送，以及确认收货、评价和结算。项目的重点是让每个角色的操作都能在其他端得到真实反馈，并让库存、权限和资金规则随业务阶段正确推进。
