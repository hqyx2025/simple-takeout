# 骑手端设计与实施计划（四端改造 · 阶段 0）

> 目标：在现有「用户端 / 商户端 / 管理端」三端基础上新增**骑手端**，形成四端完整闭环。
> 本文件是实施前的设计基线，经确认后按「分步实施」逐个小步落地并构建验证。

---

## 一、现状与改造要点

### 现状（以仓库为准）
- 配送方式为**商户自配送**：订单状态机为数字 `1 待接单 → 2 制作中 → 3 配送中 → 4 已送达（待确认）`，商户端负责 `accept(1→2)`、`deliver(2→3)`、`complete(3→4)`。
- 资金：下单即扣款进入平台托管（`escrow_status=0`），用户确认收货后 `escrow 0→1` 结算给商户。
- 角色：`USER=0 / MERCHANT=1 / ADMIN=2`（`AuthInterceptor` 按 role 鉴权）。

### 改造核心
把**配送环节从商户转移到骑手**，但**不改动数字状态码本身**（数字状态仍是唯一权威）：

| 状态 | 触发方（改造后） |
| --- | --- |
| 1 待接单 | 用户下单 → 商户接单 |
| 2 制作中 | 商户备餐；商户点「出餐完成」写入 `ready_time`，订单进入**待取餐池** |
| 3 配送中 | **骑手**取餐后触发 |
| 4 已送达 | **骑手**送达后触发 |
| escrow 0→1 | 用户确认收货（不变） |

> 关键设计：**不新增数字状态**。用 `orders.ready_time` 是否为空来表达「已出餐、待骑手取餐」，避免引入 `7 待配送` 这类新状态码而破坏既有状态机口径（大纲 17.1「以仓库现状为准」）。

## 二、数据模型变更

### 1. 新增 `riders` 表（骑手档案）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| user_id | BIGINT UNIQUE | 关联 `users.id`（`users.role=3`） |

| phone | VARCHAR(20) | 联系电话 |

### 2. `orders` 表新增字段
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| rider_id | BIGINT DEFAULT 0 | 0 表示未分配 |

> 迁移方式沿用现有做法：更新 `schema.sql` 建表语句 + 在 `SchemaMigration` 里幂等补列（`information_schema` 检查后 `ALTER`）。

## 三、配送流程（抢单模式）

```
用户下单(1) → 商户接单(2) → 商户出餐(ready_time) → [待取餐池]
                                                        ↓ 骑手抢单(条件更新 rider_id)
                                                    骑手取餐(2→3 配送中)
                                                        ↓
                                                    骑手送达(3→4 已送达)
                                                        ↓ 用户确认收货(escrow 0→1)
                                                    商户收款结算
```

**并发要点（必须条件更新）**：
- 抢单：`UPDATE orders SET rider_id=? WHERE id=? AND rider_id=0 AND status=2 AND ready_time<>''`，返回 0 行 = 已被他人抢走。
- 取餐：`… SET status=3 WHERE id=? AND rider_id=? AND status=2`。
- 送达：`… SET status=4, complete_time=? WHERE id=? AND rider_id=? AND status=3`。

## 四、接口设计

### 骑手端（role=3）
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/rider/orders/pool` | 可抢订单池（status=2 且 ready_time≠'' 且 rider_id=0） |
| POST | `/api/rider/orders/{id}/grab` | 抢单（条件更新，防重复抢） |
| PUT | `/api/rider/orders/{id}/pickup` | 取餐（2→3） |
| PUT | `/api/rider/orders/{id}/deliver` | 送达（3→4） |
| GET | `/api/rider/orders` | 我的配送单（进行中 / 已完成） |
| GET | `/api/rider/profile` | 骑手资料与统计（单量 / 收入） |
| PUT | `/api/rider/status` | 上线 / 下线 |

### 商户端（新增动作）
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| PUT | `/api/merchant/orders/{id}/ready` | 出餐完成，写 `ready_time`，进入取餐池 |

> 现有 `deliver` / `complete` 动作在引入骑手后**保留但不再由商户端调用**（兼容旧数据/回退）。

### 管理端
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/riders` | 骑手列表 |
| PUT | `/api/admin/riders/{id}/status` | 启用 / 停用 |

### 用户端
- `GET /api/orders/{id}` 的 `OrderView` 增加骑手信息（`riderName` / `riderPhone`，仅配送中及之后返回）。
- 订单详情展示骑手信息 + 配送进度（复用现有骑手动画，后续可接地图轨迹）。

## 七、风险与取舍

1. **不改数字状态码**：用 `ready_time` 表达「待取餐」，避免破坏既有状态机与前端状态文案（大纲 19.1 口径）。
2. **抢单必须条件更新**：并发抢单只允许一人成功，失败方给出「已被抢走」提示。
3. **骑手收入简化**：不做骑手独立钱包/提现，只统计单量与累计配送收入；真实结算为演进项。
4. **地图轨迹**：优先复用现有「骑手进度动画」；真实轨迹上报为演进项（需要位置上报与地图渲染）。
5. **兼容旧数据**：历史订单 `rider_id=0`、`ready_time=''`，走原商户自配送路径，不受影响。
