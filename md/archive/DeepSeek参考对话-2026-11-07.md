这题考的是技术选型的边界判断，不是“哪个更好”。一个能站住的回答框架是：事务消息解决的是“本地事务与消息发送的原子性”，但它引入了对特定 MQ 的强依赖，且半消息回查机制在中小规模系统里运维成本偏高。Outbox 的价值在于把可靠性问题收敛到你已经有的数据库事务里——业务写入和事件写入在同一个 @Transactional 边界内完成，要么一起提交，要么一起回滚，不引入新的分布式协调组件。代价是事件投递有中继延迟，且需要自己处理中继的多实例竞争和僵尸事件回收。如果你的系统规模不需要 RocketMQ 的事务消息语义，Outbox 是更轻的选择；如果已有 Kafka/RocketMQ 基础设施，事务消息可能更合适。关键不是“我用了 Outbox”，而是“我知道它在什么条件下是更好的选择”。-

追问 2：Outbox 中继挂了怎么办？事件会不会永久卡在表里？

这是 Outbox 模式最容易被打穿的地方。如果你的 OutboxRelayJob 是单实例定时扫描，面试官会立刻问：中继进程挂了，谁来投递？重启后怎么知道哪些事件没发？你的 README 写了“永不放弃投递”，但需要能说清楚“不放弃”的机制。

追问 3：Redis Stream 的“至少一次”投递，为什么消费端还必须做幂等？

因为 Redis Stream 的 consumer group 不提供 exactly-once。消费者 XREADGROUP 拿到消息后、在 XACK 之前崩溃，消息会留在 PEL 里，被 XCLAIM 或 XAUTOCLAIM 重新投递给另一个消费者。这就是“至少一次”的来源。所以幂等键不能依赖 Redis 的投递语义，必须落在业务侧——比如 message_id + business_key 的唯一约束或幂等表。面试官如果继续问“PEL 大了会怎样”，你要能说出：PEL 是内存中的基数树结构，未确认消息堆积会消耗堆内存并拖慢 XREADGROUP 性能，生产上需要监控 PEL 长度并对僵尸消息做主动 claim。-

二、安全的下半场：你只讲了“认证”，没讲“授权”和“数据安全”

前几轮详细拆了登录防御（认证），但外卖系统真正的安全事故高发区在授权和数据层：

水平越权：用户 A 能不能通过改 orderId 查到用户 B 的订单？骑手能不能抢别人已接的单？这类问题的标准防御是资源归属校验——每个查询/操作都要带 userId 条件，而不是只校验“已登录”。面试官问“你怎么防越权”时，答“JWT 校验了 token”是错的，正确回答是“所有资源操作在 SQL 层带 owner 条件，配合网关层的路径白名单”。

垂直越权：普通用户能不能调商户/平台接口？你的四端角色（用户/商户/骑手/平台）正好是讲 RBAC 的素材——角色-权限映射、接口级注解鉴权、网关层角色路由。

SQL 注入：MyBatis 里 #{} 和 ${} 的区别，你有没有用 ${} 拼接过动态排序/表名？如果有，白名单校验了吗？

敏感数据：手机号、地址、支付信息在日志里脱敏了吗？数据库里加密存储了吗？你的项目已经有“钱包/助理加密密钥”的体系，正好可以延伸到字段级加密 + 日志脱敏。

下单幂等：用户连点两次提交，会不会生成两笔订单？标准做法是前端防重 + 后端幂等 token（下单前先取 token，提交时带 token 校验并删除）。

四、算法层选型：限流和缓存，你用的是哪种“实现”

前几轮提了限流，但没讲算法选型。面试官如果追问“你的限流用的什么算法”，答“Redis 计数器”是不够的：
