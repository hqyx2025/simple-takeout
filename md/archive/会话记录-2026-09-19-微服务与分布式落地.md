## 线 A：分布式基线收口（让单体真能水平扩展）

原后端已是「分布式就绪的单体」（无状态 JWT、Redis 跨实例限流、事务性 Outbox、Compose 编排），
缺的是「多实例下的一致性收口」。修掉 5 个缺口：

| # | 缺口 | 修法 |
|---|---|---|
| G1 | Outbox 中继无行级锁，多实例重复搬运 | `claimPending` 用 `FOR UPDATE SKIP LOCKED` + `owner`/`lease_until` 租约 |
| G2 | 消费者名固定 `consumer-1`，多实例互抢 | `consumer-<InstanceId>`（主机名+进程号+启动碎片） |
| G3 | 定时任务多实例重复扫描 | `SchedulerLock`（Redis，**不可用时 fail-open**） |
| G4 | 订单号 = 秒级时间戳 + 4 位随机数，必现碰撞 | 雪花 ID + `order_no` 唯一键冲突换号重试一次 |
| G5 | 无 traceId 贯穿 | `X-Request-Id` → MDC → logback pattern + 响应头 |

### 实测证据（非 mock）

- **SKIP LOCKED**：真实 MySQL 8.4.0 上两个并发事务，会话 A 持锁时 B 拿到**不相交**的行集（A={1,2,3} / B={4,5,6}）
- **租约四场景**：未过期不可再认领 / 过期可重新认领 / `markRetry` 即释放 / 已投递永不认领
- **订单号先红后绿**：回滚成旧实现 → 同秒 200 单产出 **199 个不同号**（用例 RED）；换雪花 → 200/200
- **雪花并发**：16 线程 × 2000 = 32000 个 ID 零重复

### 一处对 Spec 的修正

Spec 称 G3 是「重复取消/重复退款」的正确性缺口。实测 `cancelPending` **早已是条件更新**
（`WHERE id=? AND status=0`），多实例并发也只有一次成功——真实缺口仅是**重复扫描的浪费**。
因此 `SchedulerLock` 定位为性能优化而非正确性保障，且必须 fail-open（Redis 挂时任务照跑）。

  Dockerfile 改双 jar 镜像

### 实测发现两个 Spec 未预见的安全缺陷（均已修复 + 契约测试守护）

**① XFF 被网关整体剔除 → 全站共用一个限流桶**
根因：Spring Cloud Gateway 4.3.x 的可信代理机制，来源不匹配 `trusted-proxies` 时调用
`RemoveXForwardedHeadersFilter` **主动剔除** X-Forwarded-*；且该属性语义是**正则**匹配
远端地址字符串而非 CIDR（写成 `0.0.0.0/0` 匹配不上 `127.0.0.1`，静默失效）。
后果：后端 `LoginRateLimiter.clientIp()` 退化为用网关地址 → 一人触发封禁让所有人登录失败。

**② 客户端伪造 XFF 可绕过登录限流**
`for-append: true` 时攻击者的 `X-Forwarded-For: 1.2.3.4` 被保留在列表**最前**，
而后端取 `split(",")[0]` 正是伪造值 → 每换一个 IP 就重置一个限流桶。
改为覆写语义（`for-append: false`），网关作为信任边界丢弃不可信输入。

两条都留了契约测试（`GatewayXForwardedConfigTest` 4 用例）并做「先红后绿」验证。

## Phase 3：方案 C（共享契约层先行）

用户先要求在自己的评估基础上拍板，我给出 A/B/C 三方案，用户选 **C**。理由（实测证据）：

1. **抽 catalog 会破坏下单原子性**：`OrderService` 有 **25 处** catalog DAO 调用（`storeDao` 11 /
   `goodsDao` 6 / `seckillDao` 6 / `specDao` 2），其中 6 个是**写操作**
   （`goodsDao.deductStock`、`specDao.deductStock`、`seckillDao.deductQuota`、
   `storeDao.updateMonthlySales`、`goodsDao.restoreStock`、`specDao.restoreStock`）
   **全在 `@Transactional` 内**。跨进程后即分布式事务，而 Saga 是 Phase 5 的事——
   中间会留「库存已扣但无补偿」的窗口
2. **共享库下外拆收益被高估**：数据并未隔离，只是多一个进程；「网关能按域路由」Phase 2 已验证
3. **Spec 设想的「挪 Controller 修路由」不成立**：`/api/stores/{id}/reviews` 的 URL 不变，
   网关按前缀照样送错，修正须落在网关精确路由规则

### 实际落地

- 新增 `takeout-common`（**65 个文件**：model 30 / dao 21 / common 8 / security 5 / service 1）
- **关键手法：保持包名 `com.example.takeout.*` 不变、只改物理位置**——Java 包名与路径无关，
  因此全部既有 import **零改动**。这是 200+ 用例跨模块搬迁后仍全绿的原因；
  按常规改包名会产生数百处 import 变更，风险与工时高一个量级
- **中途纠错**：第一版把全部 21 个 DAO 无差别搬进 common（含购物车 `CartItemMapper`，
  属 trade 域），`mvn compile` 失败暴露该错误，已移回 app。
  教训：共享层边界按「本域 vs 跨域共享」判断，不是「能不能编译过」
- 删除自己造的两个东西：只含 pom + 启动类的空骨架 `takeout-catalog-service`、
  零引用且签名靠猜的 `StoreQueryPort`

### 实测发现的既有缺陷（与拆分无关，已修）

**Redis 挂掉时下单直接 500**，违背 AGENTS.md §4「Redis 不可用时跳过防重校验」的承诺。
根因：`OrderService:172` 的 `getIfAvailable()` 只判断 **bean 是否存在**，不代表真能连上；
Redis 进程挂了 bean 仍在，`setIfAbsent` 抛 `RedisConnectionFailureException` 冒泡成 500。

- **归属确认**：`git diff` 确认该文件未被本次拆分修改，代码来自 `141ea68`
- 同模式的另外 5 处（`SchedulerLock`/`HotDataCacheService`/`DomainEventPublisher`/
  `LoginRateLimiter`/`DomainEventConsumer`）**都有异常保护，只有这一处漏了**（单点遗漏）
- **先红后绿**：修复前 500 → 修复后 200（订单 id=58，库存 966→965）；
  单测把 catch 体改回 `throw e` → 2 用例报 `RedisConnectionFailure`，恢复 → 3/3 绿
