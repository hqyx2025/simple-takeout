## 用户需求

> 骑手端的注册并没有正确注册。传给后端的 role 是 0 而不是 3。

> 注册后不应该直接登录的，而是让用户自己再输入一遍。

两条需求都在登录页的注册链路上，构成同一段流程的前后两步：先把角色注册对，再把注册与登录拆成两步。

## 一、根因分析

### 1. 骑手注册落库成了普通用户（缺一不可的三个事实）

| # | 事实 | 位置 |
| --- | --- | --- |
| ① | 前端用「是否商户」二分映射角色：`role === UserRole.MERCHANT ? 1 : 0`，`UserRole.RIDER`(=3) 走 else → **发 0** | `entry/src/main/ets/service/ApiService.ets` 的 `apiRegister` |
| ② | 后端只校验 `role != 0 && role != 1 && role != 3`，**0 是合法值** → 注册返回成功，建的是 `role=0` 普通用户（还按用户规则送了 20 元余额） | `server/.../service/AuthService.java#register` |
| ③ | 注册流程第二步自动登录带 `loginType=RIDER`，后端 `roleOf("RIDER")=3` 与 `user.role()=0` 不等 → `BizException(403, "登录端与账号角色不匹配，请切换正确的登录端")` | `AuthService#login` + `LoginPage` |

所以表现不是"注册失败"，而是**注册成功但立刻登不进去**——注册接口没有任何报错，账号却已经错了。
`LoginPage` 当时还会把 403 的原文当错误提示弹出来，用户看到的是"登录端与账号角色不匹配"，与"注册"二字毫无关联，
这也是本缺陷难以第一眼定位的原因。

### 2. 与上一次骑手缺陷的关系（同一缺陷类的另一半）

前序提交 `a0234ce` 修的是**反向**映射：`ApiService.toUser()` 只映射 `2→ADMIN / 1→MERCHANT`，
其余一律落 `CUSTOMER`，导致骑手登录后被认为是普通用户、被登录页的角色校验 `logout()` 掉。
那次只补了「服务端 → 前端」的读方向，**没有同步检查「前端 → 服务端」的写方向**，
于是同一张表在写方向留了洞，本次踩中。

> 教训：`UserRole` 与后端 role 码是一张双向映射表，
> **任何一个方向只覆盖部分角色，都会以"另一端的校验失败"的形式暴露**。
> 新增角色时必须同时改 `Models.ets` 的 `UserRole`、`toUser()`、`toServerRole()` 三处。

## 二、修复内容

### 1. 补全服务端角色码映射（`0b9d02b`）

- `ApiService.ets` 新增 `toServerRole(role: UserRole): number`，显式覆盖 **0 用户 / 1 商户 / 2 管理端 / 3 骑手** 四种角色，
  与既有 `toUser()` 成对；`apiRegister` 改为调用它。函数注释锁住失效表现，避免后续被"简化"回二分写法。
- `LoginPage.ets` 同一缺陷类的三处分支补骑手（此前骑手全部落到"用户"分支）：
  提交日志的角色名、角色不匹配的错误提示（新增"该账号不是骑手账号"）、快捷登录失败提示（新增"骑手快捷登录失败"）。
- **后端未改**：`AuthService.register` 本来就接受 role=3，问题全在前端。
- 骑手档案无需在注册时创建：`RiderService.profile()` 在首次进入骑手端时幂等建档。

### 2. 注册成功后不再自动登录（`3267216`）

原流程注册成功后立刻用同一份明文密码再登录一次并直接进首页，用户没有再次确认密码的机会，
也把"注册"和"登录"两步揉成了一步。

改为：注册成功 → **停留在登录页并切回登录态**。

- 清空密码、清空用户名；**手机号保留**（便于对照，只强制重敲密码）。
- `selectedRole` 保持注册时选择的角色，登录时 `loginType` 仍与被注册角色一致（骑手注册后登录端仍是 RIDER）。
- 新增 `@State tipMsg`，绿色成功提示「注册成功，请使用该密码登录」+ Toast「注册成功，请登录」；
  提交按钮与手动切换登录/注册模式时清空该提示，避免陈旧文案残留。
- 删除自动登录分支：注册**不再产生任何登录态与 Token**，`isLoggedIn` / `authToken` 全程不变，
  session 完全由用户手动登录那一步建立。
- 仓库内注册调用点仅此一处（`LoginPage.ets`），无其他入口需要同步。

## 四、本次暴露的工具链陷阱

1. **hvigor 构建在受限文件沙箱下会静默挂死**：hvigor 需要写工作区之外的
   `C:\Users\Administrator\.hvigor\project_caches\...` 并拉起构建 daemon。受限沙箱下依次表现为
   ① `ENOENT ... @ohos\hvigor\bin\hvigor.js` → ② `程序"node.exe"无法运行: Access is denied` →
   ③ 命令**空输出且立刻返回**，而 `.hvigor/outputs/build-logs/build.log` 时间戳**一动不动**（即构建根本没跑）。
   放开为完全访问后 2 秒内即 `BUILD SUCCESSFUL`。
   **判定依据只能是 `build.log` 里的 `BUILD SUCCESSFUL` + HAP 时间戳**，空输出与 `exit=0` 都不能当成成功。
2. 首次报的 hvigor 缓存 ENOENT 是**瞬时状态**（重试即恢复，`bin/hvigor.js` 实际存在），不必按提示删缓存目录。
3. `Get-CimInstance Win32_Process` 在受限沙箱下报「拒绝访问」，查进程命令行需换方式。
4. **git / mysql 的正常 stderr 会被 PowerShell 当成 terminating error**：`git push` 成功仍返回 `exit code: 1`
   （stderr 打 `remote: Powered by GITEE.COM` 之类进度），`mysql -p` 亦然（stderr 打密码告警）。
   判定成败要看业务输出行（如 `1351ecf..8bb0ea5  master -> master`），不要只看 `$LASTEXITCODE`。
   这与 `AGENTS.md` §8 里 hvigor 写 stderr 导致 `$ErrorActionPreference='Stop'` 误判是同一类问题。
