# 会话记录：微服务、ERP、并发、JVM 与发布验证

归档日期：2026-10-27（Asia/Shanghai）。项目：简单外卖。

本记录按用户要求归档本次需求、实现、实测、发布与限制。历史归档和既有工作区内容保留；实际运行事实以本节发布结果和对应证据为准。

## 用户要求与实现范围

用户要求先核实源码，再直接完善微服务、高并发、JVM 性能治理及餐饮 ERP，完成迁移、后端接口、可操作页面和验证。随后要求 Docker 与 HAP 设备验证、说明技术现状，并明确授权更新 GitHub、部署服务器、更新文档、归档会话及更新本机 Docker 镜像。

- API 26 / ArkTS 前端、Java 25 / Spring Boot 后端、Gateway、Redis、MySQL、JdbcTemplate、购物车 MyBatis-Plus 和已有事务 / 幂等 / Outbox 均沿用。
- 拆出 `takeout-erp` 独立服务及独立数据库；交易主服务拥有账号、菜品、订单和资金事实。商品目录与订单扣库存存在本地事务耦合，因此当前继续留在主服务，未宣称目录已独立拆分。common 的 DAO、安全和业务实现迁回 app，仍保留共享模型。
- ERP 管理餐盒、包装等非食材耗材：供应商启停、采购草稿 / 提交 / 确认 / 关闭、分批收货、防超收、防重复入库、不可覆盖的库存台账、盘点 / 报损及独立审核、冲销、应付 / 付款凭证 / 未付和经营对账。采购单位与固定基础单位通过单据换算率转换；付款是线下付款凭证登记，不扣应用钱包。没有引入食材配方或将菜品销量直接当作原料消耗。
- 内部调用有连接与读取超时；资金 / 库存写入不做 HTTP 盲重试。Outbox 保留失败事件、退避重试、收件箱幂等、积压观察和管理端重投入口。ERP 授权仍依赖主服务，主服务不可用时拒绝业务操作。
- 保留数据库事务、条件更新、唯一约束、精确金额和 specId；补齐浏览分页边界、API 在途准入、请求体上限、线程 / 连接限制。普通缓存故障回源，限流故障保留本地保护。
- 增加本地启动、有限负载和受控 JVM 诊断脚本。GC 日志轮转，JFR 按需启动并限容量；默认关闭 OOM 堆转储，不公开诊断文件。

## 实际验证

| 范围 | 实测结果与边界 |
| --- | --- |
| Docker 后端 | Temurin 25.0.5+8、MySQL 8.4.11、Redis 7.4.11；Maven reactor 676 项，0 失败 / 错误 / 跳过。镜像构建时官方 JDK 归档使用固定 SHA-256 校验，本机缓存仅解决构建网络问题 |
| Web | 四套 Node 回归 82 项通过；真实浏览器完成供应商 → 采购确认 → 两批收货 → 台账 → 跨账号审核报损 → 付款对账，最终耗材库存 195 只；超收被拒绝 |
| 并发 | 双 App 实例下购物车累加、重复下单、余额支付、骑手抢单和退款审批通过；24 次同收货请求仅入库一次，并发付款仅一个成功者。核对库存、余额及支付 / 退款台账 |
| 故障 | ERP 停机返回 503，订单仍可提交，失败事件留存后重投；同事件额外重复投递 3 次，收件箱仅一条。权限服务停机时 ERP 拒绝操作，恢复后正常。Redis 停机 300 次读取中 240 次成功、60 次正常 429，余额和库存不变。过大请求 413，内部路由不对外开放 |
| HAP | 主包 / 测试包及隔离验证包均构建成功。API 26 Pura X View 模拟器六类通过：LoginFlow、SearchFlow、StoreDetailCart、CheckoutFlow、OrderPaymentSelection、AdminFlow。结算新增一笔 22.59 元待付款订单，余额不变、库存减少 3；没有发起真实外部支付 |
| 阶梯负载 | 1 / 4 / 8 / 16 / 32 并发。8 并发约 170.13 RPS，P99 274.05 ms；32 并发出现 10 次正常 429，业务错误 0。不能把达到下单预算后的拒绝计作重复扣款或性能通过 |
| 定速负载 | 双 App 各 1 CPU / 768 MiB、48 个负载账号，80% 浏览 / 10% 加购 / 10% 下单并余额支付；100 次混合操作/秒，20.08 秒，2200 次 HTTP 请求，109.56 RPS，P95 61.32 ms，P99 88.85 ms，错误 / 拒绝均为 0。新增订单 200，库存减少 200，余额扣减及支付台账增加均为 2200 元，无重复成功支付 |
| JVM | 自动选择 Serial GC；定速采样期间两 App 平均占用约 40.45% / 36.98% 单核，堆使用约 44–62 MiB，非堆最高约 126 MiB，直接内存各约 8 MiB。无 Full GC，JFR 最大 GC 停顿 2.13 ms，连接池各最多 10 个连接、采样无等待。未据此更换 GC 或堆叠参数，短测不能排除长期泄漏 |

设备验证使用独立包名和只连接本机的配置，原包和已有数据保留；正式源码恢复后按字节校验并重新构建正式域名优先的 debug HAP。Search 用例改为点击真实原生清除按钮，保留历史区域和结果清除断言。Docker 原失效 IPC 目录保留备份后恢复启动，未重置 Docker 数据。

原始脚本、日志、截图、JFR、私有配置和结果保存在本机 `TemporaryCacheStorage/docker-device-verify/`。其中私有凭据、令牌和诊断文件不提交 GitHub、不公开下载。关键结果为 `linux-tests.json`、`hap-verification.json`、`browser-flow.json`、`functional.json`、`fault-check.json`、`capacity-target.json`、`resource-summary.json` 和 `final-runtime.json`。较早的 Windows 实测属于另一环境，未挪用为本轮 Docker 或服务器性能结果。

## 保留边界

- 当前属于交易主服务 + 独立 ERP 的服务拆分，商品目录尚未独立，common 仍共享部分模型。
- ERP 覆盖采购及非食材耗材，不含食材配方、自动耗料、通用财务总账、税务、人事或制造排程。
- 本轮模拟器和本机负载结果不代表物理真机、真实外部支付 / 退款、真实邮件或生产容量；服务器数据库版本与本机测试版本须分别记录。
- 长期稳定性、全页面字体 / 深色模式、正式签名与 AppGallery 发布仍未验收。既有安全复测的 RT-16 / 22 / 31 / 32 边界继续保留。
