## 一、店铺详情页「＋」后数量不显示（`86b2d37`）

**两个缺陷叠加**，只修任一个都不生效：

1. `getQty()` 在渲染路径里读 `AppStorage.get('cartItems')`。`AppStorage.get()` 直接读全局存储，**绕过 ArkUI 的状态观察**，组件不与它建立依赖 → 值变了界面不重建。
2. ForEach key 用稳定的 `goods.id`，点「＋」后局部更新对象/数组容器都会按 key 复用旧列表项。

修法：`getQty()` 改读被观察的 `@StorageLink cartItems`，并新增 `@State goodsRenderVersion`（在 `updateCartInfo()` 里自增）拼进 key（`` `${this.goodsRenderVersion}-${item.id}` ``）。

**验证方式（关键）**：这类「状态变了但视图不重建」的缺陷，光看修复后变绿不能证明用例有效。做法是**临时回滚修复**跑一遍确认必然失败（`expect 1 equals 2`），恢复后再确认通过。新增 `entry/src/ohosTest/ets/test/StoreDetailCart.test.ets`（111 行）就是按这个标定流程写的，设备实测 **1/1 Pass**。

## 二、分类切换空转、订单页标题被裁、钱包页（`14402fb`）

### 2.1 分类分区切换"点了没反应"——根因在种子数据

链路本身早就写好了：芯片走美团式**店内分类**（`categories.type='MERCHANT'` + `goods.merchant_category_id`），接口 `GET /api/stores/{id}/categories`。但种子数据**从未建过任何 MERCHANT 分类**，商品的 `merchant_category_id` 全为 0 → 芯片只剩「全部 + 该店唯一的平台分类」，两者返回的列表**完全相同**，所以点了看起来没反应。

> 排查中被一个错误假设误导过：曾先按 `/api/stores/{id}/merchant-categories` 探接口，得到 500 `NoResourceFoundException: No static resource api/stores/2/merchant-categories`——真实路径是 `/api/stores/{id}/categories`。**URL 猜错时不要先怀疑业务代码。**

由 `DataSeeder.ensureStoreMerchantCategories()` 幂等补齐（第一版，见第三节的补修）。

### 2.2 订单页「我的订单」被裁掉下半

头部 `Row` 同时写了 `.height(56)` 与 `.padding({ top: 40 })`。**ArkUI 的内边距算在高度内** → 内容区只剩 16px，20 号字标题需要约 27px，被裁。去掉写死的 `height` 即可。

### 2.3 删除「余额数据来自数据库」文案

删除该 `Text(this.refreshStatus)` 节点，保留「立即刷新」按钮并右对齐。`@State refreshStatus` 仍被失败提示复用，故保留变量本身。

### 2.4 新增钱包页（余额 + 已绑定银行卡）

用户拍板只读钱包页，因此**没有**做绑卡/解绑。按项目规则「业务数据禁止前端模拟」，银行卡走真实数据链路：

| 层 | 内容 |
| --- | --- |
| 表 | `bank_cards`（`ensureBankCardTable()`，含 `card_no_last4`、`status`、`idx_bank_card_user`） |
| 种子 | `ensureBankCards()` 为 `13800138000` / `13900139000` 各补两张（招商银行·储蓄卡·6688、工商银行·信用卡·8899） |
| 接口 | `GET /api/wallet/bank-cards`（`UserCenterController` + `UserCenterService.listBankCards`） |
| 前端 | 新增 `pages/BalancePage.ets`（316 行），`fetchBankCardsApi()`，注册进 `main_pages.json` |

**安全口径**：库里**只存卡号后四位**（`card_no_last4 VARCHAR(4)`），掩码由 DAO 的 `MAPPER` 拼装（`"**** **** **** " + last4`），因此数据库、接口与日志**都不出现完整卡号**。余额的权威来源仍是 `users.balance`（`/auth/me`），钱包页**刻意不自行推导余额**。

两个 `ensureXxx()` 都同时挂在 `run()` 的「已有数据」与「全新 `seed()`」两个分支上，保证旧库与新库都能补齐。

### 2.5 钱包页踩到的真实产品缺陷：Jackson 不序列化 record 方法

掩码最初写成 record 的**普通方法** `public String cardNoMasked()`。它既不满足 `getX()`/`isX()` 命名，也不是 record 组件 → **Jackson 序列化 record 只认组件**，接口里根本没有这个字段，前端 `Text(card.cardNoMasked)` 拿到 `undefined`，银行卡号整行空白。

设备 dump 的文本节点从「默认」直接跳到下一行说明文字，正是这一行缺失的证据。修法：把 `cardNoMasked` 提升为 record **组件**，值在 DAO 构造时算好传入。修正后接口返回 `"cardNoMasked":"**** **** **** 6688"`。

## 三、分类分组补修：两种漏网店铺（`bed04f1`）

第一版 `ensureStoreMerchantCategories()` 上线后复查数据，**仍有 10 家店不可用**。三个独立漏洞：

| 漏洞 | 现象 | 修法 |
| --- | --- | --- |
| 判定条件只看「有没有分类」 | 商户自建过分类但商品没挂上去的店继续空转 | 改用「该店**使用的**分类数 < 2」才重新分组 |
| 按 `is_special` **全局**一刀切 | 31~40 号店各 6 件商品**全是招牌** → 全塞进「招牌热销」，芯片仍只有一个非空项 | 改**按店铺**、按商品 id 顺序确定性轮转 |
| 只补 `merchant_category_id=0` 的行 | 被第一版写错的行已不是 0，永远够不到 | 重新分组按「使用分类数 < 2」触发，**不依赖原值** |
| 默认分类按**位置**推断 | 商户 3 自建的「你好」占了首位 → 永远建不出「招牌热销」，招牌商品落进「你好」 | 改**按名字**补齐，显式查 `name='招牌热销'` 的 id |

要点：重新分组**必须确定性**（结果只取决于商品 id 顺序）才能保持幂等；分类本身**从不删除**；使用 ≥2 个分类的店铺（含商户自己整理的）一律不动。

**验收口径是数据而非 UI**：

```sql
SELECT COUNT(*) FROM (
  SELECT s.id FROM goods g JOIN stores s ON s.id = g.store_id
  GROUP BY s.id HAVING COUNT(DISTINCT g.merchant_category_id) < 2
) t;   -- 必须为 0
```

两份库都查了：本机 3306 → `bad_stores 0`（41 店）、`min_cats = max_cats = 4`；compose 容器 3307 → `bad_stores 0`（40 店）、每家恰好 4 个非空分类；二次启动无重排日志（幂等）。

> **两份库数据集不同，不能只验一份就下结论**：容器是「40 家店 × 30 件商品」的均匀重新生成数据（6 件招牌）；本机 3306 是「41 家店、商品数 6~30 不等」的累积数据——**「整店全招牌」这种形态只在本机出现**。而模拟器里的 App 连的是**容器**（`10.0.2.2:9000`），所以这条路径**只能做数据库口径验证，设备实测覆盖不到**。测试用例的注释与提交说明都如实写明了这一点，没有拿 store 34 冒充「全招牌店」。

## 八、经验教训（已同步 `AGENTS.md` 第 8 节）

1. **Jackson 序列化 record 只认「组件」**：给前端用的字段必须写在构造参数里，派生值在 DAO/构造处算好传进来；在 record 里加个方法**不会**出现在 JSON 里。
2. **容器的 `getText()` 返回空串**：`ON.id()` 打在 `Row`/`Column` 上能查到节点但没有文本；断言卡片内容要查内部文本节点。
3. **横向 `Scroll` 里的 `Text` 用文案定位，不要用 id**：`.id('goods-cat-x')` 在设备上 `ON.id()` 查不到，`ON.text('招牌热销')` 稳定可用。
4. **分类芯片空转的根因在种子数据**，且修法有四个坑（判定条件、按店铺轮转、不能只补 0、默认分类按名字补齐），验收口径是 SQL 而不是 UI。
5. **两份数据库数据集不同**，`bad_stores` 必须两份都查；「整店全招牌」形态只在其中一份出现。
6. `.docx` 就地填写用 `python-docx` 深拷贝段落 XML 后 `addnext` 插入，可保留原字体与版式；**合并单元格会让 `row.cells` 重复产出同一段落**，遍历前必须按 `id(cell._tc)` / `id(p._p)` 去重，否则「7 个占位符」会被数成 42 个。
7. 本机控制台是 ANSI 代码页，**Python/`Get-Content` 直接打印中文会乱码**：校验脚本一律把结果 `WriteAllText` 成 UTF-8 文件，再用文件工具读。
