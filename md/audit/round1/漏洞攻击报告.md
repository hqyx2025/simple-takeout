## 0. 一页结论

| 级别 | 数量 | 代表问题 |
| --- | --- | --- |
| **Critical** | **1** | 线上任意登录用户可无限“铸币”，可兑换真实订单 |
| **High** | 4 | 骑手/商户自助注册；JWT 密钥是模板短语；MySQL/Redis 暴露面；全站共享限流桶可被锁死 |

```

### V-01 ｜【Critical】develop 档对外 = 任意登录用户无限铸币，可兑换真实订单

- **证据**（代码已确认 + 线上已验证）
  - AuthController.java:201-205 —— POST /api/auth/recharge 只要登录态；**无支付密码、无频率限制、不写支付流水**
  - AuthService.java:326-338 —— 仅判 demoRechargeEnabled，金额 0.01~10000，随后 userDao.addBalance()，**可无限次调用**
  - application-develop.yml:4-6 develop 默认 recharge-enabled: true；.env:22 亦为 true
  - 唯一硬闸 ProductionHuaweiGuard.java:18-21 带 @Profile("production") → **只有 production 安全**
  - AuthService.java:84-86 注册送 20 元体验金，可批量叠加
- **PoC（线上实测）**
  ```
  POST /api/auth/login {"phone":"13800138000","password":"123456","loginType":"USER"} → 200
  GET  /api/auth/me → balance 20.00
  POST /api/auth/recharge {"amount":0.01} → 200 {"balance":20.01}

- **影响**：余额可下真实订单 → 正常履约 → 商户结算/骑手收入由平台垫付。叠加 V-02 的自助商户注册，攻击者可把“免费订单”结算进自己控制的店，形成**余额→订单→商户余额**闭环。
- **修复**：演示能力按 profile **反向装配**（production 下 bean 不存在）；充值写 payment_records(channel=DEMO) + 日上限 + 接入限流；DemoModeWarning 升级为启动 fail-fast；公网站改 production + signup-balance=0。

### V-02 ｜【High】商户/骑手自助注册零审核，线上入口已放行

- **证据**（线上已验证 + 代码已确认）
  - AuthController.java:207 RegisterRequest(... int role)；AuthService.java:76-85 只拒 role=2，**明确放行 role=1/3**
  - RiderService.java:36-47 骑手首次进端**自动建档**（status=1）；:72-85 接单位置任意设置
  - OrderService.java:908-958 抢单池按“半径 + 已出餐”过滤；:962-984 取餐/送达只校验 rider_id=自己
  - OrderDao.java:385-389 池查询 status=2 AND ready_time<>'' AND rider_id=0；OrderService.java:1006-1009 视图含完整 AddressInfo(name, phone, detail)
- **线上探针（未建号、无写入）**
  ```
  register {role:3} → 400 "验证码不正确或已过期"   ← 已过角色校验
  register {role:1} → 400 "验证码不正确或已过期"
  register {role:2} → 400 "角色不合法"              ← 管理员被拒
  ```
  注册验证码发给**攻击者自己填的邮箱**，门槛只是一封邮件。
- **影响**：任何互联网用户可成为骑手 → 读取真实订单的**姓名、手机号、详细地址** → 抢单并直接标记送达 → 24h 自动结算给商户；真实用户钱货两空。
- **边界**：骑手 total_income 只是 riders 表计数器（RiderDao.java:73-76），**不进余额、不可提现**。损失是履约欺诈 + PII 泄露 + 提前结算。
- **修复**：注册只收 role=0；商户/骑手走申请+审批（审批前 status=0）；riders.status 默认 0；抢单池只下发脱敏信息（手机号抢单成功后给）。

### V-03 ｜【High】JWT 密钥是模板短语且三处复用（线上已换，但代码不设防）

- **证据**（代码已确认 + 线上已验证）
  - application.yml:61-64 takeout.jwt.secret 取自环境变量，expire-hours: 72
  - JwtUtil.java:28-32 直接用原始字节做 HMAC key（49 字节 → jjwt 选 HS384）；:62-68 只 verifyWith(key)，无 issuer/audience/算法白名单
  - 本地 .env 实测：**49 字符、纯 [a-z-]、7 段可读英文词 + 年份**，非随机；同一密钥还被复用为验证码 HMAC 盐（SmsVerificationService.java:44）与 AI Key 派生盐（AssistantConfigService.java:41-42）
  - 无启动期熵断言：SmsVerificationService.java:61 只校验长度 >= 32，49 字符弱口令可过
- **线上验证（关键修正）**：用本地 .env 的 49 字符密钥，以 HS384/HS256/HS512 伪造 sub=1、role=0、pwdAt 为空的 token 打 /api/auth/me → **三次全部 401「登录凭证无效或已过期」**（签名失败，而非改密校验失败）。结论：**线上密钥与仓库 .env 不同，未被这条链打穿**。若线上沿用模板短语，则为 Critical。
- **残余风险**：代码不阻止弱密钥；密钥三处复用（JWT/HMAC/AI 盐）导致一处泄露全崩；.env 是部署模板的复制源，运维照抄即中招。
- **修复**：轮换为 32 字节随机；启动断言“长度≥32 且字符集熵达标，否则拒绝启动”；parseToken 加 requireIssuer + 锁定算法；用途拆分三把密钥；.env.example 不留可复用占位。

### V-04 ｜【High】Redis 无口令 + MySQL root 明文，compose 却把两者发布到 0.0.0.0

- **证据**（代码/配置已确认；线上不可达）

  - docker-compose.yml:27-29 MySQL 3310:3306；.env:20 应用以 **root** 连库
  - application.yml:12 JDBC useSSL=false&allowPublicKeyRetrieval=true
  - LoginRateLimiter.java:137-150 限流桶/黑名单全落 Redis
- **验证**：docker compose config 解析 = 0.0.0.0:3310 / 0.0.0.0:6387 / 0.0.0.0:8087；线上两端口实测**不可达**（云安全组挡着）。
- **攻击链**（一旦放行）：无口令连 6387 → DEL takeout:rl:login:*:blocked 解除所有封禁 → 篡改缓存/清验证码 → CONFIG SET dir + SAVE 落地文件。MySQL 侧：低熵 root 口令 + 明文传输 → 改余额/改 role。

### V-05 ｜【High】XFF 被覆写 → 全站共用一个限流桶，10 次错登锁死所有用户

- **证据**（静态推断，配置链确定）
  - gateway/application.yml:33 trusted-proxies: ".*"、:46 for-append: false（覆写而非追加）
  - server/docker/nginx-domain.conf:33 nginx 设 X-Forwarded-For $remote_addr，:43 反代 127.0.0.1:9087
  - LoginRateLimiter.java:121-135 取 XFF **首段**；:36 login: 10/60s → 封 600s
- **机理（与“伪造绕过”方向相反）**：公网 → nginx → docker → gateway 时，gateway 看到的对端恒为同一地址 → 覆写后**所有用户 clientIp() 相同** → 攻击者 10 次错登写入共享封禁键 → **全体 429 持续 10 分钟**，每 10 分钟重放即可长期压制登录/注册/找回。
- **验证**：线上 3 次错登返回 400 而非 429（阈值未到，说明限流在跑）。**故意未打满 10 次，避免真的锁死你的演示站。**
- **修复**：trusted-proxies 收窄为 nginx/docker 网段；取 IP 用“最右侧非可信跳”；限流键改 ip+账号双维度。

### V-10 ｜【Medium】上传接口无频率/配额

- **证据**：UploadController.java:25-28 仅 store(file)；FileStorageService.java:56-78 无用户配额；LoginRateLimiter.java:34-48 无 upload 策略。

### V-11 ｜【Medium】CORS 全开 + JWT 存 localStorage + 无安全响应头

- **证据**：WebConfig.java:62-69 allowedOriginPatterns("*")；网关 app.js:19 token 存 localStorage；无 CSP / nosniff / frame-options。
- **现状**：线上预检 403（网关无 globalcors，Spring Cloud Gateway 默认拒），属“意外安全”；Bearer 需脚本自加，实际不可直接利用。
- **风险**：配置意图与线上行为相反——一旦绕过网关直连应用，通配 CORS 立即生效；任何 XSS 都可直接读 token。
- **修复**：显式来源白名单；token 改 httpOnly cookie 或 BFF；补安全头；把 preflight 403 写进部署文档。

### V-12 ｜【Medium】限流“故障即放行”且只有 IP 维度

- **证据**：LoginRateLimiter.java:63-74,77-101 Redis 异常一律放行；键只有 IP。
- **影响**：Redis 抖动时暴力破解零阻力；与 V-05 叠加时两个方向都不安全（要么绕过，要么全站锁死）。

### V-13 ｜【Medium】注册/取码可枚举账号

- **修复**：查询串脱敏（手机号/地址参数）、IP 截断、按保留期清理。

### V-19 ｜【Low】/api/auth/refresh、/api/auth/logout 免鉴权且无限流

- **证据**：WebConfig.java:48-49 放行；AuthController.java:129-155 无限流；RefreshTokenService.java:58-98 每请求 FOR UPDATE + 全表过期清理（TokenBlacklistDao.java:30,45）。
- **影响**：并发打 refresh 制造锁等待与清理风暴（资源放大）；token 为 256bit 随机，数据面无法爆破。
- **修复**：两端点挂限流；全表清理移出热路径。

### V-20 ｜【Low】Swagger 路径写在鉴权放行名单里（误导性配置）

- **证据**：WebConfig.java:56-58 放行 /v3/api-docs/** 等，但拦截器只挂 /api/**——这三条永远不会被拦截，写进放行名单只会误导后人；OpenApiConfig.java:18-27 定义了 bearerAuth 但不产生鉴权。
- **现状**：默认/生产关闭，线上实测 404。
- **修复**：从放行名单删除；需要时独立 profile + Basic 认证。

### B. 与队友结论的差异（我做的二次验证）

1. **AZ-01 由 Critical 降为 High**：队友用内存桩 UserDao 证明“伪造 token 能过 AuthInterceptor”，方向正确；但我用**真实线上**验证，本地密钥签的 HS384/256/512 三种 token **全部 401**，说明线上密钥已换。真实风险是“代码不防弱密钥 + 密钥三处复用 + 模板可复制”，不是当前可接管。
2. **AZ-10 由 Critical 降为 Medium**：管理员 13100131000/123456 线上实测 **400**（已改密）。保留 Medium 是因为默认值仍写死在 application.yml:58，且主 compose 不传该变量。
3. **AZ-04（演示充值）由 Medium 升为 Critical**：队友因“production 有守卫”降级，但**线上就是 develop 且已实测成功**，暴露面优先于代码意图。
4. **新增线上验证矩阵**：/api/admin/users 401、文档 404、CORS 403、端口不可达——这些是纯静态审计无法给出的“否证”，避免报告虚高。
