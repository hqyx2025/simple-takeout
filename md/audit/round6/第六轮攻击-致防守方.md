## 1. 本轮发现

### RT-29 ｜【Medium】验密许可现在覆盖 4 次 Redis 往返：Redis 一慢，登录容量从 34 掉到 6

**证据（代码）**：`AuthController.java:132-143` 的回调在**许可内**执行，它含 4 次 Redis 调用：

1. `isBlocked("login", ip)` → `redis.hasKey`
2. `recordAttempt("login-total", ip)` → `redis.execute(RECORD)`
3. `isBlocked("login-account-fail", resolved)` → `redis.hasKey`
4. `recordAttempt("login-account-total", resolved)` → `redis.execute(RECORD)`

而 Redis 客户端超时是 `spring.data.redis.timeout: 500ms`、`connect-timeout: 500ms`（`application.yml:42-43`）。所以**每次登录的许可持有时间 = 4 × Redis 延迟 + 94ms PBKDF2**。

**我怎么测的**（真实 `LoginRateLimiter` + 真实 `AuthService` + 真实 Semaphore，把 `StringRedisTemplate` 换成"每次调用耗时 500ms"的替身，即恰好等于你们配置的超时）：

    # 探针：md/audit/cache/round6-probe/Round6RedisCouplingProbeTest.java
    # mvn -f server/pom.xml -pl takeout-app -am test "-Dtest=Round6RedisCouplingProbeTest"
    [P7] fast-redis   single-login wall time = 95 ms
    [P7] fast-redis   redis calls per login (fast) = 4
    [P7] fast-redis   concurrent=30 -> 503=0  ok=0 elapsed=1589ms

    [P7] redis-500ms  single-login wall time = 2152 ms
    [P7] redis-500ms  redis calls per login (degraded) = 4
    [P7] redis-500ms  concurrent=30 -> 503=24 ok=0 elapsed=6466ms

**结论**：

| 指标 | Redis 正常 | Redis 退化（500ms/次） |
| --- | --- | --- |
| 单次登录许可持有时间 | 95 ms | **2152 ms**（4×500 + 94） |
| 每许可吞吐（2 许可） | 约 21 次/秒 | **约 0.95 次/秒** |
| 30 个并发登录的结果 | 全部受理 | **24 个 503** |
| 首次出现 503 的并发数 | 35（你测的） | **约 6** |

**为什么这是你这次修复引入的**：第五轮之前，这 4 次 Redis 调用在许可**之外**，所以 Redis 变慢只会让每个请求整体变慢，**许可仍只被 PBKDF2 占住 94ms**，容量维持 34。你把预算挪进回调（RT-27，方向正确）之后，Redis 的延迟被直接算进了许可持有时间。

**这和你自己的设计承诺冲突**。`README.md:65` 写着：

> **Redis 故障自动降级回源数据库，不影响主流程**

缓存读写确实降级了，但**登录不再"不受影响"**：Redis 一慢，登录容量掉 22 倍，队列（32 个名额）在几秒内被占满，合法用户拿到 503。而登录是所有流程的入口。

**顺带一个攻击放大器**：饱和登录所需的外部 IP 数，在 Redis 正常时约 40 个，Redis 退化时约 16 个——因为每个攻击请求现在占用名额 2.1 秒而不是 0.094 秒。我不夸大这个数字，但它说明"Redis 抖动"和"登录 DoS"这两个原本独立的故障会互相放大。

**我要你做的选择**：

- **A. 改**：让许可只覆盖 CPU 计算，不覆盖限流 I/O。可选：
  1. 回调里的 Redis 检查加**健康短路**：检测到 Redis 退化（连续超时）时只用本地窗口（`LoginRateLimiter` 已经支持本地窗口），许可持有时间回到约 94ms；
  2. 把 4 次往返**合并**（例如 `isBlocked` + `recordAttempt` 用一次 Lua 同时完成检查与计数），把往返数降到 1-2 次；
  3. 预算检查放到许可之前，但按 RT-27 的要求在 503 时**退还**已占用的额度（你上一轮否决过"退款"，那就选 1 或 2）。
- **B. 接受**：在 README 的限流章节写明"Redis 退化时登录容量会降到约 6 并发、单次约 2.1 秒"，并**修正第 65 行"不影响主流程"的说法**，改成"缓存读写降级；登录容量受 Redis 延迟影响"。

无论选哪个，请回答 Q10/Q11。

### RT-30 ｜【Low】许可持有时间包含 I/O 后，README 的容量换算表失效

**证据**：`README.md:275` 给的公式是 `等待 >= (ceil(N/P) - 1) × T`，其中 T 被描述为"该副本在 P 个验密同时执行时的**单批耗时（包括查询与限流）**"。

问题在于：**T 现在取决于 Redis 延迟，而运维无法从公式里看出这一点**。你表里写"30 人：P=2，等待 5000ms，需 T 小于约 300ms"。但 Redis 退化时 T ≈ 2150ms，此时 `(ceil(30/2)-1) × 2150 = 30 秒`，远超 5000ms 上限 → 表格里"30 人"那一行在 Redis 退化时**根本不成立**。

**我要你做的选择**：A. 在表格里加一列或加一行注释，写明"T 包含 4 次 Redis 往返；Redis 延迟上升时 T 会成比例上升，需重新实测"；B. 说明为什么这不重要。
