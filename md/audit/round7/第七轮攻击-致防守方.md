## 1. 本轮发现

### RT-31 ｜【Low，多副本时升 Medium】一次瞬时 Redis 错误会让"封禁检查"在整个冷却期内对全站失效

**证据（代码）**：`LoginRateLimiter.java:115-130`

    boolean blocked = Boolean.TRUE.equals(loginRedis(action, () -> redis.hasKey(blockKey(action, ip))));
    if (blocked) rememberRedisBlock(action, ip);
    return blocked;

`loginRedis` 在冷却期返回 `null`（`:261`），`Boolean.TRUE.equals(null)` 为 `false`，于是 `isBlocked` 返回"未封禁"。而 `loginRedis` 的 `finally` 对**任何异常**都进入冷却（`:274` 的 `!completed ||`），与耗时无关。

**我怎么测的**（真实 `LoginRateLimiter`，Redis 替身可控地"抛异常"或"报告封禁"）：

    # 探针：md/audit/cache/round7-probe/Round7ShortCircuitProbeTest.java
    [P8] control healthy Redis reports blocked -> isBlocked=true
    [P8] during-error call -> isBlocked=false (fail-open; cooldown armed)
    [P8] after-recovery call -> isBlocked=false redis-calls-made=0 (0 = block check skipped)
    [P8] recordAttempt during cooldown redis-calls=0
    [P8] VERDICT active-block-hidden=true

**读法**：Redis 健康且明确报告"该 IP 已封禁"时，限流器正确拒绝；只要先发生**一次**异常（例如连接池 `max-wait: 200ms` 超时、或 Redis 抖动），这次请求 fail-open 放行，**并且此后 5 秒内 `isBlocked` 对任何身份都不再查 Redis**（我实测第二次调用 `redis-calls-made=0`）。

**三个我关心但文档没写清的点**：

1. **第一次出错的那次请求本身就是 fail-open 的**——它在触发冷却的同时被放行；
2. **窗口是全局的**，不是按身份：一次错误让**所有 IP、所有账号**的封禁检查失效 5 秒；
3. **冷却会自我续期**：Redis 持续慢/故障时，每 5 秒那次单探测仍然慢 → 再冷却 5 秒 → **共享预算在整个故障期间都不被查询**。所以实际窗口不是"5 秒"，而是"故障持续多久就是多久"。

**影响（为什么我标 Low 而不是 Medium）**：你文档写了"尚未在本副本观察到的其他副本计数和封禁无法读取；多副本的全局预算退化为每进程保护"，所以跨副本不可见是**已声明**的。而且体验站是 **1 个 app 副本**（你自己在 Q4 表里写的），单副本下本地镜像与 Redis 同步，攻击者拿不到额外预算——**所以在当前部署上这条没有实际可利用性**。

**它变成 Medium 的条件**：主 Compose 是 **2 副本**（`docker-compose.yml` 的 `replicas: 2`）。2 副本下，Redis 故障期间共享预算退化为每进程，攻击者的有效失败预算从 10 变成 20；若将来扩到 N 副本就是 N 倍。**这不是我要你现在改，是要你把这个倍数写进文档**——现在文档只说"退化为每进程保护"，没说"因此攻击者的尝试次数变成 N 倍"。

**我要你做的选择**：

- **A. 改**：把冷却做成**按身份**而不是全局（例如冷却只作用于"本进程尚未观察过该身份"的查询），或者冷却期内 `isBlocked` 对"未知"返回**保守拒绝**而不是放行；
- **B. 接受并在文档里补一句**："Redis 故障期间，跨副本共享预算退化为每进程，攻击者的有效失败/总量预算变为原来的 N 倍（N=app 副本数）"。

### RT-32 ｜【Low，多副本或重启后生效】"最多保留 600 秒"实际可达约 2 倍：本地镜像在观察到封禁时重新起算完整时长

**证据（代码）**：`LoginRateLimiter.java:239-253`

    if (window.blockedUntil <= now) {
        window.blockedUntil = now + policyFor(action).blockSeconds() * 1000L;
        window.expiresAt = window.blockedUntil;
    }

`now` 是**观察到封禁的时刻**，不是 Redis 里那次封禁的**设置时刻**。所以本地镜像总是从"观察时刻"起算完整时长。

**我怎么测的**（把策略缩短到 block=2s 以便观察；两个限流器实例共享同一个 Redis 替身）：

    [P8] A observes Redis block at t=2ms    -> true
    [P8] B observes Redis block at t=1404ms -> true
    [P8] at t=2105ms Redis-blocked=false ; A.isBlocked=false B.isBlocked=true
    [P8] VERDICT block-outlives-redis=true policy-block=2000ms still-blocked-at=2105ms

**读法**：Redis 的封禁在 t=2s 到期，A（在 t=0 观察到）也随之解封；但 B（在 t=1.4s 才观察到）要到 t=3.4s 才解封。**B 比 Redis 多封了 1.4 秒，且观察越晚、超出越多，上限是一个完整政策时长。**

放大到真实参数：`login@@ / `login-account-fail@@ 的 `blockSeconds = 600`，所以**受害者在某个副本上被封的实际时长可达约 1200 秒**，而 `README.md:275` 写的是"最多保留 600 秒"。

**两个可达路径**：

1. **多副本**：攻击者可以**故意选择时机**——先在副本 A 触发封禁（T=0），等到 T+599s 再向副本 B 发一次携带受害者手机号的登录请求，让 B 起算新的 600 秒。受害者此后在 B 上要到 T+1199s 才能登录，而 Redis 早已解封。
2. **任何一次 app 重启/部署**：重启后本地表为空，下一个请求重新观察到 Redis 封禁 → 本地重新起算完整 600 秒。**这条在单副本上也成立**，而且运维发版就是重启 app（`docker-compose.yml` 的 app 服务）。

**和 RT-16 的关系**：RT-16 的"10 次失败锁 600 秒"你已接受。这条让它变成"攻击者可控时机下最多锁约 1200 秒"，属于同一风险的**时长放大**，不是新类型。我标 Low，但文档里的"最多 600 秒"需要改。

**我要你做的选择**：

- **A. 改**：让 `rememberRedisBlock` 记住的是"观察到封禁的时刻 + 一个不超过剩余 TTL 的时长"——最小实现是给本地镜像一个**不超过 Redis 政策时长的上限**并注明是保守值；或者干脆在 `isBlocked` 命中本地镜像时不重新起算（当前逻辑已做到），但**首次观察**仍会重起算，这一点需要显式承认；
- **B. 接受并改文档**：把"最多保留 600 秒"改成"本地镜像自观察时刻起算完整政策时长；多副本或重启后，受害者被封的实际总时长可达政策时长的约 2 倍"。
