## 二、仍未修复、已明确接受的四条

防守方对以下四条选择了"接受风险"，且都给出了量化边界（这是我认可的处理方式——**不装作已解决**）：

| 编号 | 内容 | 量化边界 |
| --- | --- | --- |
| RT-16 | 跨 IP 的账号硬封禁：10 次错密触发 600 秒封禁，攻击者可反复触发 | 单次固定封禁 600 秒，拒绝请求不续同一 TTL；持续新增攻击无总时长上界；带外恢复 = root SSH 脚本清键 + 重启全部 app（隔离环境已演练）；叠加 RT-32 时可能延长 |
| RT-22 | 人工恢复重启全部 app，会清空**所有**动作的本地限流窗口并中断在途请求 | 每次恢复重置全部本地窗口；在途请求丢失；健康等待 90 秒不是 SLA |
| RT-31 | 登录 Redis 慢调用/异常触发本进程全部登录身份冷却，冷却期不读取共享封禁；已知本地封禁仍拒绝 | 每轮 5 秒，故障可续期；多副本降级为 N 份本地配额。当前 demo N=1；主 Compose 默认 N=2 时单 IP 失败 10→20、总量 60→120、账号总量 30→60 |
| RT-32 | 本地封禁镜像从"观察时刻"起算完整时长 | 原始封禁总时长可接近 2B：失败桶约 1200 秒、总量桶约 120 秒 |

## 三、攻击方自己的更正（保留在案）

为了这十轮的可信度，我自己犯的错一并记录：

1. **RT-21 的"1250 个 IP"是错的**（只算了失败桶，漏了 `login-total`），正确约 22 个；第五轮自我更正并撤回基于它的"成本降低 50 倍"论据。
2. **"HMAC 低成本不可区分"方案被防守方驳回且驳回成立**——真实账号仍须验原哈希，两条路径无法都降到 1ms；已撤回。
3. **第二轮的端到端 PoC 数字（40/0、10/30）不可信**——当时未加 `-am`，`takeout-common` 取自旧 jar。该文件已降级为"机理旁证"，第二轮结论改压在我亲自实测的 SQL 排序规则等价类与限流器隔离探针上。
