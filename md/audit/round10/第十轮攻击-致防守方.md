## 1. 本轮发现

### RT-38 ｜【Medium】64 KiB 单值上限低于你们自己发的那份数据集：129 家店起，首页目录缓存永久失效，而且没有配置项、没有可见告警

**证据（代码）**：`HotDataCacheService.java:51、269-280`

    private static final int MAX_ENTRY_BYTES = 64 * 1024;      // ← 硬编码，不是配置项

    String encoded = objectMapper.writeValueAsString(new CacheEntry(businessKey, value));
    if (encoded.getBytes(StandardCharsets.UTF_8).length > MAX_ENTRY_BYTES) {
        log.debug("[缓存写入] 载荷超过 64 KiB，本次只返回查询结果 key={}", key);   // ← debug，生产不可见
        return;
    }

**为什么这条现在才致命**：这一轮你把 `ALL_STORES = "stores:source:all"` 改成了**整份原始店铺目录缓存成一条**（`Keys.java:382`）。也就是说，**首页店铺列表的缓存命中与否，取决于"整份目录的 JSON 是否小于 64 KiB"这一个布尔条件**。而在上一轮的设计里，这个上限分散在每条按坐标的视图上；现在它集中在了最热的那一条上。

**我怎么测的**（真实 `Store` 记录 + 与 `safeSet` 同一个 Jackson，以及内存 Redis 替身跑真实 `get()`）：

    # 探针：md/audit/cache/round10-probe/Round10CatalogSizeProbeTest.java
    [P11] stores=20  raw-catalog-json=10134 bytes  over-cap(65536)=false
    [P11] stores=100 raw-catalog-json=50777 bytes  over-cap(65536)=false
    [P11] stores=160 raw-catalog-json=81437 bytes  over-cap(65536)=true
    [P11] stores=200 raw-catalog-json=101877 bytes over-cap(65536)=true
    [P11] stores=500 raw-catalog-json=255177 bytes over-cap(65536)=true
    [P11] first store count that exceeds the 64 KiB entry cap = 129

    [P11] 500-store catalog: value-keys-written=0 source-loads=1
    [P11] second identical request: source-loads=2 (2 = cache never filled, every request hits the DB)
    [P11] VERDICT oversize-catalog-silently-uncached=true

**临界点是 129 家店。** 500 家店时目录 255,177 字节，是上限的 3.9 倍，**缓存键一个都没写进去**；两次相同请求都回源，说明它**永远不会被填上**。

**而 500 家店正是这个仓库自带的数据集。** `scripts/seed-demo-catalog.py` 第 55、96 行：

    assert sum(a['count'] for a in anchors)==500 and len(anchors)==14
    expected={'users':14,'categories':56,'stores':500,'goods':6000,...}

**三个叠加的问题**：

1. **阈值被自己的数据集越过**：129 < 500。你在回复里写了"目录编码超过 64 KiB 时仍跳过缓存，不能把这些数字外推为大目录"——这个边界声明是对的，但你**没有把 500 这个数字代进去**，所以没发现它已经被越过；
2. **上限是硬编码的**（`private static final int MAX_ENTRY_BYTES`），运维**没有任何旋钮**可以调高。要改必须改代码重新构建；
3. **跳过是静默的**（`log.debug`，生产默认 INFO 看不到）。运维看到的现象只是"数据库负载莫名偏高"，**没有任何日志告诉他缓存没在写**。

**影响**：数据集一旦超过 129 家店，`ALL_STORES` 永久未命中 → 每个首页请求都执行 `storeDao.listAll()` 拉全部 500 家店，再对 500 家店逐个算距离、转视图。`RECOMMENDED_STORES` / `SPECIAL_GOODS` / `RANK_GOODS` / `SECKILLS` 同理（它们也是整份候选集缓存）。这与我在第八轮报的"缓存层被打穿"效果相同，但**这次不需要攻击者，是正常流量自己触发的**。

**我要你做的选择**：

- **A. 改**（三条独立，建议至少做前两条）：
  1. **把上限做成配置项**（例如 `TAKEOUT_CACHE_MAX_ENTRY_BYTES`，默认调高到 1 MiB 级别），并在 README 环境变量表登记；
  2. **超限时升到 `warn` 并带上 key 与字节数**（现在是 debug），让运维能看见；
  3. **对目录类缓存分片**（例如按 `categoryId` 或按 id 区间拆成多条），使单条不随店铺总数线性增长——这才是结构性解法。
- **B. 接受**：写明"店铺数超过 129 时首页目录缓存失效"，并在 README 里给出这个数字与当前数据集（500）的对照。

无论选哪个，请回答 Q21/Q22。
