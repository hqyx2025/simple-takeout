## 1. 本轮发现

### RT-34 ｜【Medium】浏览类接口的缓存键空间不受限：约 13.5 万次请求即可把 1 GiB 写进 Redis，而 Redis 没有 maxmemory

**先说结论**：任何注册用户（公开注册只开 role=0，但注册是开放的）都可以用**自选的坐标和 `maxDistanceKm`** 让缓存层为每一个请求创建一条**全新的、内容约 8 KB 的**缓存键。这些键带 300–420 秒 TTL，但创建速率远高于过期速率；**Redis 没有配置 `maxmemory`，也没有淘汰策略**，因此内存只增不减，同时 `--appendonly yes` 让 AOF 同步膨胀。

**证据（键空间）**：`HotDataCacheService.java:387-393`

    /** 坐标归一化：约 100m 粒度，避免每个用户坐标都产生独立 key。 */
    private static String coord(Double value) {
        if (value == null || !Double.isFinite(value)) return "n";
        return String.valueOf(Math.round(value * 1000.0) / 1000.0);
    }

注释说这是为了"避免 key 爆炸"。**它没有达到这个目的**——取整只是把连续坐标变成 0.001 步长，没有给键空间设上界。我实测：

    # 探针：md/audit/cache/round8-probe/Round8CacheKeySpaceProbeTest.java
    [P9] 1000 distinct in-range coords -> distinct keys = 1000
    [P9] 1000 out-of-range finite coords -> distinct keys = 1000
    [P9] sample out-of-range key = stores:all:9999.123:-9999.456
    [P9] valid-range key space = 180001 x 360001 = 64800540001 pairs (before categoryId/limit multipliers)

即：**合法范围内就有 6.48×10¹⁰ 个坐标组合**；而**越界坐标同样被接受**（`listStores` 只校验 `categoryId`，见 `StoreService.java:328-334`），所以实际键空间没有上界——`9999.123` 也会成为一条独立的键。

**更糟的是 `maxDistanceKm` 根本没取整。** `Keys.recommendedStores`（`HotDataCacheService.java:366-369`）：

    return "stores:recommended:" + maxDistanceKm + ":" + limit
            + ":" + coord(latitude) + ":" + coord(longitude);

`StoreService.java:352-357` 只校验 `0 < maxDistanceKm <= 20`、`1 <= limit <= 50`，**但键里用的是原始 double**。所以 `maxDistanceKm=2.0000000001` 与 `2.0000000002` 是两条不同的键，而两者都在合法范围内 → 又是约 10¹⁵ 个取值。这条接口的响应还是**最多 50 家店**的推荐列表，单键载荷比普通店铺列表更大。

**证据（载荷与规模）**：用与 `HotDataCacheService.serialize` 同一个 Jackson 序列化一份 20 店的 `StoreView` 列表：

    [P9] serialized 20-store list = 7954 bytes per cache key
    [P9] keys needed to occupy 1 GiB = 134993

**约 13.5 万次请求 → 1 GiB Redis 内存。** 用 `recommendedStores` 且 `limit=50` 时单键更大，所需请求数更少。

**为什么没有东西拦住它**：

| 环节 | 状态 |
| --- | --- |
| 接口鉴权 | 需要登录态，但**注册开放**，一个普通账号足够 |
| 接口限流 | `StoreController` **完全没有接入 `LoginRateLimiter`**（我 grep 过，0 处）；`POLICIES` 里也没有任何浏览类动作 |
| nginx 限流 | 只有 `/takeout/uploads/` 有 `limit_req`（`nginx-domain.conf:4、54-56`），API 没有 |
| 坐标校验 | `Store.java:105-109` 有 `validCoordinates`，**但它只用于算距离**（算不出就显示"未知距离"），**不参与缓存键** |
| Redis 内存上限 | `docker-compose.yml:46-66` 与 `docker-compose.demo.yml:14-22` **都没有 `maxmemory`，也没有 `maxmemory-policy`**；只有 app 有 768M/1024M 限制，Redis 没有 |
| 持久化 | 两处都是 `--appendonly yes` → 每条 SET 追加进 AOF，磁盘同步增长 |

**影响**：Redis 内存耗尽 → 容器 OOM 或被系统杀掉 → **限流封禁状态、验证码、Outbox 流与去重键全部丢失**，同时热点缓存全灭导致数据库被回源打满。这不是数据泄露，是**可用性与资源**问题，所以我定 Medium；但它的门槛（一个普通账号 + 无限制请求）比我前几轮报的东西都低。

**我要你做的选择**：

- **A. 改**（建议，成本很低，三选一或组合）：
  1. **给键空间设硬上界**：把 `coord()` 的粒度从 0.001 放宽到 0.01（约 1 km），并把 `maxDistanceKm` 也取整（例如 `Math.round(x * 10) / 10.0`）——这样键空间降 100–1000 倍且仍然"够用"；
  2. **在 `StoreService` 入口对坐标做与 `validCoordinates` 同款的区间校验**，越界直接 400（把"未知距离"这条路径关掉）；
  3. **给浏览类接口加限流**（例如 `browse` 动作 120 次/分钟/账号），并给 Redis 配 `maxmemory` + `maxmemory-policy allkeys-lru` 作为兜底。
- **B. 接受**：写明"缓存键空间无上界、Redis 无 maxmemory"，并说明为什么当前演示环境可接受。

无论选哪个，请回答 Q16/Q17/Q18。

**证据**：`StoreController.java:216-224`

    List<Store.StoreView> stores = storeService.listStores(categoryId, latitude, longitude);
