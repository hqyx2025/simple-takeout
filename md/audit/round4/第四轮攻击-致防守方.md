## 1. 本轮发现

### RT-21 ｜【Medium】恒定耗时的代价：不存在账号的失败成本从 ~1ms 抬到 ~96ms，且"1 个 IP 能买多少 CPU"由你们的配置旋钮决定

**我怎么测的**（`PasswordUtil.matchesForLogin`，当前源码，预热后取三次最小值）：

    # 探针：md/audit/cache/round4-probe/Round4PaddingProbeTest.java
    # mvn -f server/pom.xml -pl takeout-app -am test "-Dtest=Round4PaddingProbeTest"
    [P4] nonexistent-account = 96 ms
    [P4] modern-600k-hash    = 95 ms
    [P4] legacy-sha256       = 95 ms
    [P4] broken-hash         = 94 ms

**先给你记功**：四条路径的耗时被拉平到 94–96ms，RT-18 的时序侧信道确实关掉了。这一点我复核通过。

**但代价你要认**：`matchesForLogin` 第 65 行对 `rounds < ITERATIONS` 一律 `derive(..., ITERATIONS - rounds)` 补足。于是：

- 修复前：不存在的账号在 `findByPhone` 返回空后立刻出错，单请求成本约 1–5ms；
- 修复后：**不存在的账号也要跑满 600,000 轮 PBKDF2，约 96ms**；
- 也就是说，攻击者**不需要任何账号**，就能让每次请求消耗 100ms 量级的 CPU；而限流侧只有 `login-total`（默认 60 次/60 秒/IP）和 `login@@（失败 10 次/60 秒/IP）拦着。

**算一下你们的余量**（按 docker-compose.yml 的配额 `cpus: '1.0'` × 2 副本 = 2 核）：

| 配置 | 单 IP/分钟可买到的 CPU | 打满 2 核需要的 IP 数 |
| --- | --- | --- |
| 默认 `login-total=60`、`login-failure=10/600s` | 10 次失败 ≈ 0.96s / 10 分钟 ≈ **0.0016 核** | ~1250 个 IP |
| 按 RT-17 的建议调大到 `login-failure=100` | ≈ 9.6s / 10 分钟 ≈ **0.016 核** | ~125 个 IP |
| 若把 `login-total` 也提到 600 | ≈ 57.6s / 分钟 ≈ **0.96 核** | **~2 个 IP** |

第三行不是我要你调成这样，而是说：**你把阈值做成可配置（这是对的），同时把"每请求 CPU 成本"从 1ms 抬到 96ms，这两个改动乘在一起，等于把"CPU 打满需要多少 IP"变成了运维可调的参数。** 你在 Q2 里说"失败 10 次/60 秒/出口 IP 是上一轮顺带定的数"，那接下来一定要调大——调大的那一刻，RT-21 就从"余量薄"变成"可打"。

另外注意：`login-account` 是**按账号**的，攻击者换一个随机手机号就绕开它，只用 `login-total` 的 60 次/分钟。所以上面第二、三行是可达的，不是理论值。

**我要你做的选择**：

- **A. 改**：给登录验密加一个**全局并发上限**（例如 `Semaphore(4)` + 200ms 超时 → 503），或者把不存在账号的补足成本降到"与 600k 轮不可区分但绝对成本低"的方案（例如统一走一次 HMAC 固定成本 ~1ms，再对真实哈希做 PBKDF2——两条路径耗时一致、总成本下降两个数量级）；
- **B. 接受**：写明"登录端点的 CPU 预算 = `login-total` × 96ms/IP/分钟"，并在 README 与 `.env.example` 里把"调大阈值会等比放大 CPU 面"写成运维须知。

我建议 A 的第二种（低绝对成本 + 不可区分），它同时满足 RT-18 和 RT-21。

### RT-22 ｜【Low-Medium】恢复动作的副作用：`docker restart` 会清空**所有** action 的本地窗口，而攻击者 10 个请求就能让你重启

**证据（代码）**：

- `LoginRateLimiter.java:57-59`：`local` 与 `overflow` 是**实例字段**，随 JVM 生命周期；
- `recover-login-account.py:65`：`run(["docker", "restart", "--time", "15", *app_ids])` —— 重启**全部** app 副本；
- 因此每次恢复不仅清掉账号桶的本地镜像，还会把 `upload`、`order`、`payment-password`、`register`、`email-code` 等**所有动作**的本地窗口一起清零。

**后果**：

1. 你说过"Redis 故障时本地窗口继续保护"。**恢复动作本身会把这份兜底清零**：攻击者在 Redis 抖动期先打满 `upload` 的本地窗口，再花 10 个请求触发管理员锁定 → 运维重启 → 本地窗口全空 → 攻击者又拿到一轮完整本地预算。安全上更难，但至少同一类"本地兜底会被外部动作重置"的问题应被记录；
2. 攻击者用 10 个请求就能触发一次**全站 app 重启**（丢弃在途连接），这是比"管理员被锁"更硬的可用性代价，而你把它记作"恢复手段"；
3. 脚本只清 `login-account` 两键，**不碰** `login@@` 与 `login-total`，这一点你已在回复里写明（管理员与攻击者共用出口时仍需换出口），我认可这个边界。

**我要你做的选择**：

- **A. 改**：恢复改为"只删 Redis 两键 + 通过仅监听回环的管理端点清理单副本本地镜像"（不需要重启），并在回复里给出该端点只对 `127.0.0.1` + root token 可用的验证；
- **B. 接受**：在回复里写明"每次恢复会重置全部本地窗口"，并在运维手册里写清"恢复后应确认其他动作的 Redis 预算仍然生效"。

### RT-24 ｜【Low】`includeSubDomains` 是**一年期**承诺，而你同时在这个域名上跑博客

**证据**：`nginx-domain.conf:18、33`：`Strict-Transport-Security "max-age=31536000; includeSubDomains"`。

**问题**：HSTS 一旦下发，浏览器会把 `*.hqyx.website` 全部强制 HTTPS **一年**，且没有"撤销 preload/回滚"的快捷方式（除非用户清缓存）。你自己在回复里也说"没有发起 preload 登记"——那 `includeSubDomains` 的收益（防子域降级）和代价（任何 HTTP-only 子域当场不可用，包括内网、临时服务、旧服务）要一起写。

**我要你做的选择**：A. 给出 `*.hqyx.website` 当前的解析清单与"全部已启用 HTTPS"的核验，或先改成 `max-age=7776000`（90 天）滚动；B. 接受，并把"该域一年内不得新增 HTTP 子域"写进运维约束。
