## Q4 登录端点允许的 CPU 预算

**本轮最终保持 `TAKEOUT_LOGIN_TOTAL_LIMIT=60`、`TAKEOUT_LOGIN_FAILURE_LIMIT=10`**，窗口均为 60 秒，来源失败封禁仍为 600 秒，没有认定校园出口必须调大。另有账号失败 10/60/600、账号总量 30/60/60。

验密许可默认为 `TAKEOUT_LOGIN_VERIFY_MAX_CONCURRENT=2`、`TAKEOUT_LOGIN_VERIFY_WAIT_MILLIS=200`。它跨同一 app 进程内所有来源、账号及角色共享，覆盖查询、密码计算、旧哈希升级和令牌生成，异常也释放许可；不是每个 IP 一把 Semaphore。并发仅允许配置为 1..4，等待为 0..200 ms，超范围拒绝启动。

| 编排 | app 副本 | 每副本 CPU 配额 | 默认同时验密上限 |
| --- | --- | --- | --- |
| 主 Compose | 2 | 1 CPU | 合计 4 |
| 体验站使用的 demo 覆盖 | 1 | 2 CPU | 合计 2 |

这两个形态均由本轮合成 Compose 配置核验，不能把主编排的两副本套给 demo。CPU 配额是整个 app 的上限，不是登录独占或登录只占某个百分比的保证；持续多来源攻击仍可能耗尽配额。源码并发限制解决的是无界同时验密与排队问题，不把它描述成消除了所有 CPU 拒绝服务。

也不采用攻击表中的 IP 数量作为容量保证：失败预算在请求完成后记数，预先通过检查的请求可并发进入；来源总量提供的粗上界是每窗口 60 个请求，按本机约 94 ms 算约 5.6 CPU 秒的突发需求，并非每个请求都会得到验密许可。调高总量/失败阈值、缩短封禁会增加可达 CPU 消耗，这一约束已进入 README 和示例配置。

## Q5 有没有不重启的恢复路径

**没有可以保证清理各副本本地镜像、且无需 app 重启的受支持恢复路径。** 没有新增回环管理 HTTP 端点或信号处理器，也不把仅删 Redis 后偶尔能恢复的状态当作完整流程。

当前恢复仍等于：root 人工执行目标管理员账号预算清理＋全部 app 副本重启＋全部 action 的本地窗口清零。它只重启 app，不重启数据库、Redis、网关或独立博客。**恢复期间在途请求丢失是本轮接受的代价**；可用性损失覆盖全部 app 调用，不能只算管理员登录。

此决定已写入 [README 运维约束](D:/work/jiandanwaimai/README.md:267)。脚本必须由持有既有 SSH 权限的 root 显式使用 `--apply`；攻击者十个请求可以造成账号锁定，**不能直接调用或自动触发重启**。仍需人工决定是否执行恢复。

### RT-22

**选择：接受风险，B。**

- **受影响者**：人工恢复时的全部 app 请求，以及依赖任一 action 本地限流窗口的用户；不只被封管理员。
- **触发条件**：root 确认后执行恢复脚本的 `--apply`。没有自动恢复任务，外部错误登录不是直接重启权限。
