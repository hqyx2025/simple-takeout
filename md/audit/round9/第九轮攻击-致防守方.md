## 1. 本轮发现

### RT-36 ｜【Medium】512 个固定槽位把命中率压到约 19%，而槽位号可以被外部离线算出

**证据（槽位可计算）**：`HotDataCacheService.java:245-247`

    String storageKey(String businessKey) {
        return keyPrefix + "hot:v2:" + Math.floorMod(businessKey.hashCode(), CACHE_SLOTS);
    }

`String.hashCode()` 是公开、确定性的。攻击者**不需要发任何请求**就能算出任意业务键落在哪个槽：

    # 探针：md/audit/cache/round9-probe/Round9CacheSlotProbeTest.java
    [P10] hot key 'categories'        -> slot takeout:hot:v2:28
    [P10] hot key 'banners'           -> slot takeout:hot:v2:199
    [P10] hot key 'announcements'     -> slot takeout:hot:v2:12
    [P10] hot key 'stores:all:n:n'    -> slot takeout:hot:v2:321
    [P10] hot key 'stores:0:n:n'      -> slot takeout:hot:v2:80
    [P10] hot key 'stores:3:n:n'      -> slot takeout:hot:v2:211

**并且一次请求就能把热键挤掉**（我用内存 Redis 替身跑完整 `get()` 路径，统计回源次数）：

    [P10] colliding attacker key found after 318 offline candidates -> stores:all:10.0:20.317
    [P10] hot loads after 2 requests (1 = cache hit) = 1
    [P10] hot loads after poisoning (2 = hot entry was evicted) = 2
    [P10] VERDICT single-request-evicts-hot-cache=true

攻击者离线试 318 个候选就找到了与首页店铺列表同槽的键，然后**一次请求**把它挤掉。

**证据（命中率）**：这一条比"能挤掉"更重要。**你这一轮同时删掉了坐标取整**（你的回复原话："坐标不再以 0.001 粒度合并，保留真实查询精度"）。取整原本的作用是让**相近坐标共用一条缓存**；删掉之后，每个用户自己的 GPS 坐标都是一个独立的逻辑键，而它们只能落进 512 个槽。

你自己在探针里量到的那一行其实已经说明了问题：

    [P9/new] valid-coordinate-samples=1000 logical-identities=1000 actual-value-slot-names=192

**1000 个不同坐标只映射到 192 个槽。** 我这边独立量到的偏斜更明显——要覆盖全部 512 个槽，需要 21319 个候选键（均匀分布下约 3200 个就够，实际差了 6.6 倍）：

    [P10] distinct business keys tried=21319 slots covered=512

也就是说 `stores:*` 这一族的 `hashCode` 分布是偏斜的。**结论：带定位的浏览查询，缓存命中率上限约等于 `槽数 ÷ 活跃坐标数`。** 1000 个活跃坐标 → 上限约 19%；一个城市级用户量（1 万个不同坐标）→ 上限约 5%。**绝大多数浏览请求会直接落到 MySQL**，而 MySQL 与 app 同机、app 只有 1–2 核。

**我要澄清一个我不主张的点**：挤掉缓存**不是放大器**。攻击者一次请求挤掉一条，受害者的下一次请求回源一次，比例约 1:1；受害者回填后缓存又热了。所以我不说"一个请求打垮缓存"。我说的是下面两件事：

1. **结构性命中率塌陷**：删掉坐标取整 + 512 槽，使带定位的浏览查询在真实用户规模下几乎必然未命中。这是**你这次修复引入的、且与攻击者无关**的日常性能回归；
2. **槽位可被外部计算**：这让攻击者可以**定向**选择挤掉哪一条（例如首页店铺列表），而不必盲猜；配合 120 次/分钟/账号的预算，足以持续压制最贵的那几条查询。

**我要你做的选择**：

- **A. 改**（下面三条互相独立，可只做其中一条）：
  1. **把槽数从 512 提上去**（例如 8192 或 16384）——命中率上限按 `槽数 ÷ 活跃键数` 线性改善，而键数上界仍然固定；
  2. **恢复坐标取整**（0.001 或更粗），让相近坐标共用缓存条目——这是命中率的**主因**，比加槽更有效；
  3. **把浏览缓存与安全状态拆开**：浏览缓存单独一个 Redis DB/实例并配 `allkeys-lru`，槽数可以放得很大，而且缓存抖动不会碰到限流/验证码/Outbox。
- **B. 接受**：写明"带定位浏览查询的命中率上限 = 槽数 ÷ 活跃坐标数（默认约 19% @1000 坐标）"，并说明为什么这个代价可接受。**请给出你测过的命中率数字**，而不是只写"碰撞会降低命中率"。

无论选哪个，请回答 Q19/Q20。

### RT-37 ｜【Low】回源锁也是按槽的，无关请求会因为"同槽"而互相等待最多 500 毫秒

**证据**：`HotDataCacheService.java:123-131、172-199`

    token = tryLock(redis, redisKey);          // redisKey = 槽键，不是业务键
    if (token == null) {
        T waited = awaitRebuild(redis, redisKey, key, typeRef);   // 自旋等待
        ...
    }

`awaitRebuild` 每轮 `safeGet` 都要求 `businessKey.equals(entry.key())`；同槽但不同业务键时它永远拿到 `null@@，于是**一路 sleep 到 `rebuild-wait-ms`（默认 500ms）上限**才返回 null 交给调用方回源。

**为什么这是本轮引入的**：第五轮之前锁键是 `业务键 + ":lock"`，"同槽"不存在，只有**真正同一个键**的并发才会触发这段等待——那正是击穿保护想要的。现在锁键也是槽键，**任意两个碰巧同槽的无关查询都会让后者白等最多 500ms**，同时占着一个 Tomcat 工作线程。

**影响**：命中率越低、并发越高，这种白等越频繁；表现为浏览接口偶发 +500ms 延迟与线程占用上升。它是可用性/性能回归，不是安全洞，所以我标 Low。

**我要你做的选择**：A. 让 `awaitRebuild` 在"槽里是别人的键"时立即返回而不是等满 500ms（把"同键并发"与"同槽不同键"区分开）；B. 说明为什么保留。
