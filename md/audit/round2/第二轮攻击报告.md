## 三、发现详情

### RT-01 ｜【High】登录限流可被完全绕过：账号桶键与凭据查询口径不一致，成功登录还会清掉整条 IP 桶

结论：登录接口的实际猜测上限不受限。攻击者只要持有任一自己的账号，就能对任意手机号（含管理员）无限猜密码，并顺手清掉 IP 级封禁。

证据（代码）
- AuthController.java:112-140 —— 桶键由"原始请求串"决定，成功登录重置 IP 桶：

      String accountKey = loginAttemptIdentity(ip, req.phone());   // ip + sha256(phone 原文)
      if (loginRateLimiter.isBlocked("login", ip) || loginRateLimiter.isBlocked("login-account", accountKey)) throw 429;
      loginRateLimiter.recordAttempt("login-account", accountKey);
      try { ...login...; loginRateLimiter.reset("login", ip); loginRateLimiter.reset("login-account", accountKey); }

- AuthController.java:132-140 —— loginAttemptIdentity 只做 SHA-256(phone)，无任何规范化，键空间由攻击者控制。
- LoginRateLimiter.java:109-121 —— reset 同时删除计数键与 :blocked 标记 ⇒ 成功登录可解除已生效的封禁。
- UserDao.java:40-42 —— SELECT * FROM users WHERE phone = ? 走 MySQL 排序规则等值比较，不是严格字节比较。

证据（数据库口径，本机 MySQL 8.4.0 实测）
生产/建表口径：server/database/takeout-latest.sql:37 为 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci；schema.sql:4-22 只写 DEFAULT CHARSET=utf8mb4，MySQL 8 下即取 utf8mb4_0900_ai_ci（临时实例 SHOW CREATE TABLE 回显证实）。

| 探测（users.phone = '13800138000'） | 命中行数 |
| --- | --- |
| phone = '13800138000' | 1 |
| phone = CONCAT('13800138000', U+200B) | 1 |
| phone = CONCAT('13800138000', U+200B ×3) | 1 |
| phone = CONCAT('138', U+200B, '00138000')（中间插入） | 1 |
| phone = '13800138000 '（尾随空格） | 0 |
| phone = '13800138001' | 0 |

"在 0900_ai_ci 下等价于空串"的字符：U+200B / U+00AD / U+200C / U+200D / U+2060 / U+FEFF / U+0000 全部为 1，U+00A0 为 0。即每个手机号至少有 7 类、任意位置、任意长度的隐形变体 → 变体空间是组合级无限。

证据（隔离探针，真实 LoginRateLimiter，不依赖数据库）
- 固定键连打 15 次：reached=10，limited=5 —— 拦截机制本身是好的。
- 40 个不同变体键（每 9 次模拟一次"自己登录成功"清 IP 桶）：reached=40，limited=0 —— 换键即无限。

影响
1. 对任意用户无上限口令猜测 → 账号接管；对 role=2 管理员同样适用（登录接口不区分端，loginType 可省略）。
2. 作废防御报告 V-12；连带使 V-13（枚举）、V-06（弱口令）价值骤增。
3. 附带 DoS：每次失败都执行 PBKDF2-HMAC-SHA256 600,000 轮（PasswordUtil.java:16），匿名请求即可打满 CPU（compose 配额 2 副本 × 1 CPU，docker-compose.yml:78-80）。

线上状态：未实测（会触发共享封禁桶，且本报告边界禁止对线上做口令猜测）。可达性依据：登录路径不依赖任何 profile，线上只读探测显示认证收口正常（4.4）。

为什么防守方没堵住：防御报告 V-12 写"保留 IP 桶和'来源＋账号摘要'桶，自己的成功登录不能清除他人猜测预算"。这句在实现上两半都不成立：(1) "账号摘要"是对攻击者可控字符串做 SHA-256，没有绑定库内 userId，它不是"账号桶"而只是"请求串桶"；(2) reset("login", ip) 清的是整条 IP 桶含 :blocked，正是"他人的猜测预算"。第一轮 V-05 修的是"IP 怎么算"，V-12 修的是"并发下预算怎么原子占用"，"键与查询是否同一口径"这一层从未被检查。防守方回归测试 AuthControllerRateLimitTest 只覆盖固定手机号，因此看不出来。

修复建议
1. 登录限流的账号维度改用库内解析出的 userId（先 findByPhone 再判定），键换成 "u"+userId。
2. 登录入口对 phone 做与注册同款的 ^1\d{10}$ 校验（RT-02 的前提）。
3. 成功登录只清"自己的"预算，不要删 IP 级 block。
4. users.phone 等身份列改 COLLATE utf8mb4_bin（或 utf8mb4_0900_as_cs），从存储层消灭隐形字符等价类。
5. 账号维度加指数退避 / 滑块，同一账号跨 IP 总失败数设上限。

### RT-02 ｜【High 的放大器】登录入口不校验手机号格式，与注册、找回口径不一致

结论：注册与找回都对 phone 做 ^1\d{10}$ 锚定校验，唯独登录完全不校验，直接把任意字符串交给 SQL。这正是 RT-01 能成立的前提。

证据
- AuthService.java:95（注册 registrationEmail）与 :195（recoveryUser）都有 phone.matches("1\\d{10}")。
- AuthController.java:112-121（login）直接把 req.phone() 传给 authService.login，无格式校验；AuthService.login（:115）直接 userDao.findByPhone(phone)。
- AuthService.java:273（改手机号）也做了锚定。

修复建议：三处统一走同一个 normalizePhone()，并在 DAO 层对身份列使用二进制排序规则（双保险）。

### RT-03 ｜【Medium】0 元订单可进入"已支付"：应付被营销活动减到 0 时无券路径不拦

结论：payAmount == 0 只在"用了优惠券"这一支被判非法；由 NEW_USER 立减把应付减到 0 时被放行，随后 deductBalance(userId, 0) 在余额为 0 时也会成功（WHERE balance >= 0），订单直接变已支付。

证据
- OrderService.java:417-426：

      if (payAmount < 0) throw new BizException("优惠金额不能超过订单金额");
      if (appliedCoupon != null && payAmount <= 0) { throw new BizException("优惠券抵扣后应付金额为 0，请更换优惠券"); }

  守卫写了 appliedCoupon != null，因此"无券但被减到 0"不被拒绝。
- OrderService.java:397-401 —— NEW_USER 在 !orderDao.hasAnyOrder(userId) 时 discount += reduceAmount。
- UserDao.java:193-196 —— UPDATE users SET balance = ROUND(balance - ?,2) WHERE id=? AND balance >= ?，amount=0 恒成立。
- OrderService.java:1043-1045 —— 结算额 max(0, payAmount - deliveryFee) → 0。

攻击链：商家配置 NEW_USER 减免 ≥（货款+配送费）→ 新用户下应付 0 的单 → 余额 0 也"支付成功" → status 0→1 → 正常履约。PICKUP 单 deliveryFee=0，只需减免 ≥ 货款。

线上状态：未测（需要真实下单）。判为逻辑口子，不是可远程构造的参数漏洞。

修复建议：把 if (payAmount <= 0) throw 提到分支外；或 0 元单单独走"免支付直接置已支付"并记 payment_records(channel=PROMO, amount=0)，同时明确结算与对账口径。

### RT-05 ｜【Medium】支付密码限流桶与"设置支付密码"共用，未设密码的用户会把自己锁死 600 秒

证据
- OrderController.java:89-97：余额支付前 recordAttempt("payment-password", "u"+userId)。
- AuthController.java:195-202：设置支付密码也用同一个 action="payment-password"、identity="u"+userId。
- LoginRateLimiter.java:38：payment-password 策略 = 5 次/60 秒，超限封 600 秒。
- OrderService.java:524-531：未设密码的用户无论传什么都会被拒（"请先在账号安全中设置支付密码"），但仍消耗预算。

影响：新用户连点 5 次余额支付 → 封 600 秒 → 期间连"设置支付密码"也 429，钱包入口自锁。这是把预算提前到校验之前引入的可用性回归。

修复建议：设置密码与支付校验拆成两个 action；或"未设置支付密码"的拒绝路径不消耗预算。

### RT-11 ｜【Low】重置/设置支付密码不推进 password_changed_at，旧会话不被踢出

证据：AuthService.java:161-170（setPaymentPassword）与 :184-192（resetPaymentPasswordByEmail）都只调 updatePaymentPassword；对比 changePassword（:155-156）会写 password_changed_at。

影响：支付密码变更后，已泄露的会话仍可继续用旧支付密码做余额支付；与"支付密码是第二因子"的定位冲突。

修复建议：支付密码变更时同步推进改密时间或单独的 payment_password_changed_at，并吊销 refresh token。

---

### RT-12 ｜【Low】商户员工无法操作订单：merchantFlow 只认店主

证据：OrderService.java:880-885 只用 store.ownerId() != ownerId；而 StoreService.java:806-812 的 requireOwned 允许员工。两处口径不一致。

影响：被授权为店员的账号能改商品、看统计，却不能接单/出餐（过严，不是越权）。

修复建议：统一改用 requireOwned 语义，并在审计日志里记录实际操作人。

---

### RT-13 ｜【Low｜线上实测】/uploads/<不存在> 返回 500 并匿名写 ERROR 堆栈

证据（线上实测，单次 GET）：

      GET https://hqyx.website/takeout/uploads/redteam-nonexistent-1025.jpg
      HTTP 500  {"code":500,"message":"服务器内部错误，请稍后重试","data":null}

缺失静态资源本应是 404。匿名可无限次触发（该路径不走 /api/** 拦截器，无限流）→ GlobalExceptionHandler.handleOther 每次写一条含堆栈的 ERROR 日志 → 可能冲刷 logback totalSizeCap，淘汰审计归档。

修复建议：/uploads 缺资源返回 404；该路径挂限流。

---

### RT-14 ｜【Low】客户端明文 HTTP 回退 + 高德 JS Key 硬编码

证据：entry/src/main/ets/common/Constants.ets:146 LOCAL_BASE_URL = 'http://10.0.2.2:8087'；HttpClient.ets:34-60 在远程探测失败时静默回退（且把任意 2xx-4xx 视为健康）；Constants.ets:182-184 硬编码 MAP_JS_KEY / MAP_JS_SECURITY_CODE。

影响：网络异常或链路被干扰时，客户端可整体降级到明文 HTTP（Bearer token 裸奔）；高德 Key 随包分发（前端 Key，风险有限但可被配额盗用）。

修复建议：Release 构建禁用本地回退（或编译期裁剪）；探测判据收窄为正业务接口 200；Key 服务端下发或绑定应用签名。

---

### RT-15 ｜【Low】商户统计收入口径无 max(0,·)，与结算入账不一致

证据：OrderDao 的 aggregateMerchantStats 收入列用 pay_amount - delivery_fee，而 settleMerchant 用 max(0, pay_amount - delivery_fee)（OrderService.java:1043-1045）。极端优惠单在商户统计里会出现负收入；V-14 只修了骑手侧。

修复建议：统计口径统一加 GREATEST(0, pay_amount - delivery_fee)。

### 4.1 排序规则等价类（本机临时 MySQL 8.4.0，端口 3311，独立数据目录）

      SHOW CREATE TABLE users;  -- ... DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
      INSERT INTO users(username, phone, password) VALUES('victim','13800138000','x');

      SELECT COUNT(*) FROM users WHERE phone=CONCAT('13800138000', _utf8mb4 0xE2808B);              -- 1
      SELECT COUNT(*) FROM users WHERE phone=CONCAT('13800138000', _utf8mb4 0xE2808BE2808BE2808B);  -- 1
