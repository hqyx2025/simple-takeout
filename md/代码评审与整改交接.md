  1. 赠金额度纳入配置：`takeout.demo.signup-balance`（`application.yml` 默认 20，`application-production.yml` 固定 0）；`AuthService.register` 读配置。

### 2.3 改绑邮箱/手机号无二次验证（会话泄漏可升级为永久抢号）

- **位置**：`AuthService.updateProfile` / `updateProfileInternal`（`AuthService.java:250-278`）只校验格式与唯一性，**不要当前密码、不要验证码**；`PUT /api/auth/me`（`AuthController.java:188-192`）只需登录；找回只依赖 phone+email 匹配（`AuthService.recoveryUser`，`AuthService.java:190-203`）。
- **影响**：拿到任意有效 access token → 改绑为攻击者邮箱 → 邮件找回改密 → 受害者失去找回通道；且改绑成功后旧 token 仍有效（只有改密会 bump `password_changed_at`）。
- **修复要求**：
  1. 修改手机号或邮箱时要求**当前登录密码**（推荐，改动最小）或新邮箱验证码；只改昵称/头像不要求。
  2. 改绑成功后 bump `password_changed_at`（或写一个 `credential_changed_at`），让旧 token 全部失效，需要重新登录。
  3. 前端 `ProfileEditPage.ets` 对应用户输入密码/验证码；后端 `ProfileUpdateRequest` 增加字段，保持旧字段兼容。
- **验收**：不带凭证的 `PUT /api/auth/me` 改手机号/邮箱被拒；改绑后旧 token 请求返回 401；只改昵称仍成功。
- **风险**：涉及登录态；注意别影响管理端员工资料修改等复用路径，逐条确认调用方。

### 2.4 找回密码接口可枚举账号是否存在（已实测复现）

- **位置**：`AuthService.recoveryUser`（`AuthService.java:190-201`）：手机号不存在/禁用返回「手机号或邮箱不匹配」，手机号存在但邮箱不匹配返回「邮箱错误，请输入该手机号绑定的邮箱」；端点为公开路由（`WebConfig.java:50-53` 排除鉴权）；限流仅 IP 维度（`LoginRateLimiter.java:37`，email-code 5 次/60s/IP）。
- **实测**：见 §1.2 表格（两种响应可直接区分）。
- **修复要求**：
  1. 两种失败统一返回同一 code/message（如「手机号或邮箱不匹配」，或统一「验证码请求已受理，请检查邮箱」）；
  2. 发码前若匹配失败，**不要**发送邮件，也不要暴露原因；
  3. 增加**目标手机号/邮箱维度**限流（与 §3.5 合并），避免代理池批量筛选手机号。
- **验收**：两种输入返回完全相同的状态码与 message；正常用户流程不变；单测覆盖。
- **风险**：正常用户输错邮箱后提示变模糊，前端文案需引导「请确认手机号与该账号绑定的邮箱」。

HOUR` 取 200 条；`orders` 表索引没有 `(status, escrow_status, complete_time_dt)` 组合（`schema.sql` orders 段只有 user/store/rider/page/admin_status/pending_timeout/rider_pool）；`OrderAutoConfirmJob` 的锁 TTL 5 分钟（`OrderAutoConfirmJob.java:30-36`）。
- **缺口**：
  1. 一条订单结算异常会中断整批，后面的订单要等下轮；
  2. **存量订单 `complete_time_dt` 为 NULL（历史双写前的行）永远不会被自动结算**，抵消 C1 的收益；
  3. 候选查询无匹配索引，订单量大时全表扫；
  4. 锁 TTL(5min) > 扫描间隔(60s)，实际约 5 分钟一轮（可接受，但要知道）。
- **修复要求**：
  1. 循环内逐单 try/catch + 单条失败日志（订单 ID、异常类型），继续处理后续；
  2. `SchemaMigration` 增加一次性回填：`UPDATE orders SET complete_time_dt = STR_TO_DATE(NULLIF(complete_time,''), '%Y-%m-%d %H:%i:%s') WHERE complete_time_dt IS NULL AND status = 4`（先 `SELECT` 校验格式，分批 LIMIT；无法解析的行记日志不阻塞）；
  3. 新增索引 `idx_orders_auto_confirm (status, escrow_status, complete_time_dt)`；
  4. 可选：锁 TTL 调到 2 分钟或改为扫描间隔内。
- **验收**：真库测试伪造一条会抛异常的订单，后续订单仍被结算；回填后存量已送达订单能被自动结算；`EXPLAIN` 走新索引。
- **风险**：回填涉及存量数据，只动 `status=4`；先备份或先 `SELECT` 计数。

## 11. 结论摘要（可直接进答辩/论文）

> 本项目为 HarmonyOS NEXT（ArkTS）+ Spring Boot 四端外卖系统，含 Redis 热点缓存、事务性 Outbox + Redis Stream 异步事件、平台资金托管（escrow）、多副本部署与月度备份。交易内核已达工程级：库存/秒杀/状态全部条件更新且锁序固定，事件与业务同事务落库，支付回调全字段验签，密码 PBKDF2 加盐，SQL 全程参数化，多副本定时任务与事件投递均有正确的行级认领与幂等设计。
>
> 第二轮评审提出的 P1/P2/P3 整改已落地：资金与身份边界、验证码限流、自动结算回填与容错、默认 mock 可用性、隐私政策、CI 门禁、前端稳定 key/懒挂载/角色守卫/服务拆分、Compose 与脚本基础治理已完成；错误提示统一出口、4.9 细项和设备脚本路径仍是后续尾项。后端测试与前端 HAP 构建通过；Redis 真库用例已进入 CI，但本机 Windows Lettuce selector 受运行环境限制，设备真机回归仍按范围外保留。剩余问题集中在三类：**（1）身份与资金边界**——注册赠金可批量套取（绕过充值门禁）、改绑邮箱无二次验证、找回接口可枚举账号；**（2）验证与可演示性**——验证码单次性用例仍被 CI 跳过、自动结算对存量数据不生效、默认 mock 环境下注册/找回不可用、隐私政策未覆盖邮箱；**（3）结构性质量债**——前端 14 处版本号 key 强制重建、两个巨型文件、错误提示双通道、工程卫生与文档事实漂移。
>
> 按本文件 P0 → P1 → P3 低成本项 → P2 的顺序推进后，资金与身份风险可收敛到可接受范围，关键路径具备机器验证；P2 属质量提升，不改变业务正确性。范围外事项（上架签名、正式 HTTPS、真机回归、订单分页、微服务外拆、演进项）已明确冻结，不再重复讨论。
