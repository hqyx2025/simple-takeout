## 3. 批次 A｜资金与身份（P0，必须先做，约半天）

### A1｜基线问题：`/api/auth/recharge` 让任意登录用户无限造余额

**当前状态**：默认关闭与显式配置开关已实现；本地 HTTP 验收尚未执行。

- **位置**：[`AuthController.java:189`](server/takeout-app/src/main/java/com/example/takeout/controller/AuthController.java:189)（`@PostMapping("/recharge")`，只取 `userId`）；[`AuthService.java:217`](server/takeout-app/src/main/java/com/example/takeout/service/AuthService.java:217)（`recharge` 仅校验 0.01–10000，无角色/环境/凭证校验）
- **现象**：任意登录用户调一次即加余额，上限 1 万/次、不限次数。余额可直接支付订单，`confirmOrder` 又把 `pay_amount` 打给商户 → 平台凭空造钱；与真实支付宝流水混在一起后账实永远不平。
- **前端入口**：[`BalancePage.ets:270`](entry/src/main/ets/pages/BalancePage.ets:270) → [`AppStorageManager.ets:507`](entry/src/main/ets/service/AppStorageManager.ets:507) → [`ApiService.ets:760`](entry/src/main/ets/service/ApiService.ets:760)
- **修复要求**：加配置开关 `takeout.demo.recharge-enabled`，**默认 `false`**；`AuthService.recharge` 首先判断，未开启抛 `BizException(403, "演示充值未开启")`。本地演示需要时显式打开（见 A3 的 profile 方案）。前端不改逻辑（开关关闭时正常显示后端错误）。
- **验收**：默认配置下 `POST /api/auth/recharge` 返回业务失败且余额不变；显式 `TAKEOUT_DEMO_RECHARGE_ENABLED=true` 后本地演示流程（充值 → 余额支付）照旧可用。
- **风险**：若忘记在本地打开，演示时充值按钮报错。需在 README 快速开始里写明。

### A2｜基线问题：escrow 结算与退款竞态可产生 `status=6 + escrow=1`

**当前状态**：结算 SQL 与锁定读已修复；真 MySQL 并发验收尚未执行。

- **位置**：
  - [`OrderDao.java:264`](server/takeout-common/src/main/java/com/example/takeout/dao/OrderDao.java:264) `releaseEscrow`：`UPDATE orders SET escrow_status=1 WHERE id=? AND escrow_status=0` —— **只判 escrow，不判 status**
  - [`OrderDao.java:205`](server/takeout-common/src/main/java/com/example/takeout/dao/OrderDao.java:205) `markRefunding`：`WHERE status=4 AND escrow_status=0`
  - [`OrderService.java:1016`](server/takeout-app/src/main/java/com/example/takeout/service/OrderService.java:1016) `confirmOrder`：用**无锁** `findById` 读状态（经 `requireOrder`，[:1140](server/takeout-app/src/main/java/com/example/takeout/service/OrderService.java:1140)），再调 `releaseEscrow`（[:1025](server/takeout-app/src/main/java/com/example/takeout/service/OrderService.java:1025)）
- **现象（可复现的时序）**：`confirmOrder` 读到 status=4 → 并发退款成功把 status 改为 6（escrow 仍 0）→ `releaseEscrow` 成功 → 结果 `status=6, escrow=1`。此后管理员审批退款，`refundEscrow`（`WHERE escrow_status=0`，[`OrderDao.java:259`](server/takeout-common/src/main/java/com/example/takeout/dao/OrderDao.java:259)）必然失败，退款单永远 PENDING，只能 reject 掩盖；同时商户已入账。
- **修复要求**：
  1. `releaseEscrow` 增加状态条件：`... WHERE id=? AND escrow_status=0 AND status=4`；
  2. `confirmOrder` 改为锁定读：新增 `OrderDao.findByIdForUpdate`（已有类似方法可复用/参照）后再判 status，或直接依赖 `releaseEscrow` 的条件更新并把"读取状态"的校验放在更新之后；
  3. 全仓检查其他调用 `releaseEscrow`/`refundEscrow` 的路径，确认调用前状态与 SQL 条件一致。
- **验收**：新增/扩展现有真库测试，模拟"确认收货"与"申请退款"并发，断言最终状态只能是 (`status=4, escrow=1`) 或 (`status=6, escrow=0`)，二者不可同时；退款审批在两种终态下行为正确。
- **风险**：本地库若已存在 `status=6 + escrow=1` 的脏数据，需人工核对对应退款单后修数据（不要写在启动迁移里自动改钱）。

## 5. 批次 C｜业务闭环与一致性（P1，按需）

### C1｜基线问题：缺自动确认收货 / 自动结算，escrow 可能永久为 0

**当前状态**：自动确认任务和统一结算逻辑已实现；真 MySQL 验收尚未执行。

- **位置**：`releaseEscrow` 全仓仅 [`OrderService.java:1025`](server/takeout-app/src/main/java/com/example/takeout/service/OrderService.java#L1025) 一处调用（用户点"确认收货"）；`server/takeout-app/src/main/java/com/example/takeout/job/` 下只有 `OrderTimeoutJob`、`OutboxRelayJob`。
- **评审起始快照现象**：用户不点确认收货时，商户不会结算，收入/统计长期悬空。
- **修复要求**：新增 `OrderAutoConfirmJob`，复用 `OrderTimeoutJob` 的既有模式（`SchedulerLock` + 条件更新 + 分批 LIMIT）；条件：`status=4 AND escrow_status=0 AND complete_time_dt <= NOW() - INTERVAL ? HOUR`（`complete_time` / `complete_time_dt` 见 `schema.sql` 的 orders 表，注意 DATETIME shadow 双写）；成功后给商户加 `pay_amount` 并写 Outbox 事件，与 `confirmOrder` 逻辑抽公共方法，避免两份结算代码漂移。配置项 `takeout.order.auto-confirm-hours`（默认 24）。
- **验收**：真库测试构造"已送达 N 小时前"的订单，跑 job 后 `escrow_status=1`、商户余额增加、事件已写；重复执行不重复打款（条件更新保证）。
- **依赖**：先做 A2，否则自动任务会踩同一个竞态。

### C2｜支付渠道调用位于数据库事务（常带行锁）内

- **位置**：`OrderService.java:722-746`（事务内 `findByIdForUpdate` 后调 `closePendingPayment`，[`ExternalPaymentService.java:216`](server/takeout-app/src/main/java/com/example/takeout/service/thirdparty/ExternalPaymentService.java:216)）；`ExternalPaymentService.java:94-107` 用 `TransactionTemplate` 包住渠道查询；退款路径 `AdminService.java:452-471` 事务内调退款。
- **影响**：渠道抖动（默认超时秒级）时行锁与连接池被拖住；批量退款会放大。
- **修复要求**：事务内只做本地条件更新 + 写 Outbox 事件，渠道关单/退款由提交后（`TransactionSynchronization.afterCommit`）或消费者执行并重试；退款已有 `refundNo` 幂等兜底（`ExternalPaymentService.java:333`），可复用。
- **验收**：mock 渠道注入延迟/失败，事务内不出现渠道调用（日志顺序可证）；失败可由重试补偿到终态。
- **风险**：中高风险改造，涉及资金语义，需逐路径核对，不要一次性全改。

### C3｜待付款取消依赖支付渠道可用

- **位置**：`OrderService.java:744-746`、`555-570`；`closePendingPayment` 失败抛 503（`ExternalPaymentService.java:234`）。
- **现象**：渠道不可用时，用户取消与 `OrderTimeoutJob` 都失败；订单停留在 status=0，`ensurePayable`（`OrderService.java:538`）又拒绝支付 → 库存/秒杀名额/优惠券长期被占。
- **修复要求**：渠道关单失败不阻塞本地取消（本地状态先到终态 + 记录待关单补偿），或按 C2 同思路异步化。
- **验收**：让渠道 mock 抛错，取消订单仍成功、库存回滚，补偿表/事件记录存在。

### C4｜评价可并发重复

**当前状态**：前端按商品评价，服务层锁定订单行后查重；真实并发验收尚未执行。

- **位置**：`schema.sql` 的 reviews 表无 `(order_id, goods_id)` 唯一键；`OrderService.java:1076-1085` 非锁定读后插入；`ReviewDao.java:69-73`。
- **现象**：同一订单双击/并发提交可写两条评价，污染店铺评分。
- **修复口径**：一个订单内每种商品各一条；已通过锁定订单行串行化该订单的评价提交，再检查 `(order_id, goods_id)` 是否已有评价。
- **验收**：并发提交两次，只成功一条，另一次返回明确业务错误。
- `orders.reviewed` 表示订单内商品均完成评价；前端通过 `selectedGoodsId` 选择待评价商品。

### C5｜已确认口径：配送费归骑手，商户结算扣除配送费

- **评审起始快照位置**：`pay_amount = goods_amount + delivery_fee - discount`；商户结算曾全额使用 `pay_amount`，同时骑手收入计入 `delivery_fee`。
- **评审起始快照现象**：配送费在商户和骑手收入中重复计算。
- **决策与实现**：已确认配送费归骑手；商户实收按 `pay_amount - delivery_fee`，商户收入统计同步使用净结算金额。
- **验收**：同一订单商户收入 + 骑手收入 = 用户实付 + 平台补贴（无重复、无遗漏）。

## 11. 评审结论摘要（可直接用于答辩/论文）

> 本项目为 HarmonyOS NEXT（ArkTS）+ Spring Boot 四端外卖系统，含 Redis 热点缓存与事务性 Outbox、Redis Stream 异步事件、平台资金托管（escrow）、多副本部署与月度备份。交易内核达到工程级水准：库存/秒杀/状态全部条件更新且锁序固定，事件先随业务事务落库再异步投递（无幽灵事件），支付回调全字段验签，密码 PBKDF2 加盐，SQL 全程参数化。
>
> 起始评审快照发现的资金、身份、匿名评价与自动结算问题已完成对应代码整改；workflow 已接入 28 个真 MySQL 用例，但远端 Actions 尚未验证。外部支付事务改造及部分高风险闭环项仍列在 §10，不能视为已完成。
>
> 按本文批次 A→B 完成整改后，资金与身份路径的风险可收敛到可接受范围，且关键路径具备机器验证；剩余项（前端巨型文件拆分、分页与缓存失效优化、部署生产化）属于质量提升，不影响业务正确性。
