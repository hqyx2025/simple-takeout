# 校园外卖平台后端开发提示词大纲（完整版）

## 1. 项目概述

**项目名称**：简单外卖

**项目目标**：开发一个面向校园场景的外卖订餐平台，包含用户端、商户端、管理端三个端。用户可浏览校园内商家、菜品，下单并完成支付、收货、评价；商户可管理店铺、菜品、接单出餐；管理员可对平台用户、商家、订单、退款等进行管理。

**核心功能**：

- 用户端：注册登录、浏览商家/菜品、搜索、购物车、下单、支付、订单跟踪、确认收货、评价、地址管理、优惠券等。
- 商户端：入驻申请、店铺管理、菜品分类/菜品管理、订单接单/出餐、营业统计、评价回复。
- 管理端：用户管理、商户审核、分类管理、订单管理、退款处理、公告/轮播图管理、数据统计。

**角色说明**：

| 角色           | 说明       | 权限范围                    |
| ------------ | -------- | ----------------------- |
| 用户（USER）     | 校园内普通消费者 | 浏览、下单、支付、评价、管理个人地址和优惠券  |
| 商户（MERCHANT） | 校园内商家    | 管理店铺、菜品、订单（接单、出餐）、查看统计  |
| 管理员（ADMIN）   | 平台运营人员   | 全平台管理，包括用户、商户、订单、退款、内容等 |

**前端说明**：前端使用 ArtUI 进行页面开发，所有数据均来自后端接口。后端开发优先，前端完全以后端接口文档为准进行对接和调试。

### 2.3 通用约定

- **接口前缀**：
  - 认证接口：`/api/auth/**`（注册、登录、登出等）
  - 用户端：`/api/user/**`（需 USER 角色）
  - 商户端：`/api/merchant/**`（需 MERCHANT 角色）
  - 管理端：`/api/admin/**`（需 ADMIN 角色）
  - **除认证接口外，所有接口均需登录后携带 JWT 访问，包括浏览类接口。**

- **响应格式**：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {},
  "timestamp": 1690000000000
}
```

- **分页响应**：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "records": [],
    "total": 100,
    "current": 1,
    "size": 10
  },
  "timestamp": 1690000000000
}
```

- **状态码**：
  - 200 成功
  - 400 参数错误
  - 401 未认证
  - 403 无权限
  - 404 资源不存在
  - 500 服务器内部错误
  - 1001 用户名已存在
  - 1002 验证码错误
  - 2001 订单状态异常
  - 2002 库存不足
  - 2003 超出配送范围
  - 3001 商家未营业
  - 3002 商品已下架
  - 4001 退款失败

> 注：当前仓库统一响应（ApiResponse）仅使用 200 与业务错误直接 code（如 403、400）；以下 1001~4001 业务码为**预留**，待对应演进项落地后启用，AI 不得虚构未落地的状态码枚举。

## 3. 用户角色与权限模型

### 3.1 角色

- 采用统一 `user` 表存储所有账号，通过 `role` 字段区分：`USER`、`MERCHANT`、`ADMIN`。
- 商户关联 `merchant` 表存储店铺信息；管理员不需要额外表。
- 一个用户账号只能对应一个角色（简化设计），商户入驻时创建 MERCHANT 角色账号。

### 3.2 权限控制

- 登录成功后签发 JWT，包含 `userId`、`role`、`username`。
- 后端使用拦截器解析 JWT，将用户信息存入 ThreadLocal。
- 自定义 `@RequireRole("USER")` 注解标注在 Controller 类或方法上，拦截器校验角色。
- 管理端接口仅允许 `ADMIN`，商户端仅允许 `MERCHANT`，用户端仅允许 `USER`。

## 4. 登录与认证流程

### 4.1 注册

**用户注册**：

- 接口：`POST /api/auth/register/user`
- 参数：`username`、`password`、`nickname`、`phone`、`smsCode`
- 逻辑：
  1. 校验用户名、手机号唯一性。
  2. 校验短信验证码（测试环境可固定 123456 或使用 Hutool 生成验证码并打印日志）。
  3. 密码使用 BCrypt 加密存储。
  4. 创建 USER 角色用户，状态为启用。
  5. 返回注册成功，可选自动登录。

**商户注册（入驻申请）**：

- 接口：`POST /api/auth/register/merchant`
- 参数：`username`、`password`、`shopName`、`contactPhone`、`address`、`businessLicense`、`description`、`logo`
- 逻辑：
  1. 创建 MERCHANT 角色用户，状态为启用。
  2. 创建 `merchant` 记录，状态为 `PENDING`（待审核）。
  3. 等待管理员审核通过后方可营业。

### 4.2 登录

- 接口：`POST /api/auth/login`
- 参数：`username`、`password`、`loginType`（USER/MERCHANT/ADMIN）
- 逻辑：
  1. 查询用户是否存在，校验密码 BCrypt。
  2. 校验用户状态（禁用则拒绝）。
  3. 校验角色是否与 `loginType` 匹配（管理员只能登录管理端）。
  4. 生成 JWT，有效期 24 小时，返回 token 和用户基本信息。
- 响应：

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "userInfo": {
    "userId": 1,
    "username": "user1",
    "nickname": "张三",
    "role": "USER",
    "avatar": "http://..."
  }
}
```

### 4.3 登出

- 接口：`POST /api/auth/logout`
- 逻辑：前端删除本地 token 即可，后端可记录登出日志（可选）。

### 4.4 令牌刷新

- 接口：`POST /api/auth/refresh`
- 参数：`refreshToken`
- 逻辑：校验刷新令牌，签发新 JWT（可选实现，简单版本可省略）。

> **体验取舍**：JWT 有效期 24 小时（见 14.1），当前未实现刷新令牌，用户每 24 小时需重新登录一次（18.2 要求 401 强制回登录页）。若保留该简化，前端应在 Token 临近过期时给出续期/重新登录引导，避免用户在操作中途被登出。

## 5. 数据库设计

### 5.1 ER 关系概述

- 一个用户（USER）拥有多个地址、购物车、订单、评价、优惠券。
- 一个商户（MERCHANT）拥有一个店铺、多个菜品分类、多个菜品、多个订单。
- 一个订单包含多个订单项（菜品快照），关联一个地址、一个用户、一个商户。
- 一个订单可产生一个支付记录、一个退款记录、一个评价（或每个订单项评价）。
- 一个优惠券可被多个用户领取，一个用户可持有多个优惠券。

## 6. 核心订单状态机（目标演进状态机）

> **本章为目标演进状态机**：描述第三方支付、退款审批等演进能力落地后的完整状态模型，当前仓库不实现本章状态流转。当前仓库以 19.1 节数字状态机（0~6）为唯一权威，本章演进状态与数字状态的映射见 6.4。

### 6.1 状态定义

| 状态值             | 说明             |
| --------------- | -------------- |
| PENDING_PAYMENT | 待支付            |
| PENDING_ACCEPT  | 已支付，待商家接单      |
| ACCEPTED        | 商家已接单，制作中      |
| DELIVERING      | 已出餐，配送中        |
| DELIVERED       | 已送达，待用户确认收货/评价 |
| COMPLETED       | 已完成            |
| CANCELLED       | 已取消            |
| REFUNDING       | 退款中            |
| REFUNDED        | 已退款            |

### 6.2 状态流转

```
PENDING_PAYMENT --支付成功--> PENDING_ACCEPT
PENDING_PAYMENT --用户取消/超时--> CANCELLED
PENDING_ACCEPT --商户接单--> ACCEPTED
PENDING_ACCEPT --商户拒绝接单--> CANCELLED (自动退款)
PENDING_ACCEPT --用户取消(需商家确认)--> REFUNDING
ACCEPTED --商户出餐--> DELIVERING
DELIVERING --商户/骑手标记送达--> DELIVERED
DELIVERED --用户确认收货--> COMPLETED
DELIVERED --用户申请退款--> REFUNDING
COMPLETED --用户申请售后退款(可选)--> REFUNDING
REFUNDING --管理员/商户同意--> REFUNDED
REFUNDING --管理员/商户拒绝--> 回退到原状态（如DELIVERED或COMPLETED）
```

> 注：当前仓库取消订单为**即时取消**（数字状态 1/2/3 均可取消，escrow 0→2 即退余额，无商家确认环节），上图中 REFUNDING 审批链路为演进项（见 7.11/9.7）。

### 6.3 状态变更日志（演进项）

- 演进项：每次状态变更写入 `order_status_log` 表，记录操作人、时间、前后状态、备注，用于审计和问题排查。
- 现状：无日志表，状态变更依赖现有日志体系记录（见 12 章）。

### 6.4 演进状态机与当前数字状态映射

| 演进状态（6.1） | 数字状态（19.1） | 当前仓库实现 |
| --- | --- | --- |
| PENDING_PAYMENT | 0 待付款 | 预留：下单即扣款，不进入该状态 |
| PENDING_ACCEPT | 1 待接单 | 现状：下单后直接进入 |
| ACCEPTED | 2 制作中 | 现状：商户接单（1→2） |
| DELIVERING | 3 配送中 | 现状：商户出餐（2→3） |
| DELIVERED | 4 已送达，待确认 | 现状：status=4 且 escrow_status=0 |
| COMPLETED | 4 已完成 | 现状：status=4 且 escrow_status=1（确认收货结算后） |
| CANCELLED | 5 已取消 | 现状：取消即退（escrow 0→2 + 退余额 + status=5） |
| REFUNDING | 6 退款中 | 预留：现状无退款审批中间态 |
| REFUNDED | 6 退款中（已退款） | 现状以 escrow_status=2 表达，无独立状态 |

> 注意：演进状态 DELIVERED 与 COMPLETED 在现状数字状态中都对应 4，差异通过 escrow_status 表达（0=待确认收货，1=已结算完成）；前端文案必须按 status + escrow 联合判断（见 21.6）。

### 7.7 购物车

- `POST /api/user/cart/add`：添加菜品到购物车
  - 参数：`productId`、`quantity`
  - 逻辑：
    1. 校验菜品存在且上架，库存充足。
    2. 查询当前用户是否已有该商户的购物车；若无则创建。

- `PUT /api/user/cart/item/{itemId}`：修改购物车明细数量
- `PUT /api/user/cart/item/{itemId}/select`：选中/取消选中
- `PUT /api/user/cart/select-all`：全选/全不选（按商户）
- `DELETE /api/user/cart/item/{itemId}`：删除购物车明细
- `DELETE /api/user/cart/clear`：清空购物车

### 7.8 下单（现状：余额支付，下单即扣款）

- 接口：`POST /api/orders`
- 参数：

```json
{
  "storeId": 1,
  "items": [{ "goodsId": 1, "quantity": 2 }],
  "addressId": 1,
  "couponId": 1,
  "remark": "少放辣"
}
```

- 说明：items 中可附带 name/price 供展示，金额以服务端数据库实时价格为准；couponId 为 0 表示不使用优惠券。
- 业务逻辑（现状实现，全部在单个事务内）：
  1. 校验店铺存在且营业（stores.status=1）。
  2. 校验地址属于当前用户。
  3. 逐项校验商品存在、属于该店、上架（goods.status=1）。
  4. 计算商品总金额 goodsAmount = Σ(price × quantity)。
  5. 校验满足起送价（goodsAmount >= stores.min_order）。
  6. 校验优惠券：归属当前用户、未使用、店铺匹配（平台券或同店）、未过期、满足门槛。
  7. 计算实付 payAmount = goodsAmount + delivery_fee - discount（不得为负）。
  8. 校验余额充足并扣减用户余额（下单即扣款，无待支付状态）。
  9. 核销优惠券（如使用）。
  10. 创建订单：status=1（待接单）、escrow_status=0（资金托管）、items/address JSON 快照、order_no 唯一。
  11. 店铺月销量 +1。
  12. 返回订单详情（含实付金额、托管状态）。
- 异常情况：
  - 起送价不足：提示"未达到店铺起送价"。
  - 余额不足：提示"余额不足，请先充值"（充值接口为演进项）。
  - 商家未营业：提示"店铺当前未营业"。
  - 商品已下架：提示"商品已下架：XX"。
  - 优惠券不可用：提示"优惠券不可用"。
- 数据操作序列与事务边界详见 22.2。

### 7.9 支付（现状：余额支付；第三方支付为演进项）

**现状（余额支付）**：下单时直接从用户余额扣款并进入托管（见 7.8 第 8 步），无独立支付接口、无支付回调、无支付记录表；orders.pay_time 字段预留。前端提交订单后显示"支付处理中"加载态，由后端一次完成扣款与下单，不允许前端绕过余额直接提交。

**演进项（未落地，须用户批准后实施）**：
- `POST /api/user/payment/{orderNo}/mock|wechat|alipay`：独立支付接口（余额/微信/支付宝）。
- 支付回调接口（`/api/payment/notify/wechat|alipay`）：验签后更新支付记录与订单状态。
- 支付记录表 `payment_record`（见 5.2）。
- 支付超时任务：扫描 15 分钟未支付订单自动取消并回滚库存（见 10.6）。
- 演进项落地前，前端不得展示支付方式选择、支付倒计时等依赖上述接口的交互。

### 7.10 订单列表与详情

- `GET /api/user/order/list`
  - 参数：`status`（可选，按状态筛选）、`page`、`size`
  - 返回订单简略信息。
- `GET /api/user/order/{orderNo}`
  - 返回订单详情：订单状态、商品明细、金额、地址快照、时间线、配送信息。

### 7.11 订单操作（现状实现）

- `PUT /api/orders/{id}/cancel`：取消订单（现状）
  - 条件：订单归属当前用户，状态为 1 待接单 / 2 制作中 / 3 配送中，且 escrow_status=0。
  - 逻辑：escrow 0→2（条件更新，防重复退款）→ 退回用户余额 → status=5。
  - 口径说明：这是"用户取消无商家确认"的简化策略，取消即退、即时到账；如需商家确认取消（REFUNDING 审批链路），属于演进项（见 6.2/9.7）。
  - 失败反馈："当前状态不可取消" / "订单资金已处理，不能重复退款"。
- `PUT /api/orders/{id}/confirm`：确认收货并结算（现状）
  - 条件：订单归属当前用户，状态为 4，且 escrow_status=0。
  - 逻辑：escrow 0→1（条件更新，防重复打款）→ 商户余额 +payAmount（仅一次）。
  - 失败反馈："订单尚未完成，不能确认收货" / "订单款项已结算或退款，不能重复确认"。
- `POST /api/orders/{id}/review`：评价已完成订单（现状，详见 7.12）。
- 催单（`urge`）：演进项，现状无对应接口；落地时需配套商户端查看催单的接口（见 8.5）。
- 申请退款（`refund`）：演进项，现状取消即退（见上方 cancel），无独立退款申请与审批链路（9.7 为管理端演进）。

### 7.12 评价（现状：订单整体评价；按菜品评价为演进项）

- 接口：`POST /api/orders/{id}/review`（现状实现）
- 参数：`rating`（1~5）、`content`、`tags`（标签数组，可选）
- 逻辑（现状实现）：
  1. 校验订单属于当前用户且状态为 4（已完成）。
  2. 校验订单未评价过（orders.reviewed=0），防止重复评价。
  3. 创建评价记录（reviews 表，按店铺整体评价，user_name 昵称快照）。
  4. 订单标记 reviewed=1。
- 演进项：按菜品分别评价（product_id）、评价图片、评价后更新商户平均分（10.8）、商家回复评价（8.7）。
- `GET /api/user/review/list`：我的评价列表（演进项；现状为按店铺查询评价列表的接口，无"我的评价"独立入口）。

### 7.13 优惠券

## 8. 商户端接口与流程

### 8.1 商户认证

  - 参数：`open`（true/false）
  - 逻辑：更新 `open_status` 字段。

### 8.3 菜品分类管理（演进项）

- `PUT /api/merchant/category/{id}`：修改分类
- `DELETE /api/merchant/category/{id}`：删除分类（若分类下有菜品则禁止删除）

### 8.4 菜品管理

- `GET /api/merchant/product/list`
  - 参数：`categoryId`、`keyword`、`status`、`page`、`size`
- `POST /api/merchant/product`：新增菜品
  - 参数：`categoryId`、`name`、`description`、`image`、`price`、`original_price`、`stock`、`is_recommend`
- `PUT /api/merchant/product/{id}`：修改菜品
- `PUT /api/merchant/product/{id}/status`：上架/下架
- `PUT /api/merchant/product/{id}/stock`：修改库存（快速补货/清库存）

  - 删除策略（明确）：现状 goods 无逻辑删除字段，删除为物理删除；已下单订单不受影响（items 为 JSON 快照）；收藏与购物车中的该商品在下次加载时按"商品已下架"处理或过滤。

### 8.5 订单管理

- `GET /api/merchant/order/list`
  - 参数：`status`、`page`、`size`
  - 返回订单列表，按状态筛选。
- `GET /api/merchant/order/{orderNo}`：订单详情
- `POST /api/merchant/order/{orderNo}/accept`：接单
  - 条件：订单状态为 `PENDING_ACCEPT`。
  - 逻辑：更新状态为 `ACCEPTED`，记录接单时间，记录日志。
- `POST /api/merchant/order/{orderNo}/reject`：拒绝接单
  - 条件：订单状态为 `PENDING_ACCEPT`。
  - 参数：`reason`
  - 逻辑：更新状态为 `CANCELLED`，回滚库存，自动发起退款（若已支付）。
- `POST /api/merchant/order/{orderNo}/deliver`：出餐/配送
  - 条件：订单状态为 `ACCEPTED`。
  - 逻辑：更新状态为 `DELIVERING`，记录出餐时间。
- `POST /api/merchant/order/{orderNo}/complete`：送达确认（商家自配送）

## 10. 关键业务逻辑与校验

### 10.1 库存扣减与防超卖

- 下单时扣减库存，使用乐观锁：

```sql
UPDATE product
SET stock = stock - #{quantity}, version = version + 1
WHERE id = #{productId} AND stock >= #{quantity} AND status = 1
```

- MyBatis-Plus 实体增加 `@Version` 注解，或手动写 SQL。
- 支付超时/取消/退款时回滚库存：

```sql
UPDATE product SET stock = stock + #{quantity} WHERE id = #{productId}
```

- 避免重复回滚：记录回滚日志或状态判断。

### 10.2 订单号生成

- 使用 Hutool `IdUtil.getSnowflakeNextIdStr()` 或时间戳+随机数，保证唯一。
- 示例：`yyyyMMddHHmmss + 6位随机数`。

### 10.3 优惠券计算

- 满减券：`discountAmount = discountValue`（若商品总价 >= minAmount，实付金额在优惠计算之后才得出）
- 现状实现：`goodsAmount >= threshold` 即满足门槛（OrderService.createOrder）。
- 折扣券：`discountAmount = totalAmount * (1 - discountValue/10)`（如 8.5折）
- 优惠金额不能超过商品总金额。
- 同一订单只能使用一张优惠券。
- 平台券和商户券不叠加。

### 10.4 配送范围

- 根据用户收货地址经纬度与商户经纬度计算距离（Hutool 或 Haversine 公式）。
- 若超过商户配送范围（如 3km），提示"超出配送范围"。
- 校园内通常配送范围较小，可设置商户配送半径字段。

### 10.5 营业时间校验

- 下单时校验当前时间是否在 `merchant.business_hours` 范围内。
- 营业时间格式如 `"08:00-22:00"`，使用 Hutool `DateUtil` 判断。
- 若商户设置 `open_status=0`（休息中），拒绝下单。

### 10.6 超时订单处理

- 定时任务每 5 分钟执行一次：
  - 扫描 `PENDING_PAYMENT` 且创建时间超过 15 分钟的订单，自动取消，回滚库存。
  - 扫描 `DELIVERED` 且超过 24 小时未确认收货的订单，自动完成。
  - 扫描 `REFUNDING` 且超过 48 小时未处理的退款申请，通知管理员。

### 10.7 退款流程

- 用户申请退款 -> 创建退款记录，状态 `PENDING`，订单状态 `REFUNDING`。
- 管理员/商户审核：
  - 同意：调用支付退款（模拟为直接更新状态），退款记录 `REFUNDED`，订单状态 `REFUNDED`，回滚库存。
  - 拒绝：填写拒绝原因，退款记录 `REJECTED`，订单状态回退。
- 退款金额为实付金额（可部分退款，但简化版为全额退款）。

### 10.8 评价规则

- 仅订单状态为 `COMPLETED` 的用户可评价。
- 每个订单可对整体评价一次，也可对每个菜品分别评价。
- 评价后更新商户评分：计算所有评价的平均分。
- 商家可回复评价，回复后用户可见。

## 11. 统一异常处理

- 使用 `@RestControllerAdvice` 全局异常处理。
- `BusinessException`：业务异常，携带 `ResultCode` 和自定义消息。
- 参数校验异常：`MethodArgumentNotValidException` 返回 400 和第一个错误信息。
- 权限异常：`AccessDeniedException` 返回 403。
- 其他异常：记录日志，返回 500。
- 示例：

```java
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusinessException(BusinessException e) {
        log.warn("业务异常: {}", e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }
    // ...
}
```

## 19. 订单、托管和资金结算基线

当前项目采用“平台托管、确认收货后结算”的简化资金模型。余额支付属于测试环境模拟支付，不代表已经接入真实第三方支付。

### 19.1 订单状态

当前状态含义必须保持一致：

|  状态值 | 状态        | 允许的主要操作   |
| ---: | --------- | --------- |
|    1 | 待接单       | 用户取消；商户接单 |
|    2 | 制作中       | 商户出餐/进入配送 |
|    3 | 配送中       | 商户确认送达    |
|    4 | 已送达，待用户确认 | 用户确认收货并结算 |
|    5 | 已取消       | 只读        |

商户确认送达只能将订单从 3 改为 4，不能直接给商户增加余额。用户确认收货只能在状态 4 执行。

状态码 0（待付款）与 6（退款中）为预留状态：当前下单即扣款并直接进入 1（待接单），0/6 不提供任何操作入口；前端状态文案（getOrderStatusText）、状态机函数（OrderStatus.ets）与后端状态码必须保持一致（详见 21.6、22.8）。

### 19.2 托管状态

订单必须有独立的托管状态：

- `0`：托管中，用户已扣款，商户未收到结算款。
- `1`：已结算，用户确认收货后转给商户。
- `2`：已退款，订单取消或管理端审核退款后退回用户。

退款和结算必须使用条件更新或等价幂等机制，防止重复点击、并发请求导致重复退款或重复打款。

### 19.3 资金流转

```text
用户下单
  -> 校验商品、库存、地址和余额
  -> 扣除用户余额
  -> 订单 escrow_status=0
  -> 商户接单、制作、配送
  -> 商户确认送达，订单 status=4
  -> 用户确认收货
  -> escrow_status=1
  -> 商户余额增加一次
```

取消订单或管理端退款时：

```text
escrow_status=0
  -> escrow_status=2
  -> 用户余额退回一次
  -> 订单 status=5
```

## 20. 前端交互和页面一致性要求

### 20.1 地址和定位

- 用户从主页进入定位页后，可以拖动地图、搜索地点或使用当前位置。
- 点击“确认位置”保存成功后，必须弹窗说明“地址已保存，可用于主页配送和下单”。
- 弹窗必须提供“返回首页”和“留在此页”两个明确操作。
- 返回首页后主页必须刷新当前城市/市区显示和附近商品，不得要求用户重新进入页面才能刷新。
- 地址展示必须区分联系人姓名、手机号和详细地址；定位结果不能覆盖用户已经填写的联系人信息。
- 未登录点击定位时，先弹窗说明无法定位，再由用户确认是否去登录。

### 20.2 商户和商品详情

- 分类页、附近页、搜索页和收藏页中的商户卡片都必须可点击。
- 点击商户后必须进入该商户的商品详情页，详情页标题、商户 ID、商品列表和评价必须属于同一家商户。
- 不得出现“点击张亮麻辣烫却显示黄焖鸡米饭”等店铺和内容错位问题。
- 返回列表后应保留原分类、搜索关键词和滚动状态（如果平台能力允许）。
- 商品数量加减、收藏、上下架等操作必须立即刷新 UI，并同步后端失败提示。

### 20.3 数据来源和状态

所有业务页面必须明确处理四种状态：

1. 加载中：显示加载提示，禁止重复提交。
2. 成功：显示服务端真实数据。
3. 空数据：显示“暂无数据”和下一步操作建议。
4. 失败：弹窗或 Toast 使用中文说明具体原因，并允许重试。

前端不得使用与后端真实数据冲突的默认订单、收藏、店铺或商品。默认分类图标只能用于服务端暂无数据时的视觉占位，服务端返回成功后必须以服务端数据为准。

## 21. 用户操作判断与流程分析

> 本章补充各角色在核心流程中的**操作判断点**：前端体验层拦截、后端权威校验、异常分支与失败反馈，以及操作按钮与订单状态机的联动规则。前端判断失败只阻止操作、不修改数据；后端判断失败必须返回中文错误消息并记录日志。

### 21.1 判断分层原则

1. **前端只做体验判断**：登录态、输入完整性、按钮可用性、防重复提交、二次确认。前端判断失败不修改任何数据，只阻止操作并给出中文提示。
2. **后端做权威判断**：身份与角色、资源归属、订单状态机、资金托管状态、数据一致性。后端判断失败必须返回中文错误消息（统一响应 code + message），并记录日志。
3. **状态机单一来源**：前端 `OrderStatus.ets`（canTransitionOrderStatus）与后端 `OrderService`（requireStatus）必须使用同一套状态码；前端按钮显隐不得与后端校验规则冲突。
4. **资金操作必须二次确认**：取消订单、确认收货并结算等涉及余额变动的操作，前端必须弹确认框；后端仍以条件更新兜底防重复（见 22.3/22.4）。
5. **后端校验不可被前端拦截替代**：即使前端已拦截，后端仍必须独立校验用户存在性、角色、资源归属与订单状态（18.2）。

### 21.2 用户端操作判断矩阵

| 场景 | 前端操作判断 | 后端权威校验 | 失败反馈 |
| --- | --- | --- | --- |

```
└─ 成功：退回用户余额 → status=5 → 前端刷新详情/列表
```

```
├─ ConfirmDialog 二次确认（明示将结算给商户）→ 通过

├─ 后端：status=4？→ "订单尚未完成，不能确认收货"
```

### 21.4 商户端操作判断

| 订单状态 | 可用操作 | 后端校验 | 资金影响 |
| --- | --- | --- | --- |
| 1 待接单 | 接单（1→2） | 店铺归属（owner_id）+ 当前状态 | 无 |
| 2 制作中 | 出餐配送（2→3） | 店铺归属 + 当前状态 | 无 |
| 3 配送中 | 确认送达（3→4） | 店铺归属 + 当前状态 | 无（不得直接给商户加余额） |
| 4 已完成 | 查看订单、回复评价 | 店铺归属 | 待用户确认收货后 escrow 结算 |

- 商户订单列表/详情必须按 owner_id 过滤；每次操作前必须校验订单店铺归属（OrderService.merchantFlow / orderDetail 的 role=1 分支）。
- 商户确认送达只改状态（3→4），资金结算必须由用户确认收货触发，防止商户自买自结。
- 商户统计只统计 `status=4 AND escrow_status=1` 的已结算订单（今日/本周/本月），不得把托管中的款项计入营业额。
- 商户端不支持操作 0 待付款与 6 退款中状态（预留状态，见 21.6）。

### 21.5 管理端操作判断

- 商户审核：仅 `PENDING` 可审核，通过 → APPROVED，拒绝 → REJECTED（必须填写原因）。
- 退款/异常订单取消：与用户取消走相同的 escrow 条件更新链路，保证幂等（22.3）。
- 管理端账号不允许公开注册，只能由初始化或受控流程创建（18.1）。
- 管理端所有变更操作必须二次确认，并对资金操作保留审计日志。

### 21.6 操作按钮与状态机联动规则（补全）

- **前端按钮显隐**：`status=1` → 仅"取消订单"；`status=4 && escrowStatus=0` → "确认收货并结算"；`status=4` → "再来一单 + 去评价"；其余状态只读（展示时间线/配送动画）。
- **状态机同步维护**：前端 `OrderStatus.canTransitionOrderStatus(from, to)` 与后端 `requireStatus` 必须同步；新增状态流转必须先改后端状态机，再改前端工具函数与按钮显隐。
- **状态 0/6 为预留**：0（待付款）与 6（退款中）不在任何页面暴露操作按钮，当前下单直接进入 status=1；状态文案（getOrderStatusText）与后端注释必须保持一致。

## 22. 数据操作流程与事务边界

> 本章按仓库现状（server 模块 JdbcTemplate 实现）补全各核心流程的完整数据操作序列、事务边界与幂等机制，并列出大纲设计项与现状的差异清单。

### 22.1 数据操作总则

1. 多表写操作必须使用 `@Transactional`（OrderService 已覆盖下单/取消/确认收货/评价）。
2. 资金类变更必须条件更新（如 `UPDATE orders SET escrow_status=2 WHERE id=? AND escrow_status=0`），更新行数为 0 即视为已处理，防止重复退款/打款。
3. 金额计算统一保留两位小数（后端 round2，前端 OrderCalculations 纯函数），前端展示与后端计算使用同一公式。
4. 订单必须保存快照：`store_name`、`items`（商品 JSON）、`address`（地址 JSON）下单时固化；店铺改名、商品改价、地址修改不影响历史订单。
5. 写操作顺序固定：只读校验 → 扣款/核销 → 落订单主档 → 更新统计字段；任一失败整体回滚。
6. 时间字段统一 `yyyy-MM-dd HH:mm:ss` 字符串格式，由后端写入，前端不拼装业务时间。

### 22.2 下单数据操作流程（现状实现）

```
POST /api/orders  createOrder(userId, storeId, items, addressId, couponId, remark)
[只读校验]
 1. stores   查店铺，校验 status=1（营业中）
 2. addresses 查当前用户地址列表，校验 addressId 归属
 3. goods    逐项校验：存在、store_id==storeId、status=1；金额 = Σ(price×quantity)
 4. 校验 goodsAmount >= stores.min_order（起送价）
 5. coupons  校验：user_id 归属、status=0、store_id 匹配（0 或同店）、未过期、goodsAmount>=threshold
 6. 计算 payAmount = goodsAmount + delivery_fee - discount（<0 报"优惠金额不能超过订单金额"）
[事务内写操作]
 7. users    校验 balance >= payAmount，扣减余额（当前为读-算-写，见 22.9）
 8. coupons  核销：status 0→1（使用了券时）
 9. orders   INSERT：order_no（yyyyMMddHHmmss+4位随机数）、items/address JSON 快照、
            status=1、escrow_status=0、reviewed=0、create_time=now
10. stores   UPDATE monthly_sales = monthly_sales + 1
11. 返回订单详情（含 payAmount、escrowStatus）
```

**说明**：当前实现"下单即支付"（余额支付），无独立待付款状态与支付回调；订单直接进入待接单（status=1），资金同时进入托管（escrow=0）。新注册 USER 角色用户赠送 20 元测试余额（AuthService.register），余额不足时提示"余额不足，请先充值"。

### 22.3 取消订单数据操作流程（现状实现）

```
PUT /api/orders/{id}/cancel  cancelOrder(userId, orderId)
 1. orders 查订单，校验 userId 归属
 2. 校验 status ∈ {1,2,3}
 3. 条件更新：UPDATE orders SET escrow_status=2 WHERE id=? AND escrow_status=0
    → 更新行数 0 则抛"订单资金已处理，不能重复退款"（幂等）
 4. users 读当前余额，回退 balance = balance + pay_amount
 5. orders UPDATE status=5, complete_time=now
```

**口径说明**：下单时店铺月销量 +1（见 22.2 第 10 步），取消订单**不回滚**，即月销量口径为"累计下单数（含已取消）"；如需"成交数"口径，可在取消时回滚月销量（演进项）。

### 22.4 确认收货结算数据操作流程（现状实现）

```
PUT /api/orders/{id}/confirm  confirmOrder(userId, orderId)
 1. orders 查订单，校验 userId 归属
 2. 校验 status=4（商户已确认送达）
 3. 条件更新：UPDATE orders SET escrow_status=1 WHERE id=? AND escrow_status=0
    → 更新行数 0 则抛"订单款项已结算或退款，不能重复确认"（幂等）
 4. 查商户账号（stores.owner_id → users）
 5. users UPDATE balance = balance + pay_amount（商户到账，仅一次）
```

**商户确认送达（3→4）**只更新 `status=4, complete_time`，不触碰任何余额字段；结算必须由用户确认收货触发。

### 22.5 商户订单状态流转（现状实现）

| 操作 | 前置状态 | 后置状态 | 时间字段 | 资金 |
| --- | --- | --- | --- | --- |
| accept 接单 | 1 | 2 | accept_time | 无 |
| deliver 出餐 | 2 | 3 | deliver_time | 无 |
| complete 送达 | 3 | 4 | complete_time | 无（结算见 22.4） |

每次操作：校验店铺归属（owner_id）→ 校验当前状态 → updateStatus 写状态与时间字段。

### 22.6 评价数据操作流程（现状实现）

```
POST /api/orders/{id}/review  reviewOrder(userId, orderId, rating, content, tags)
 1. orders 查订单，校验 userId 归属、status=4、reviewed=0
 2. 校验 1 <= rating <= 5
 3. reviews INSERT：store_id、user_id、user_name（昵称快照）、rating、content、tags(JSON)、create_time
 4. orders UPDATE reviewed=1（防重复评价）
```

### 22.7 前端本地数据操作流程（补全）

- **购物车**：仅存于前端 AppStorage（`cartItems`），无后端购物车表；按 storeId 分组展示与结算（CartPage.checkoutStore）。
- **下单成功**：① 逐项清空该店本地购物车（updateCartItemQuantity 置 0 移除）→ ② 若使用券则 `syncCouponsRemote()` 重新拉取券状态 → ③ 写 `currentOrderId/currentOrder` → ④ 跳转订单详情页。
- **取消/确认收货**：调用后端成功后更新本地订单对象；返回订单列表时 `onPageShow` 必须重新拉取后端数据，禁止依赖本地旧状态。
- **再来一单**：将订单 items 逐项 `addToCart` 写回本地购物车（同商品数量累加，新增项沿用订单快照中的商品信息）。
- **登出**：清除内存 Token、AppStorage 登录态、持久化登录数据及账号绑定的购物车与业务缓存（18.2）。

| 16 | 评价后更新商户评分（10.8） | 现状 reviewOrder 不更新 stores.rating（默认 4.5） | 演进项：评价后重算平均分；落地前评分保持默认 |
| 17 | 逻辑删除字段 deleted（5.2 user 表） | 现状各表均无 deleted 字段，删除为物理删除 | 演进项：加 deleted 或明确级联清理；删除策略见 8.4/9.5 |
| 18 | 业务码 1001~4001（2.3） | 现状 ApiResponse 仅 200 与业务错误直接 code | 业务码预留；AI 不得虚构未落地枚举 |

### 22.9 事务与并发要点（补全风险项，均标注为演进项）

1. **余额更新为"读-算-写"**：现状 `findById → 计算 → updateBalance`，并发扣款存在覆盖风险（两笔同时下单可能只扣一笔）。演进项：改为原子更新 `UPDATE users SET balance = balance - ? WHERE id = ? AND balance >= ?`。
2. **优惠券核销非条件更新**：现状 markUsed 无条件置 1。演进项：`UPDATE coupons SET status = 1 WHERE id = ? AND status = 0`，防并发重复核销。
3. **托管资金幂等已具备**：refundEscrow/releaseEscrow 条件更新 + 事务，覆盖"重复取消/重复确认收货"测试场景（测试门槛见 24.1）。
4. **订单号唯一性**：order_no 为时间戳+4位随机数，orders.order_no UNIQUE，高并发存在碰撞概率。演进项：改用全局唯一 ID 并在冲突时重试。
5. 以上均为演进项标注，未经用户批准不得直接改动现状实现（17.1）。

## 23. API 对接和日志要求

### 23.1 API 契约

- 前端 API 路径、请求方法、字段名称和响应结构必须以当前后端 Controller 和 schema 为准。
- 统一响应至少包含 `code`、`message`、`data`。
- 前端必须处理业务失败的 HTTP 200 响应，不能只判断网络请求是否成功。
- 401 必须进入重新登录流程，403 必须提示无权限，400 必须显示后端校验消息。
- 受保护接口不得在没有 Token 时静默发送；公共接口必须在文档中明确列出。

### 23.2 前后端日志

每次前端请求后端至少记录中文业务名称、HTTP 方法、接口路径、响应状态码和后端消息。失败时必须记录用户可理解的原因。

后端必须记录请求方法、路径、用户 ID（如已登录）、角色、响应状态和异常原因。密码、JWT 完整内容、手机号完整值等敏感数据不得写入日志。

## 25. AI 执行协议

当把本大纲交给 AI 编程助手时，必须要求 AI：

1. 先读取仓库结构和相关源文件，列出将要修改的文件。
2. 说明当前实现与大纲的差异、风险和兼容方案。

本轮任务如果用户只要求“完善大纲”，AI 只能修改 Markdown 文档，不得修改业务代码、数据库脚本、配置文件或自动提交代码。
