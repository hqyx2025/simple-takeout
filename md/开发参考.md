## 1. 项目概述

- **定位**：HarmonyOS NEXT 外卖 App（毕业设计，对标美团外卖），单 HAP 工程
- **四端闭环**：用户端（搜索→下单→评价）/ 商户端（接单→出餐→统计）/ 骑手端（抢单→取餐→送达）/ 平台管理端（审核→内容→统计）
- **目录结构**：`server/` 后端模块（Spring Boot）+ `entry/` 前端模块（HarmonyOS ArkTS）
- **设计参考**：`md/archive/重构大纲提示词.md` 记录业务设计与演进设想；实际实现以仓库代码和当前需求为准。
- **`md/` 保留开发参考、设备实测指南及当前业务 / 交互诊断实施记录**；旧设计、历史实施进展、会话与验收记录归档在 `md/archive/`，按需查阅，不触发执行流程。`README.md` 的「文档索引」列出当前文档与归档入口。归档时同步更新 README、其他文档及脚本中的路径；Markdown 链接相对于所在文件解析，代码片段中的 `md/…` 路径相对于仓库根目录。
- **管理端独立后台**：ADMIN 登录后直接进入平台管理页（AdminCenterPage + 分类/店铺/订单/退款审批四个独立页面），任何情况下不展示主页/定位/购物车等 C 端功能

## 3. 构建与运行

- 后端启动：先设 `JAVA_HOME` 指向 JDK 25、导入私有环境配置，执行 `mvn -f server/pom.xml -pl takeout-common -am install -DskipTests`，再 `mvn -f server/pom.xml -pl takeout-app spring-boot:run`（端口 8087）；不要使用聚合根直接启动应用或依赖旧 common jar
  - **多模块后（Phase 2 起）**：`server/pom.xml` 是聚合根（parent + modules），模块为
    `takeout-common`（共享契约层：model/dao/security/通用工具）、`takeout-app`（单体应用）、
    `takeout-gateway`（API 网关）。因此
    - `mvn -f server/pom.xml test` 会自动跑全部模块；2026-10-25 的完整 reactor 实际执行 594 项、0 跳过。真 MySQL 用例需 `TAKEOUT_MYSQL_CONCURRENCY_TEST=1`，真实 Redis 用例需 `TAKEOUT_TEST_REDIS_PORT`，连接信息必须指向可清理的私有测试实例
    - `mvn -f server/pom.xml spring-boot:run` 需指定模块：`mvn -f server/pom.xml -pl takeout-app spring-boot:run`
    - 单模块跑测试需带 `-am`（否则找不到 takeout-common 构件），如
      `mvn -f server/pom.xml -pl takeout-app -am test -Dtest=XxxTest -Dsurefire.failIfNoSpecifiedTests=false`
    - 网关单独启动：`mvn -f server/pom.xml -pl takeout-gateway spring-boot:run`（默认监听 8087，转发到 `${TAKEOUT_APP_URI:-http://127.0.0.1:9100}`）
    - 应用端口可用 `TAKEOUT_APP_PORT` 覆盖（默认仍 8087）。与网关同机同跑时把应用挪开，如
      `--server.port=9100` 或 `TAKEOUT_APP_PORT=9100`，再由网关占住对外的 8087
    - **迁移共享代码时保持包名不变、只改物理位置**：Java 包名与路径无关，因此跨模块搬迁零 import 改动——
      这是 200+ 用例在搬迁后仍全绿的原因（Phase 3 实测）
- 前端构建（本机工具链在 `C:\Program Files\Huawei\DevEco Studio`）：
  ```powershell
  $env:DEVECO_SDK_HOME="C:\Program Files\Huawei\DevEco Studio\sdk"
  & "C:\Program Files\Huawei\DevEco Studio\tools\node\node.exe" "C:\Program Files\Huawei\DevEco Studio\tools\hvigor\bin\hvigorw.js" `
    --mode module -p module=entry@default -p product=default -p requiredDeviceType=phone assembleHap --analyze=normal --parallel --incremental --daemon
  ```
  构建日志：`.hvigor/outputs/build-logs/build.log`；判断成功要看日志里的 `BUILD SUCCESSFUL` 并确认 `entry/build/default/outputs/default/*.hap` 时间戳已更新（流水线里 `Select-String` 会吞掉退出码，别只看 `$LASTEXITCODE`）
- 后端测试：`mvn -f server/pom.xml test`。2026-10-25 安全基线为 app 585 项 + gateway 9 项，共 594 项、0 失败、0 跳过，使用上述真实 MySQL/Redis 门控和私有实例；2026-10-26 R2 前 Windows 全量为 app 647 项（61 项条件跳过）+ gateway 9 项、零失败，最终独立 Linux 全量 656 项、0 失败 / 错误 / 跳过，证据为 `TemporaryCacheStorage/publish-ci-linux-final2/summary.json`。各批结果见 [实施记录](人性化改造诊断与实施方案.md)。普通本地运行缺少环境变量会跳过相应用例，不能等同真实库完整验收。测试覆盖权限、资金状态机、幂等、并发、支付、Outbox、网关、登录容量和缓存边界。
- Docker Compose 默认单机双实例，启动前配置数据库密码与至少 32 字节 JWT 密钥。完整运行说明见 [README](<../README.md#快速开始>)。
  - 拓扑：`:8087 → gateway → app-balancer（Nginx）→ app × 2`。app 无宿主端口映射，数据库和图片共享本机数据卷；不是跨主机高可用。
  - **网关是信任边界，两处配置不可随意改**（都有契约测试守护，见 `takeout-gateway` 的 `GatewayXForwardedConfigTest`）：
    - `spring.cloud.gateway.server.webflux.x-forwarded.for-append` **必须为 false**。公网 Nginx、网关的 `ClientIpHeadersFilter`、内部代理信任正则及后端来源解析须配套，确保采用受信入口确认的来源；不能直接信任客户端传入的 `X-Forwarded-For`。旧实现曾保留伪造列表首项造成绕过，当前回归覆盖该路径
    - `spring.cloud.gateway.server.webflux.trusted-proxies` **必须显式配置且能匹配直连地址**。该项是**正则**（不是 CIDR），写成 `0.0.0.0/0` 匹配不上 `127.0.0.1` 会静默失效；失效时网关会剔除 X-Forwarded-* → 后端只能看到网关地址，**全站共用一个限流桶**（一人触发封禁让所有人登录失败）
- **多实例（水平扩展）运行**：应用无状态，可直接起多个实例连同一套 MySQL + Redis。同机多实例示例（避免占用 8087）：
  ```powershell
  mvn -f server/pom.xml -pl takeout-app spring-boot:run "-Dspring-boot.run.arguments=--server.port=9001"
  mvn -f server/pom.xml -pl takeout-app spring-boot:run "-Dspring-boot.run.arguments=--server.port=9002"
  ```
  容器可用 `docker compose up -d --scale app=3` 扩容，默认仍为两个副本。Nginx 通过 Docker DNS 动态更新地址。现有 Outbox 行级认领、消费者实例 ID 和 SchedulerLock 保留；Redis 故障时下单请求由数据库唯一键继续防重。订单号为日期加七位数字候选值，截断雪花值本身不保证唯一，最终依赖数据库 UNIQUE 和冲突重试。
- **链路追踪**：网关/上游传 `X-Request-Id` 则沿用、没有则生成，值写入日志 MDC（logback pattern 已含 `%X{traceId}`）并回写响应头。排查一次请求时，在 Compose 项目根目录执行 `grep <traceId> logs/app/app.log logs/gateway/gateway.log`；公网访问和内部转发分别查看 `logs/public-nginx/`、`logs/app-balancer/`。
- 后端测试与运行都要求 `JAVA_HOME` 指向 **JDK 25**；`server/Dockerfile` 的构建阶段也必须是 JDK 25，否则 `maven.compiler.release=25` 直接编译失败
- Release 打包（**当前范围外，可选工具**）：`scripts/enable-release-signing.ps1`（接入发布证书）→ `scripts/build-release.ps1`（签名包）→ `scripts/release-check.ps1 [-Build]`（上架体检，输出 `md/上架体检报告.md`，该报告为生成物不入库）；详见 `md/archive/上架体检与Release签名.md`。日常开发只需 debug 构建，不必碰这一套。
- **注意**：PowerShell 5.x 不支持 `&&`，连续命令必须分开执行；`git commit` 不支持 heredoc，长提交信息先写文件再 `git commit -F <file>`
- 模拟器访问宿主机后端：`http://10.0.2.2:8087`

## 4. 环境配置

- **MySQL**：本机入口 `localhost:3310`，库 `takeout`；应用使用 `TAKEOUT_DB_USERNAME`（默认 `takeout`）及 `TAKEOUT_DB_PASSWORD`，root 另用 `TAKEOUT_MYSQL_ROOT_PASSWORD`。demo 不发布数据库宿主端口。已有卷须实际修改对应数据库账号，改环境变量不会重置旧密码。
- **Redis**：本机入口 `localhost:6387`；连接参数包括 `TAKEOUT_REDIS_HOST/TAKEOUT_REDIS_PORT/TAKEOUT_REDIS_USERNAME/TAKEOUT_REDIS_PASSWORD/TAKEOUT_REDIS_DATABASE`。配置私有 `.env` 后可执行 `docker compose up -d redis`；主编排仅回环发布，demo 不发布 Redis 宿主端口。默认 `maxmemory=256mb`、`noeviction`、容器 768 MiB，保留 AOF 和自动重写。
- **缓存与事件参数**：TTL 300 秒 + 抖动 0..119 秒、空值占位 60 秒、回源锁 3000 ms；v3 缓存 512 个值槽与 512 个锁，0–7 为固定目录专属槽，8–511 为动态区。`TAKEOUT_CACHE_MAX_ENTRY_BYTES` 默认 1 MiB、启动范围 64 KiB..4 MiB，仅放大固定目录，动态单值仍最多 64 KiB；默认编码载荷上界 39.5 MiB，超限 WARN 同槽每进程每分钟最多一条。浏览入口按账号 120 次/60 秒，坐标在读缓存前校验。Outbox 中继 2000 ms、消费幂等 24 小时；当前规则见 [README](../README.md#浏览缓存资源边界)，归档架构稿仅供历史参考。
- **JWT 与刷新**：访问令牌默认 72 小时，`POST /api/auth/refresh` 使用 30 天有效、轮换且持久化摘要的 refresh token，重放已消费凭据会撤销同族会话。`POST /api/auth/logout` 撤销当前访问令牌及提供的刷新族，状态落数据库；改密和身份改绑推进 `password_changed_at` 并撤销旧凭据，禁用账号使旧会话失效。认证收口于 `AuthInterceptor`；JWT、验证码 HMAC、AI 配置、钱包密钥必须独立，格式要求见 `.env.example`，部署不能随意轮换已有加密密钥。
- **下单防重（idempotencyKey）**：`POST /api/orders` 请求体可带最长 128 字符的 `idempotencyKey`；Redis `SET NX`（5 分钟 TTL）快速拦截连点，数据库 `order_create_requests` 以 `(user_id, request_key)` 主键提供持久防重，并在订单事务中将 `order_id` 绑定到原订单。相同标识返回原订单当前状态，不因原券已核销 / 购物车已清空而再次建单；未绑定的历史占位只提示核对订单，不猜测对应订单。Redis 不可用时由数据库兜底，事务失败占位随事务回滚；旧客户端未传标识仍走原兼容路径。
- **退款申请防重**：`POST /api/orders/{id}/refund` 可带 `idempotencyKey`，服务端持订单行锁校验归属；`refund_apply_requests` 将每个已受理 `(order_id, request_key)` 固定映射到 `refund_id`，包括复用同一待审申请的不同请求标识。审批终态后的原标识仍返回原申请；拒绝后只有新的申请意图才使用新标识。`refund_records.request_key` 保留主请求与旧版本兼容，原始标识不进入公共响应模型。
- **登录/注册/下单限流**：所有 profile 必须启用。登录按来源失败 10/60/600、来源总量 60/60/60、账号失败 10/60/600、账号总量 30/60/60 分桶（次数/窗口秒/封禁秒），账号使用解析后的稳定 ID，手机号严格匹配 `1[0-9]{10}`。成功不计失败，也不清除失败预算。验密先取许可，默认 2 并发、最多 32 个等待名额、等待 5000 ms；2026-10-25 安全基线的体验站等待为 10000 ms，实际部署值须从私有配置核对。容量 503 不占准入预算。注册 5 次/小时/来源，下单 10 次/分钟/账号。Redis 故障保留有界本地/溢出桶保护；登录慢调用达 250 ms 或异常后按进程冷却 5 秒并探测恢复，多副本会退化为 N 份本地预算，不能称为全局仍共享。429、503 分别表示限流和容量拒绝；已知本地封禁仍拒绝。四项接受风险见 [最终结论](audit/最终结论.md)。
- **日志**：应用由 `server/takeout-app/src/main/resources/logback-spring.xml` 配置，网关使用同样策略的 `server/takeout-gateway/src/main/resources/logback-spring.xml`。Compose 将两者分别挂载到项目根目录 `logs/app/`、`logs/gateway/`，当前文件为 `app.log` / `gateway.log`，按天和单文件 2MB 轮转、归档压缩、保留 30 天；内部负载均衡和公网 Nginx 分别写入 `logs/app-balancer/`、`logs/public-nginx/`，按天检查、超过 10MB 提前轮转、保留 14 份；HarmonyOS 客户端写入沙箱 `filesDir/logs/mobile/`。**每条应用/网关日志带 `traceId`**（MDC 键 `traceId`）；目录可用 `TAKEOUT_LOG_DIR` 覆盖，级别用 `TAKEOUT_LOG_LEVEL`/`TAKEOUT_LOG_ROOT_LEVEL`。密码/JWT/手机号完整值禁止入日志
- **高德 Key**（双 Key 概念）：`AMAP_CONFIG.MAP_JS_KEY` 是客户端地图 JS Key，jscode 在 `AMAP_CONFIG.MAP_JS_SECURITY_CODE`；REST Key 只放 `TAKEOUT_AMAP_REST_KEY`，由后端代理使用，不写入 ArkTS。
- **订单支付时限**：`takeout.order.pay-timeout-minutes`（环境变量 `TAKEOUT_PAY_TIMEOUT_MINUTES`，默认 15 分钟）；超时扫描间隔 `takeout.order.timeout-scan-ms`（默认 60 秒，启动 30 秒后首扫）
- **评价图片存储**：`takeout.upload.dir` 默认 `uploads/`，公开 `/uploads/**`，缺失资源返回 404。写入须 JWT，单张 ≤5 MiB，校验扩展名、Content-Type 与文件魔数的一致性，支持 jpg/jpeg/png/webp/gif；`UploadService` 按账号 30 次/小时、持久化账号默认 100 MiB/全局 20 GiB 预算，本地存储保留默认 512 MiB 磁盘余量。production 使用 OBS；公开资源可读不等于可匿名上传。
- **同步与参数保留**：源码更新不轮换生产私有 `.env`、数据库 / Redis 口令、JWT / 验证码 / 钱包 / AI 加密密钥、支付凭证或地图服务凭证，不把本地测试账号、订单、券、余额或演示目录导入服务器。已有卷中的口令须与真实账号一致，钱包等密钥涉及存量密文，不能用新示例值替换。保留 MySQL、Redis、上传和备份卷，不执行 `docker compose down -v`；自动补结构不等于删除或重建业务数据。
- **本次体验站参数核对**：`ux-20261026-1950-sync-r2` 保留 develop、沙箱支付宝和余额支付；种子、充值、注册赠金、mock 验证码 / 支付均关闭，目录缓存单值上限 1 MiB，登录验密 2 许可 / 等待 10000 ms。这里只记非秘密运行参数，不记录私有环境值或验收 token。

## 5. 核心业务口径（改代码前必读）

- **安全开关与 profile**：Compose 必须显式选择 develop 或 production。所有 profile 均禁止演示充值、注册赠金、mock 支付和验证码回传，要求 QQ 邮箱验证与限流；支付宝渠道启动校验不再仅由 production 装配。develop 可用本地上传和沙箱支付，production 另要求 OBS。种子数据默认关闭；本地初始化时管理员口令至少 16 位、普通账号随机口令。
- **自动确认与结算**：`takeout.order.auto-confirm-hours` 默认 24 小时，`OrderAutoConfirmJob` 扫描已送达且未结算订单；用户确认与自动确认共用结算逻辑。商户结算额为 `pay_amount - delivery_fee`，配送费记为骑手收入。

- **订单状态机**：数字状态（**0 待付款** / 1 待接单 / 2 制作中 / 3 配送中 / 4 已送达 / 5 已取消 / 6 退款流程）与托管资金共同决定真实阶段；4 + escrow=0 待确认、4 + escrow=1 已完成、6 + escrow=0 申请处理中、6 + escrow=2 已退款。骑手本人已接的 status=2 显示待取餐。大纲字符串状态仅为历史演进参考。
- **托管资金 escrow_status**：0 托管中 / 1 已结算 / 2 已退款；确认收货不改变 status（保持 4），结算更新要求 `status=4 AND escrow_status=0`。商户实收 `pay_amount - delivery_fee`，配送费计入骑手收入；超过 `takeout.order.auto-confirm-hours`（默认 24 小时）仍未确认时，`OrderAutoConfirmJob` 自动结算。**前端状态文案必须按 status + escrow 联合判断**。
- **支付（待付款模型，已落地）**：`POST /api/orders` 占用库存/秒杀名额/优惠券并落库为 status=0，不扣余额；`POST /api/orders/{id}/pay` 按渠道支付。余额需独立支付密码，扣款与 0→1 条件更新同事务；支付宝沙箱先发起支付，服务端验签通知或主动查单确认后推进 0→1，不能凭客户端支付返回改变状态。默认 payDeadline 为创建后 15 分钟；超时扫描取消并回滚占用。商户列表不展示待付款订单；支付/退款记录持久化并保护重复确认。
- **取消订单**：用户仅可取消 status=0/1；status=0 释放库存 / 秒杀名额 / 优惠券，escrow 保持 0，status=1 按原渠道退款并条件更新 escrow 0→2、status=5。制作 / 配送中的 status=2/3 转平台，管理员仍可对未送达订单取消退款。已支付的用户 / 平台取消不退券。余额支付退余额，支付宝支付调用原渠道退款，禁止外部支付退款转存余额。
- **商家拒单**：仅待接单 status=1、escrow=0 且有门店权限时可调用 `POST /api/merchant/orders/{id}/reject`；原因包括缺货、产能不足、临时歇业与其他。缺货须传订单内 `goodsId/specId`，停售对应 SKU。退款、库存恢复、仍有效券释放与原因持久化在同一事务完成；重复请求返回原拒单结果。用户只见服务端可信原因，`reject_note` 内部备注不下发。
- **退款申请 / 历史**：`POST /api/orders/{id}/refund` 和 `GET /api/orders/{id}/refunds` 均要求用户角色 CUSTOMER（role=0）及本人订单。申请仅允许 status=4、escrow=0 且未评价；原因 code 为 `NOT_RECEIVED / QUALITY_ISSUE / WRONG_ITEM / DONOT_WANT / OTHER`，“其他”必须有说明。成功进入 status=6；平台同意按原支付渠道退款至 escrow=2、status 保持 6，已送达餐品不恢复可售库存；拒绝回到 4，必填理由供用户查看。公共 `RefundRecord` 返回编号、类型、说明、金额、状态、申请 / 处理时间与驳回理由，状态为 `PENDING / APPROVED / REJECTED / REFUNDED`。确认 / 评价后的赔付政策和证据工单未建设，不能用现有退款入口冒充完整售后。
- **配送方式**：App / Web 新单仅开放立即配送；服务端在资源占用前拒绝新建自取和预约请求。`delivery_type/expect_time` 字段继续保留以兼容存量，不代表已具备取餐核销、预约容量或改期能力。
- **多规格 SKU**：`goods_specs` 每个规格独立价格与库存；菜品的 `price`/`stock` 是**规格最低价/库存合计**（由规格聚合回写，保证列表、起送价、筛选口径一致）；购物车按 `(user_id, goods_id, spec_id)` 唯一；下单必须带 `specId`（无规格菜品传 0 且不接受非 0），订单 items JSON 快照 `specName` 保证历史可读；扣库存需**同时扣 goods 与规格库存**，取消时同步回滚
- **限时秒杀**：`seckills` 表按时间窗口 + 名额（quota/sold）控制；**仅对无规格菜品生效**（规格价与秒杀价语义冲突）；下单时后端自动套用秒杀价并占用名额（`sold + n <= quota` 条件更新），占不到名额自动回退原价；**一人一单**：`seckill_orders` 表唯一键 `(user_id, seckill_id)` 拦截重复下单。未送达取消、超时取消或商家拒单时与名额一并释放，已送达审批退款不释放可售库存或秒杀名额。
- **凑单**：`GET /api/stores/{id}/bundle?amount=X` 返回还差多少元起送（gap）与店内最低价菜品推荐；起送价判断仍以服务端下单校验为权威
- **金额口径**：券门槛按**单店商品总价**判断，配送费不计入门槛；资格同时校验归属、店铺、未用与真实到期时间，创建时间不是生效时间。优惠后 `payAmount = goodsAmount + deliveryFee - discount` 必须 >0；券等于商品额但仍支付配送费可以合法使用，不能用 `券额 >= 商品额` 一律过滤。客户端按分比较并解释不可用原因，预估推荐保留主动“不使用”；折扣 / 新客活动叠加及最终金额以服务端计算为准。月销量为“累计下单数”（取消不回滚，含待付款）；金额统一两位小数。
- **幂等与库存**：退款 / 结算必须带状态条件更新，防重复入账；结算仅允许 `status=4 AND escrow_status=0`。库存扣减用条件更新（`WHERE stock>=? AND status=1`）；未送达取消 / 商家拒单按事务恢复资源，已送达审批退款不回库。不能把“所有退款都回库”作为共享规则。
- **购物车权威契约**：下单按本店 `(goodsId, specId, quantity)` 全等核对，服务端重算金额；成功仅删对应 SKU，直购不删除现有购物车。多店客户端分店建单，部分成功保留真实成功单，只重试失败店；响应未知先沿用冻结请求核对，不能生成新标识盲目重下。
- **测试账号**：没有通用固定口令。公开注册仅普通用户，商户/骑手/管理员由平台开通。ArkTS 仍有旧快捷登录入口，其固定测试凭据不代表线上可用；设备回归需专用私有账号，避免使用管理员失败桶。终轮 30 个 QA 账号已停用，会话已撤销。
- **接口约定与隐私**：业务和浏览接口需 JWT，401 清登录态；前端缓存 / 草稿 / 异步返回按账号与页面隔离，隐私同意落盘后才恢复数据。商户需门店权限，骑手只操作本人履约单，平台权限不下放用户端；抢单池脱敏、终态隐藏收货信息，必要联系信息仅有效履约时可用。公开认证入口包括登录 / 注册、邮箱取码、两类密码找回、刷新 / 退出；刷新需有效 refresh token，支付通知需验签。精确放行路径见 `WebConfig`。网页站内接口 / 上传资源走相对路径，兼容 `/takeout/`；手机端从 `API_CONFIG` 读取正式域名优先基址。

## 7. 开发规范（ArkTS 严格模式）

- `Stack` 不支持 `justifyContent/alignItems`，用 `alignContent(Alignment.X)`；`Row.alignItems` 用 `VerticalAlign`；`Alignment` 无 `CenterStart`
- **禁止空对象字面量 `{}`**：必须定义显式 class + 静态 `create()` 工厂（满足 arkts-no-untyped-obj-literals）
- **禁止向 `object` 类型参数传字面量**（如 `Web.javaScriptProxy`）：定义显式 interface 并经方法返回实例
- 表单弹窗：每个输入字段加标签（必填/选填）+ 业务示例 placeholder（如"请输入店铺名称，如：老王快餐店"）；顶部说明操作影响
- **渲染禁用 getter 计算属性**：ArkUI 对 getter 求值存在时序问题，会引发渲染崩溃（TypeError: Cannot read property length of undefined）；列表筛选结果应显式存入 `@State` 数组 + 内联 `Array.isArray` 防御
- ForEach 的 item 参数不能用于**嵌套闭包**（onClick 内引用会编译失败），需提取 @Builder 方法传参
- **`@CustomDialog` 必须声明 `controller?: CustomDialogController` 成员**（API 26 强校验，否则报 `10905211`）；弹窗数据用闭包（`() => this.state`）读取，避免构造参数被提前求值拿到旧值
- **可选属性窄化陷阱**：`arr[i].optProp !== undefined ? arr[i].optProp : 0` 在数组元素/嵌套对象上**不会窄化**，报 `number | undefined is not assignable`；统一改用 `??` 或先取到局部变量
- `import` 语句必须集中在文件顶部，混在声明之后虽合法但易被误改
- 所有 `.ps1` 脚本必须带 **UTF-8 BOM**（否则 PowerShell 5.1 按 ANSI 解析中文导致语法错误）
- 历史规格位于 `md/archive/specs/`，仅按需参考；开发与验收以当前需求及代码为准。
- **页面标题栏统一用 `components/PageHeader.ets`**（Wave 2/4 收敛）：用户端 15 页 + 管理端 12 页 + 商户端订单页已替换。约定：标题文字逐字保留（设备 UiTest 用 `ON.text(标题)` 断言）、返回键 `backId` 透传保回归、Admin 端传 `headerBgColor: MODULE_BG.ADMIN` + `actionColor: MODULE_COLOR.ADMIN`（刷新/新增等动作按钮）、Merchant 端传 `MODULE_BG.MERCHANT`/`MODULE_COLOR.MERCHANT`。**新增页面必须用 PageHeader，禁止手写 Row+Text header**；特殊复合栏（如 SearchPage 的「返回+搜索框+搜索按钮」）因 PageHeader 无内容插槽而保留原结构，但动作元素尽量加 `SoftPressModifier` 轻按反馈。管理端 header 左侧只放返回，不放退出（退出统一放页面底部，见 `#rider-logout` 教训）。

## 8. 经验教训（陷阱清单）

- 高德地图 SDK（@amap/amap_lbs_map3d）仅 arm64 → x86_64 模拟器安装失败（9568347），用 Web JS API 方案
- OpenHarmony zlib 正确模块是 `@ohos.zlib`（非 @ohos.file.zlib）；`compressFile` 的 options 必传但字段全可选，可用类型化空对象
- SQLite 相对路径需预先 `Files.createDirectories` 创建父目录（已迁 MySQL，勿回退）
- 优惠券/收藏等业务数据**禁止前端模拟**，服务端返回后必须以后端数据为准；默认分类图标仅作暂无数据占位
- 商户统计只统计已结算订单（status=4 且 escrow=1），区分"待结算"与"已结算营业额"
- 页面包含底部固定购物车或提交栏时，主体必须用 `Scroll`/`List` 承载，并用 `layoutWeight(1)` 分配顶部栏以下的剩余高度；滚动内容保留底部安全区，避免最后的评价、提交按钮被遮挡。
- 独立详情页的结构固定为“顶部导航 + 主体纵向 Scroll/List + 底部操作栏”，不要在父级 `Column` 中让详情组件使用 `height('100%')` 挤压兄弟组件。
- 评价入口不能因暂时不可评价而完全消失：可评价显示“去评价”，未完成订单显示“评价”并提示“完成订单后才能评价”，已评价显示已评价状态。
- 收货地址必须按账号闭环：结算页地址卡片点击进入地址列表，选择已有地址后返回并刷新；定位页确认位置必须调用后端新增地址接口取得真实 `id`，不能只写本地 `id=0`；登录成功或恢复登录态时同步当前账号地址，并优先恢复默认地址。
- 持久化归一化不能把合法的 `addressList` 直接重置为空数组；退出登录清除旧账号缓存后，下一次登录必须从数据库重新恢复地址，避免账号间串地址或反复要求定位。
- 所有用户端、商户端、管理端操作按钮都必须有可感知结果：前置条件不满足时主动 Toast，接口成功显示成功提示，接口失败显示后端错误或明确失败原因；不能只依靠 `enabled(false)` 或空 `return` 让用户感觉按钮无响应。下单前置校验要把店铺起送价、地址、余额等原因明确展示。

- **骑手参与配送的链路口径（改商户/骑手端前必读）**：完整链是 `商户接单(accept 1→2)` → `商户出餐(ready：只写 ready_time，status 保持 2)` → `订单进入待取餐池` → `骑手抢单(grab：写 rider_id，status 不变)` → `骑手取餐(pickup 2→3)` → `骑手送达(deliver 3→4 + 累加骑手单量/收入)`。
  - **商户端的「出餐」必须调 `ready`，绝不能调 `deliver`**。这是真实踩过的致命断链：商户页原先把「出餐」接成 `deliver`（2→3），而待取餐池的筛选是 `status = 2 AND ready_time <> '' AND rider_id = 0`，订单一旦被推到 3 就**永久跳过骑手**——抢单大厅永远空列表、抢单永远失败（报「手慢了」）。`ready` 这个 action 后端早就有，只是前端从没调过，而设备回归脚本是手工 `Invoke-Api ... /ready` 造的数据，于是「测试全绿但真机链路是死的」。`AdminOrderPage` 的「出餐」按钮是同一个 bug 的兄弟调用点，已一并改为 `ready`。
  - **`ready_time` 是订单进池的唯一开关**：写入它的只有 `OrderDao.markReady`（由商户端/管理端的 `ready` action 触发）。没有任何 seeder/定时任务会写它，所以「新库」不会自带可抢订单，这正常。
  - **被骑手接单后商户侧必须失效**：`OrderDao` 的 `merchantDeliver`/`merchantComplete` 都带 `AND rider_id = 0`，service 侧另有 `requireNoRider`；商户订单列表改用 `toViewWithRider` 以返回 `riderName`，前端据此把「出餐完成」换成「骑手 X 已接单」、把「确认送达」换成「骑手 X 配送中」，避免商户点了必然被后端拒绝的按钮却只看到「操作失败」。管理端走的是**独立分支** `AdminController → AdminService.orderFlow`（不复用 `OrderService.merchantFlow`），因此它的 `ready`/`deliver`/`complete` 分支必须各自维护；漏掉 `ready` 会直接报「不支持的订单操作：ready」，比原来更糟。
  - **出餐后必须给可见凭据**：`ready` 不改 status，商户列表若不显示任何变化，商户会以为没点上（刷新后更无从判断）。因此 `OrderView` 增加 `readyTime` 组件（由 `OrderDao.findReadyTime` 填充，仅在 `toViewWithRider` 路径），商户端/管理端在 `status=2 && readyTime != ''` 时显示「已出餐，等待骑手接单」（id `merchant-ready-<orderId>`）而不是按钮。**给前端用的字段必须是 record 组件**（见下方 Jackson 那条）。
  - **验证这类断链不能只写 mock 业务层测试**：`OrderServiceRiderFlowTest` 把 DAO 全 mock 掉，`markReady` 改成顺手把 status 推到 3 时它**依然全绿**。真正守住的有两层：

    - `scripts/rider-chain-regression.ps1`（真实链路层，**不需要设备**）：直接打后端 API 跑完整链（下单→支付→接单→出餐完成→进池→抢单→取餐→送达→骑手单量/收入），并额外断言「商户走 deliver 的订单**确实不在池子里**」以证明出餐必须用 ready。用法：起一个独立端口的后端（`mvn -f server/pom.xml spring-boot:run "-Dspring-boot.run.arguments=--server.port=9001"`，避免动用户正在跑的 8087），再 `powershell -ExecutionPolicy Bypass -File scripts/rider-chain-regression.ps1 -ApiBase http://127.0.0.1:9001`。**`grab` 是 POST，`pickup`/`deliver` 是 PUT**，方法写错会得到 `HttpRequestMethodNotSupportedException` 被全局处理器包装成 500「服务器内部错误」，极易误判成业务故障。

- **渲染路径里禁止用 `AppStorage.get()` 取值（必须用被观察的成员）**：`AppStorage.get()` 直接读全局存储，**绕过 ArkUI 的状态观察**，组件不会与它建立依赖，值变了界面也不刷新。店铺详情页商品行数量就是两个缺陷叠加：`getQty()` 读 `AppStorage.get('cartItems')`，且 ForEach key 用稳定的 `goods.id` —— 表现为点「+」后数字不显示/不更新（设备实测：连点两次仍显示 1，断言报 `expect 1 equals 2`）。修法：`getQty()` 改读被观察的 `this.cartItems`（`@StorageLink`），并把 `goodsRenderVersion` 拼进 ForEach key。**判断标准：凡是出现在 `build()` / `@Builder` 里的取值，都必须来自 `@State`/`@Prop`/`@Link`/`@StorageLink` 成员**；`AppStorage.get()` 只允许出现在命令路径（事件回调、数据修复）里。
- **店铺照片链路（商户上传 → 用户端展示）**：stores.image 存上传接口返回的相对地址（/uploads/yyyyMMdd/xxx.png，列宽 255）。写入侧只有两处：StoreService.createStore(..., image)（新建）与 StorePatch.image（编辑，null=不修改）。读取侧用户端统一用 merchantImageSource(store.image)：有照片显示照片，没有则**保留首字母色块**（店铺列表/卡片不能让所有店都显示同一张默认图，否则顾客分不清店），只有店铺详情页顶部大图才回退 DEFAULT_MERCHANT_IMAGE。商户端新建/编辑两个表单都有「店铺照片」上传项，商户店铺列表也显示缩略图。配送半径已打通：`MerchantStoreRequest/Patch` 带 `deliveryRadius`，两个表单都有「配送半径（米）」输入，编辑默认回传当前值（旧代码不传该字段 → 服务端按 0 落库，保存店铺即静默清零）。**半径语义：商户填了按商户的，没填（0）按默认 30 公里`Store.DEFAULT_DELIVERY_RADIUS_METERS`，不再表示"不限"**；判定收口在 `Store.canDeliver`，消费点：`OrderService.createOrder` 超距直接拒绝下单（文案就是「超距，请重新选择地点」）、`StoreService.recommendedStores` 过滤附近推荐、`StoreView.deliverable` 给前端列表过滤。
- **距离必须由「用户定位 + 门店坐标」算出，算不出就是「未知距离」**：`Store.withDistance(lat,lon)` 在任一侧缺坐标时返回 `Store.UNKNOWN_DISTANCE`（旧实现沿用库里 `distance` 字符串，于是没有坐标的店会被当成 0.2km 的附近店铺，武汉的店在沈阳用户端照常出现在「附近推荐」）。筛选靠 `parseDistance` 解析数字，`未知距离` 不带数字 → 自然被排除。**两个必须同时成立的坑**：① `StoreService.recommendedStores` 的回源链路里，`.map(store -> store.withDistance(...))` 之后必须用 `toView(store, latitude, longitude)`，写成 `toView(store)`（=内部 `toView(store,null,null)`）会用 null 坐标把刚算好的距离覆盖成未知距离——这个 bug 让主页「附近推荐」一直显示库里旧字符串；② 种子/存量店铺必须有坐标，`DataSeeder.ensureStoreCoordinates()` 按**南宁**基准点（22.8177/108.3665）给 `latitude/longitude IS NULL` **或仍停在旧武汉环（30.5~30.7 / 114.2~114.4）** 的店铺幂等补点（约 0.2~1.2km）——改基准点后必须同时重落旧坐标，否则存量店仍留在旧城市；判定用"旧坐标环"而不是"有没有地址"，避免误伤商户用地图选过点的门店。契约由 `StoreDistanceTest`（模型层）与 `StoreRecommendedDistanceTest`（推荐链路，含 cache 透传 stub）钉住，两个都用例做过「先红后绿」。
- **派单半径是「商家 ∩ 骑手」两个圆（改骑手/商户半径前必读）**：`stores.delivery_radius`（商户最远配送半径，默认 30 公里）+ `riders.delivery_radius`（骑手配送半径，默认 25 公里）+ `riders.latitude/longitude/location_address`（骑手接单位置＝抢单圆心）。**配单判定分两层**：① 用户地址到门店 ≤ 商户半径——`OrderService.createOrder` 直接拒绝下单（「超距，请重新选择地点」）；② 骑手接单位置到门店 ≤ 骑手半径——`OrderService.riderPool(riderId)` 过滤抢单池、`riderGrab` 再判一次（否则拿订单 id 直接调接口就能绕开范围）。骑手未设置接单位置时池子恒空并在抢单大厅给出提示；`DataSeeder.ensureRiderDeliveryRange()` 会把没位置的骑手补到南宁种子基准点，保证新库/老库开箱可抢。**半径单位统一：库里存米，界面填公里**（骑手 25 默认 / 商户 30 默认）；<5 公里弹「不推荐太小哦，可能会无单可抢，您真的要选择吗？」，>50 公里弹「可能会接到很远的单」——都是**前端确认框而非硬拒绝**，服务端只挡 1~200 公里的明显非法值（`Rider/Store.MIN|MAX_DELIVERY_RADIUS_METERS`）。骑手/商户端两处半径接口分别是 `PUT /api/rider/range/radius`、`PUT /api/rider/range/location`、商户沿用 `PUT /api/merchant/stores/{id}` 的 `deliveryRadius`。**骑手定位口径**：接单时定位一次（`RiderOrderPoolPage` 抢单成功后 `reportRiderLocationRemote()`），**配送途中实时定位**（`RiderOrdersPage` 名下有 status=3 订单时每 30 秒上报一次，无配送单/离开页面即停）；上报地址必须是**逆地理编码结果**，不要写死"我的当前位置"（`AppStorageManager.reportRiderLocationRemote` 统一做：权限→取点→`reverseGeocodePosition`→PUT）。契约由 `OrderServiceRiderFlowTest` 的 `poolOnlyContainsOrdersWithinRiderRadius` / `poolIsEmptyWhenRiderHasNoLocation` / `grabIsRejectedForOrderOutsideRiderRadius` 钉住。
- **左上角不要放"退出登录"**：骑手中心原先把退出登录放在标题栏左侧，与全站其它页面的「‹ 返回」同一位置（`[50,183][1105,234]`）。设备实测：从地图选点返回后按习惯点左上角 (107,208) 会**直接退出到登录页**（用户报的就是这个）。现在退出登录挪到页面底部（`#rider-logout`）并加二次确认；新增页面时标题栏左侧要么放返回、要么留白，别放破坏性操作。
- **系统逆地理编码要拼去重前缀**：`geoLocationManager.getAddressesFromLocation` 有时把完整地址塞进 `roadName/premises`，逐段首尾相接会得到「中国辽宁省沈阳市沈河区辽宁省沈阳市沈河区杏林街…」。`LocationService` 的 `overlapRemainder`/`joinAddressParts` 已统一取"已有串后缀 ∩ 新片段前缀"的最长重叠再拼接，地图选点与 GPS 上报的地址都走它。
- **日志一律带当前页面标识，点击埋点只做一处**：`AppLogger.log()` 给每条日志拼 `[page=<页名>]`；页面标识由 `UiNavigation` 注册的解析器在每次写日志时实时读 `UIContext.getRouter().getState().name`，因此 push / back / replaceUrl / 系统返回键都准确（拿不到时回退 `setCurrentPage()` 的最近值，冷启动早期是 `unknown`；短页名统一成 `Index`/`CartPage` 这种路由状态格式，不要写成 `pages/Xxx`）。用户点击由 `entry/src/main/ets/common/ClickLogger.ets` 用 `UIObserver.on('willClick')` 全局监听（在 `EntryAbility` 内容加载完成后注册），日志形如 `[Click][page=CartPage] 用户点击 cart-checkout x=.. y=..`，组件 id 取自 `FrameNode.getInspectorInfo()`。**新增按钮不必写点击日志，也不要在页面里自己拼页面名**；记录非点击操作照旧 `logInfo(tag, msg)` 即可。注意 `ClickEvent` 的坐标字段是 `displayX/displayY`（没有 `displayAreaX/displayAreaY`）。
- **验证 UI 刷新类缺陷必须「先让它红一次」**：这类 bug 的根因是「状态变了但视图不重建」，光看修复后变绿不能证明用例有效（很可能压根没走到那条路径）。做法是临时回滚修复、重跑用例确认**必然失败**，再恢复修复确认**通过**。本仓库 `StoreDetailCart` 用例就是这么定标的：回滚修复 → `Tests run: 1, Failure: 1`（`expect 1 equals 2`），恢复修复 → `Pass: 1`。
- **Jackson 序列化 record 只认「组件」，额外写的 `xxxYyy()` 方法不会出现在 JSON 里**：钱包银行卡原本把掩码写成 `public String cardNoMasked()`（不满足 `getX()`/`isX()` 命名，也不是 record 组件），于是接口里**根本没有这个字段**，前端 `Text(card.cardNoMasked)` 拿到 `undefined` → 银行卡号整行空白（设备实测 text 节点从「默认」直接跳到下一行说明文字）。规则：**要给前端用的字段必须是 record 组件**（在构造参数里），派生值在 DAO/构造处算好传进来；不要指望在 record 里加个方法就能被序列化。
- **容器的 `getText()` 返回空串**：`ON.id()` 打在 `Row`/`Column` 这类容器上时能查到节点，但 `getText()` 为空（容器自身没有文本）。断言卡片内容要查**卡片内部的文本节点**（`ON.text('招商银行')`），或把 id 直接打在有文本的 `Text` 上。
- **横向 `Scroll` 里的 `Text` 用文案定位，不要用 id**：店铺详情页的分类芯片 `.id('goods-cat-<名字>')` 在设备上 `ON.id()` **查不到**（横向 Scroll 内的 Text 节点不参与 id 匹配），但 `ON.text('招牌热销')` 能稳定拿到。同理 `.id()` 里的数量（`goods-count-<n>`）比解析被省略号截断的文本更可靠。
- **店铺详情页分类芯片的空转根因在种子数据**：芯片走的是美团式「店内分类」（`categories.type='MERCHANT'` + `goods.merchant_category_id`），链路早已就绪但种子数据从未建过 MERCHANT 分类、1200 个商品的 `merchant_category_id` 全为 0 → 芯片只剩「全部 + 该店唯一平台分类」，两者商品列表完全相同，点分类「看起来没反应」。由 `DataSeeder.ensureStoreMerchantCategories()` 幂等补齐。这条修复本身踩了三个坑，都已在代码注释里锁住：
  - **判定条件不能只看「有没有分类」**：商户可能自己建过分类但商品没挂上去（本仓库商户 3 就是），只看分类存在与否会让这类店铺继续空转。改用「该店铺使用的分类数 < 2 才重新分组」——这类店铺本来就没有可切换的分区，重排不损失任何功能；而使用 >=2 个分类的店铺（含商户自己整理的）一律不动。
  - **分配必须「按店铺」轮转，不能按 `is_special` 全局一刀切**：追加店铺 31~40 各 6 件商品且**全是招牌**，一刀切会把整店商品全塞进「招牌热销」一个分类，芯片仍只有一个非空项 → 点了依旧没反应。做法是按店铺取商品、按 id 顺序确定性轮转（招牌→招牌热销，非招牌在其余分类间轮转；整店全招牌时在全部分类间轮转）。
  - **「只补 `merchant_category_id=0` 的行」修不回已经分错的数据**：第一版把 31~40 号店全塞进了一个分类，这些行已不再是 0，只补 0 的做法永远够不到它们。所以重新分组要按「使用的分类数 < 2」触发，并且**必须确定性**（结果只取决于商品 id 顺序）才能保持幂等；分类本身从不删除。
  - **默认分类要按「名字」补齐，不能按位置推断**：商户 3 自建的「你好」占据第一个位置时，按 `defaults[i]` 的位置对应会张冠李戴，而且永远建不出「招牌热销」（当年的 bug：`existingIds` 已有 4 条，补建循环一次都没进）。招牌商品的落点要**显式查 `name='招牌热销'` 的分类 id**，不要用「分类列表第 0 个」。
  - 验收口径是数据而非 UI：`SELECT COUNT(*) FROM (SELECT s.id FROM goods g JOIN stores s ON s.id=g.store_id GROUP BY s.id HAVING COUNT(DISTINCT g.merchant_category_id)<2) t` 必须为 0（两份库都要查：本机 3306 与 compose 容器 3310，两者数据集不同——容器是 40 家店各 30 件商品的均匀数据，本机是 41 家店、商品数 6~30 不等的累积数据，**「整店全招牌」这种形态只在后者出现**，所以不能只验一份库就下结论）。
- **`findComponents` 未命中同样返回 `null`（不是空数组）**，直接 `.length` 会抛 `Cannot read property length of null`；长页面里的目标节点即使能被 `findComponent` 找到，也可能在屏幕外且 `getBounds()` 返回整屏 `[0,117][1320,2232]`，拿它算中心点点击等于点空 —— 用 `UiTestHelper.scrollUntilVisible`（先直接查一次，未命中再滚回顶部逐屏下滑，只接受边界明显小于整屏的节点）。
- **设备实测脚本集合**：`scripts/device-uitest.ps1`（通用单类运行器：`-Class X -GuestClean -GrantLocation -Build`）、`device-checkout-regression.ps1`（结算负路径 + 待付款订单）、`device-review-regression.ps1`（图文评价上传/渲染/预览）、`device-merchant-regression.ps1`（商户订单流转 + 收入统计）、`device-role-regression.ps1`（骑手抢单/取餐/送达 + 管理端冒烟）、`ui-dump.ps1`（结构化解析 dumpLayout）、**`rider-chain-regression.ps1`（骑手配送真实链路，纯 API、不需要设备，见第 8 节骑手链路口径）**。

### Redis 缓存与领域事件（2025 落地时踩的坑）

- **瞬时故障绝不能升级为数据丢失**：Outbox 中继最初把 `retry_count >= max-retry` 当作「跳过」条件，实测停 Redis 下单后 `retry_count` 触顶 10，Redis 恢复后该事件**被永久跳过、再也不投递**。事件已持久化在数据库，重试几乎零成本，正确做法是**永不放弃投递**，`retry_count` 只用于告警。
- **不要为了「快速失败」关掉 Lettuce 的 `autoReconnect`**：`autoReconnect(false)` 会让客户端在 Redis 重启后永久停留在 `Currently not connected. Commands are rejected.`，Outbox 中继再也无法投递。缓存的快速失败只需靠**短超时**（`timeout/connect-timeout: 500ms`）实现，必须保留自动重连。这两条是配套的：只看单条都会做出错误取舍。
- **Lettuce 默认重试会把请求拖到 ~10 秒**：Redis 不可用时一次读请求实测约 10071ms；把 `timeout`/`connect-timeout` 收紧到 500ms 后降到约 565ms，且请求全部成功（降级回源）。
- **`XREADGROUP` 在 Stream 不存在时报 `NOGROUP`**：Stream 只在第一条消息写入后才存在，而消费者启动即开始读 → 首条事件到来前每 2 秒刷一条警告栈，淹没真实故障。解法是在消费者启动时**主动创建 Stream 与消费组**（写一条占位再删掉，或用 `MKSTREAM`），实测初始化后再无 `NOGROUP`。
- **缓存失效范围要按业务语义定，不能用注解一把梭**：库存/秒杀名额参与「列表、榜单、秒杀专区」的展示筛选，所以下单扣库存、取消回滚、退款、超时取消都必须失效 `STOCK_DEPENDENT_PATTERNS`，否则会出现「下完单列表还显示有货」。批量失效用 `SCAN` 游标，**禁用 `KEYS`**。
- **回源互斥锁必须带等待上限并最终降级**：抢不到锁的请求不能无限自旋，等不到就回源数据库——**可用性优先于「只查一次库」**，锁只是削峰不是门禁。
- **不要用 Redis 锁替换数据库条件更新来防超卖**：现有 `WHERE sold + ? <= quota` / `WHERE stock >= ?` 在本地事务内已保证不超卖；Redis 锁覆盖不到数据库写入，Redis 挂掉时反而更弱。异步化同理——`createOrder` 保持同步事务，异步只覆盖提交后的通知类动作（真正的异步下单需要 saga + 补偿）。
- **事件必须在条件更新成功之后发布**：`markPaid`/`cancelPending`/退款状态更新都是条件更新，只有在返回 true 之后才发事件，否则会产生「假支付」「假退款」事件。
- **Docker 的 JRE 镜像没有 `curl`/`wget`**：容器健康检查不能用 curl。本工程改为编译一个极简 TCP 探测类（`server/takeout-app/docker/healthcheck.java`），用 `java -cp /app healthcheck 127.0.0.1 8087` 做健康检查。
- **`docker-compose` 的 MySQL 端口要避开本机 3306**：本机有 MySQL84 服务，compose 映射到宿主 **3310**；`application.yml` 的数据源必须用 `${TAKEOUT_DB_HOST}`/`${TAKEOUT_DB_PORT}` 占位，否则容器内硬编码 `localhost:3310` 会连不上 MySQL 而 crash-loop。
- **PowerShell 5.1 用 `powershell` 而不是 `pwsh`**（本机无 pwsh）；且用 `Select-String` 过滤 `mvn` 输出会让 `$LASTEXITCODE` 失真（常显示为 1），判定 Maven 成功要看 `BUILD SUCCESSFUL`。
- **GitHub 的 Contributors 由「提交邮箱 → 账号已验证邮箱」决定，而且列表是异步缓存，改完不会立刻生效**。两个独立坑都在本仓库踩过：
  - ① 用未关联到账号的邮箱提交（本仓库曾有 221 个提交用 Gitee 的 `...@user.noreply.gitee.com`）→ GitHub 把它算成**另一个 Contributor**。修法是重写提交邮箱：`git filter-branch -f --env-filter "GIT_AUTHOR_EMAIL=...; export GIT_AUTHOR_EMAIL; GIT_COMMITTER_EMAIL=...; export GIT_COMMITTER_EMAIL" -- master`（只改 email，保留姓名/时间/信息），再 `push --force-with-lease`。**改完必须自证内容零变化**：比对重写前后的 `git rev-parse "HEAD^{tree}"`（本仓库两次都是 `5ec5886098c18a5d6d8c921e7f2234e3c8c60ed9`）并确认 `git diff <旧HEAD> <新HEAD>` 输出为空。注意 filter-branch **要求工作区干净**，有未提交改动时先 `git stash push <file>`（只 stash 那一个文件，别用 `-u`）。
  - ② 已推上去的 AI 署名（`Co-Authored-By: Claude`）即使随后 amend + force push 把该提交删掉，Contributors 里仍可能长期留着 "Claude" 条目——GitHub 不会立即重算贡献者缓存（实测超过 1 天仍在；通常需数小时至 24h，顽固时只能找 Support 清除）。**所以 AI 署名一次都不要推**。
  - 另：`refs/original/` + reflog 会留着旧对象，彻底清理用 `git update-ref -d`（逐个删 `refs/original/*`）+ `git reflog expire --expire=now --all` + `git gc --prune=now`；重写后哈希全变，其他机器上的旧克隆必须重新 clone。

## 11. 边界条件口径与待办

> 本节起源于 2026-09 边界条件专项，已按 2026-10-26 当前源码修正券资格、地址并发与退款规则；下方注明日期的历史实测仍只代表当时版本。

**已确定的口径**（避免再次"修回去"）：

- **起送价以服务端为唯一权威**：多店结算时服务端**按店逐个**校验（只算该店商品）；结算页**不再做**"所有店合计 vs 最大起送价"的前置拦截——两者口径不一致会给出自相矛盾的提示。
- **券后实付必须为正**：以含配送、计入所有实际优惠后的 `payAmount > 0` 为准，零 / 负实付拒绝且差额不退。单店商品 ¥10、配送 ¥3、使用 ¥10 券可支付 ¥3；免配送且券覆盖全部应付则不可用。客户端推荐是预估，不能替代营销叠加后的服务端金额。
- **支付严格按 payDeadline**：超时后由 `OrderTimeoutJob` 扫描取消（`create_time < deadline`，无宽限期）。`payOrder` 在扣款前也显式判定——`payDeadline` 的 epochMs 已过直接抛「订单已超过支付时限，请重新下单」，不再出现「倒计时归零了还能支付成功直至扫描兜底」的窗口。
- **退款终态就是 status=6 + escrow=2**：管理端同意退款后订单**停留在 6**（不再流转到 5），前端按 status + escrow 联合判断文案。这是状态机终态，不是"卡住"。
- **资金三件套**：扣款用条件更新 `deductBalance`（余额不足返回 false）、退款/结算用原子自增 `addBalance`；**禁止**再出现"读余额→改→整值写回"（`UserDao.updateBalance` 已删除）。
- **状态流转一律条件更新**：`updateStatusFrom(from,to)` / `merchantDeliver` / `merchantComplete` / `markRefunding`，rowcount=0 必须抛错整单回滚，不得先查后改。
- **骑手单量与收入写在 `OrderService.riderDeliver` 事务内**（`RiderService.recordDelivered` 已删除），且骑手 `status != 1` 时禁止抢单/取餐/送达。
- **事件去重键在处理成功后才写**：先写会让"处理失败但未 ACK"的事件在重读时被自己的键判成重复而永久丢弃。
- **文本列宽在服务层就挡**：所有用户可输入的文本（商品/店铺/分类/Banner/公告/备注/评价/退款原因/地址）都要在写库前按 `schema.sql` 的列宽给出可读提示，不要让 MySQL 列宽溢出变成 500。已覆盖：用户名 64、店铺名 128、店铺公告/地址 512、配送时间 32、商品名 128、商品描述 512、商品图片 255、商品标签 32、规格名 64、分类名 32、Banner 标题 64/副标题 128/图 255/跳转参数 128、公告标题 128/内容 1024、订单备注 255、评价内容 512、退款原因 255、地址姓名 64/详情 255。
