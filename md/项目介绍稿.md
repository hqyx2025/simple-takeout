# 简单外卖项目介绍稿

适用场景：毕业设计答辩、项目演示、作品介绍。功能说明更新至 2026 年 10 月 28 日；本轮业务、最终验证日志与发布占位见 [10/28 会话归档](archive/会话记录-2026-10-28-业务闭环与发布.md)。**当前部署状态：待本次发布核验**；release、commit、GitHub CI 与线上结果由 main 核验后补。

大家好，今天向大家介绍的项目叫“简单外卖”，它是一套基于 HarmonyOS NEXT 开发的外卖点餐系统。

这个项目以日常外卖场景为背景，将用户点餐、商户出餐、骑手配送和平台管理连接起来。项目重点是围绕同一笔订单，让不同角色完成各自的操作，并处理支付、库存、优惠券、退款和结算之间的关系。

接下来，我从功能、业务流程和技术实现三个方面介绍。

首先是系统功能。

项目包含用户、商户、骑手和平台管理员四种角色，不同角色拥有对应的操作入口和访问权限。

用户端支持浏览和搜索店铺、查看商品、选择规格、加入购物车，以及领取优惠券和参与限时秒杀。搜索会区分没有结果和加载失败，失败时保留关键词。收货地址分开填写地图位置与楼层门牌，购物车单项删除可在 6 秒内撤销，整店清空前会明确确认。

结算会预估优惠并解释券不可用的原因，主动“不使用”选择和备注在往返页面时保留。服务端固定按最优折扣、本店首笔成功支付的新客立减、优惠券的顺序计算，赠品门槛用折扣后的商品金额。同值活动按编号确定，订单保存定价快照；新客资格下单时持久占用，未付款取消释放，付款后用掉，不因后续退款再次成为新客。多店部分成功只重试失败店铺，结果未知时核对原请求，最终金额以服务端为准。

商户端维护店铺、分类、规格、库存与上下架。待接单可选择无法接单的原因，缺货核对具体商品或规格并停售，按责任退款和退回仍有效券。制作、配送后取消不恢复可售库存。商家可接单、出餐、按订单快照进行自配送、回复评价、为售后举证，查看真实近 30 天销量、净结算、售后扣款与待偿账目。商品销量按真实订单行数量、门店销量按已支付订单数，排除取消和全额退款，历史 seed 销量不进入榜单。

骑手端提供上线、下线、待取餐池和抢单。订单创建时保存骑手配送或商家自配送快照，门店之后改设置只影响未来订单。骑手模式按出餐、抢单、取餐、送达推进，自配送不进入骑手池。抢单前收货信息脱敏，履约时可复制地址、拨号，结束后隐藏隐私。无人接单、联系不上、地址问题或餐损可以持久上报，平台分页核对后选择取餐前改派、继续或取消。系统不把文字地址搜索当作精确导航，也不编造送达倒计时。

平台管理端负责店铺审核、商品监管、账号、内容、订单、经营统计及配送异常处置。售后支持用户图片证据与商家举证，仍只由管理员裁决；同意前核对金额和原渠道后果，拒绝填写用户可见理由，被驳回后 48 小时内可申诉一次。App 和 Web 以服务端 capabilities 为动作权威，空或畸形能力禁操作，服务端仍独立校验角色和订单状态。

商户和管理员在网页端「采购与库存」维护供应商、非食材耗材、采购、分批收货、台账、盘点报损、付款和经营对账。物料与供应商支持分页搜索，关联筛选随翻页保留。结果未知的写请求按账号与门店保存在浏览器会话，重进页面也要核对原内容、使用原编号重试。付款凭证纠错、错误付款冲销、实际供应商退款均追加审计，不覆盖历史；净已付与有效收货应付保持核对。这部分不从应用钱包付款，也没有食材配方或按销量自动扣料。

下面用一笔订单说明系统的核心流程。

用户选择商品规格、数量、地址和优惠券后提交订单，服务端会重新校验商品价格、库存及优惠条件，并生成待付款订单。此时会占用相应库存、秒杀名额和优惠券；如果用户超过 15 分钟没有付款，系统会自动取消订单并释放这些占用。

支付成功后商户接单、出餐，再由订单快照指定的骑手或商家完成配送，用户确认收货。系统区分送达和已完成，默认送达 24 小时自动结算，与 48 小时售后期限分开。用户直接取消限待付款或待接单，制作与配送转平台处理。未支付取消释放资源和新客占用；已支付用户取消不返券，商家或平台责任取消退回仍有效券。自取和预约暂未开放。

送达后 48 小时内，即使已经确认收货、结算或评价，仍可在剩余实付范围内申请部分或全额退款，并提交图片证据。部分退款保留原结算阶段，累计全额退款才进入全退终态，已送达餐品不回可售库存。结算后商户承担不超过原净结算部分，先扣可用余额，不足记待偿，后续结算按 FIFO 抵扣，钱包不变负；骑手收入不扣回，差额记录平台售后成本。收入记在实际结算日，结算后退款在退款日扣回商户承担部分。

目前项目支持余额支付和支付宝沙箱支付，退款按原渠道处理。沙箱用于验证对接流程，正式外部支付和退款仍需专项联调。

在技术实现上，移动端使用 ArkTS 和 ArkUI，面向 HarmonyOS NEXT API 26 开发；后端使用 Java 25 和 Spring Boot，MySQL 保存业务数据，Redis 承担热点数据缓存和领域事件传递。项目还提供网页体验入口，与鸿蒙客户端共用服务端账号、购物车、地址和订单数据。

技术设计中，我想重点介绍四个方面。

第一是交易一致性。下单、库存、付款和结算通过本地事务、唯一约束、行锁与条件更新保护。外部退款不能随数据库回滚，所以调用渠道前先用 REQUIRES_NEW 在独立表保存稳定退款号和退款意图；渠道确认记 CONFIRMED，本地业务提交后记 DONE。渠道成功而本地台账或事件失败时，后台每轮有界恢复，沿用原编号与取消责任信息；已有渠道意图的售后不能改为驳回，取消恢复期间不能继续履约。余额退款仍在本地事务完成。

第二是缓存与故障降级。分类、店铺、商品和公告等浏览数据使用 Redis 缓存，减少重复查询数据库。缓存设计包含空值占位和过期时间随机化等处理；当缓存服务不可用时，浏览查询可以回源数据库，保持基本访问能力。

第三是服务边界和业务事件的可靠传递。Gateway 将采购接口路由到独立 ERP，ERP 使用独立数据库；账号、订单、菜品与资金事实仍属于交易主服务。内部调用有明确超时，写操作不盲目重试。事务性 Outbox 将订单事件与业务数据一同保存，再由后台任务投递到 ERP 收件箱和 Redis Stream；失败时持久重试，消费端按事件号幂等，管理端可以查看积压并人工重投。ERP 停机不会回滚已提交的订单，但通知会延迟；权限服务不可用时 ERP 拒绝业务操作。

第四是通过实测管理性能。项目提供有上限的负载工具、GC 日志、线程快照和按需 JFR。2026 年 10 月 27 日，本机两个 App 各限制 1 CPU、768 MiB，在 20 秒混合负载中完成 2200 次请求，吞吐 109.56 RPS，P95 61.32 ms、P99 88.85 ms，错误和拒绝为零，库存、余额和支付台账核对通过。这是 10/27 历史本机短测，不是本轮压测或线上容量，也不能排除长期泄漏；当时保留 JVM 自动选择的 GC。

在使用体验方面，页面采用暖白背景、深棕文字和陶橙强调色，受影响页面同步检查深色与关键操作热区。六批改造重点是减少重复输入、显示真实状态、预防误操作，并提供失败后的恢复入口。相关 API、网页和模拟器链路已经分批验证；全页面大字号、物理真机和无障碍验收仍需继续进行。部署使用 Docker Compose，网页通过域名的 /takeout/ 路径访问，手机端与网页共用服务端数据；未签名 debug HAP 不代表应用商店发布。

“简单外卖”的主要价值，是把鸿蒙应用开发与外卖业务流程结合起来，覆盖从商品浏览到订单履约、售后和结算的主要环节，也将权限隔离、并发控制和故障处理纳入实现。它目前定位于毕业设计和学习展示项目，可以用于演示业务流程和技术方案。
