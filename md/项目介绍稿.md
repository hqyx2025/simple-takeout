# 简单外卖项目介绍稿

适用场景：毕业设计答辩、项目演示、作品介绍。正常语速约 7–8 分钟。功能说明更新至 2026 年 10 月 26 日；服务器版本为 `ux-20261026-1950-sync-r2`，运行源码为 `fc37a14`，发布核验时间为 2026-10-26 20:30:14 +0800。

大家好，今天向大家介绍的项目叫“简单外卖”，它是一套基于 HarmonyOS NEXT 开发的外卖点餐系统。

这个项目以日常外卖场景为背景，将用户点餐、商户出餐、骑手配送和平台管理连接起来。项目重点是围绕同一笔订单，让不同角色完成各自的操作，并处理支付、库存、优惠券、退款和结算之间的关系。

接下来，我从功能、业务流程和技术实现三个方面介绍。

首先是系统功能。

项目包含用户、商户、骑手和平台管理员四种角色，不同角色拥有对应的操作入口和访问权限。

用户端支持浏览和搜索店铺、查看商品、选择规格、加入购物车，以及领取优惠券和参与限时秒杀。搜索会区分没有结果和加载失败，失败时保留关键词。收货地址分开填写地图位置与楼层门牌，购物车单项删除可在 6 秒内撤销，整店清空前会明确确认。

结算会按当前商品和优惠券预估推荐，并解释券不可用的原因；用户主动选择“不使用”后，往返地址管理也会保留选择和备注。多店订单分别反馈建单结果，只重试失败店铺；网络中断、结果不确定时沿用原请求核对，避免重复下单。营销叠加与实际应付金额仍以服务端计算为准。

商户端主要处理店铺经营，包括维护资料、管理分类和规格、调整库存及上下架商品。待接单订单可以选择无法接单的原因；缺货时核对订单内的具体商品或规格并停售，按规则退款和恢复有效优惠券。用户看到可信的拒单原因，商家内部备注不会公开。商户还可以接单、完成出餐、回复评价，并查看已结算营业额和待结算金额。

骑手端提供上线、下线、查看待取餐订单和抢单功能。抢单前收货信息脱敏，接单后按“待取餐、配送中”完成履约，可复制完整地址或打开系统拨号；门店有有效坐标时可打开地图。标记送达前要确认已经交付，结束后隐藏收货信息。系统不把文字地址搜索当作精确导航，也不编造送达倒计时。

平台管理端负责店铺审核、商品监管、账号管理、轮播公告、全平台订单和经营统计。订单与退款使用服务端分页和筛选；退款默认查看待审批，同意前确认订单、金额和原渠道退款后果，拒绝必须填写用户能看到的理由。这样，四种角色围绕真实业务数据协同工作。

下面用一笔订单说明系统的核心流程。

用户选择商品规格、数量、地址和优惠券后提交订单，服务端会重新校验商品价格、库存及优惠条件，并生成待付款订单。此时会占用相应库存、秒杀名额和优惠券；如果用户超过 15 分钟没有付款，系统会自动取消订单并释放这些占用。

支付成功后，商户接单、出餐，骑手取餐、配送并标记送达，用户再确认收货。系统区分“已送达”和“已完成”：送达后可能仍待确认、待结算，确认收货前会说明结算后果。用户只能直接取消待付款或待商家接单订单，制作和配送阶段转平台处理；新结算暂只开放立即外卖配送，自取和预约需补齐履约规则后再开放。

符合现有条件的订单可申请退款。用户选择原因、补充说明后提交，可再次进入查看申请编号、金额、处理时间和拒绝理由；失败不清空输入，同一次重试不生成新申请。已送达餐品退款不会恢复成可售库存。确认或评价后的售后政策、部分退款和图片证据工单仍需补齐。

目前项目支持余额支付和支付宝沙箱支付，退款按原渠道处理。沙箱用于验证对接流程，正式外部支付和退款仍需专项联调。

在技术实现上，移动端使用 ArkTS 和 ArkUI，面向 HarmonyOS NEXT API 26 开发；后端使用 Java 25 和 Spring Boot，MySQL 保存业务数据，Redis 承担热点数据缓存和领域事件传递。项目还提供网页体验入口，与鸿蒙客户端共用服务端账号、购物车、地址和订单数据。

技术设计中，我想重点介绍三个方面。

第一是并发情况下的数据一致性。用户连续点击下单、多个用户同时购买最后一件商品，或者退款与确认收货同时发生，都可能造成业务冲突。项目通过数据库事务、唯一约束和带状态条件的更新，限制重复下单、库存超卖和重复结算等问题。订单金额和业务状态由服务端计算、校验，客户端负责展示和提交操作。

第二是缓存与故障降级。分类、店铺、商品和公告等浏览数据使用 Redis 缓存，减少重复查询数据库。缓存设计包含空值占位和过期时间随机化等处理；当缓存服务不可用时，浏览查询可以回源数据库，保持基本访问能力。

第三是业务事件的可靠传递。项目采用事务性 Outbox，将订单相关事件与业务数据放在同一数据库事务中保存，再由后台任务投递到 Redis Stream。消费端进行去重处理，让部分后续动作能够异步执行，同时降低业务已经提交、事件却没有记录的风险。

在使用体验方面，页面采用暖白背景、深棕文字和陶橙强调色，受影响页面同步检查深色与关键操作热区。六批改造重点是减少重复输入、显示真实状态、预防误操作，并提供失败后的恢复入口。相关 API、网页和模拟器链路已经分批验证；全页面大字号、物理真机和无障碍验收仍需继续进行。部署使用 Docker Compose，网页通过域名的 /takeout/ 路径访问，手机端与网页共用服务端数据；未签名 debug HAP 不代表应用商店发布。

“简单外卖”的主要价值，是把鸿蒙应用开发与外卖业务流程结合起来，覆盖从商品浏览到订单履约、售后和结算的主要环节，也将权限隔离、并发控制和故障处理纳入实现。它目前定位于毕业设计和学习展示项目，可以用于演示业务流程和技术方案。
