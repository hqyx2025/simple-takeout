## 三、1000 人高并发场景分析

### 3.1 并发安全机制总览

| 场景 | 机制 | SQL | 失败处理 |
| --- | --- | --- | --- |
| 库存超卖 | 乐观锁条件更新 | `WHERE stock >= ? AND status = 1` | 抛异常回滚事务 |
| 规格库存超卖 | 乐观锁条件更新 | `WHERE stock >= ? AND status = 1` | 同上 |
| 秒杀名额超卖 | 条件更新 | `WHERE sold + ? <= quota` | 名额用完回退原价 |
| 秒杀重复下单（一人一单） | 唯一键 + INSERT IGNORE | `seckill_orders` UNIQUE(user_id, seckill_id) | 抛「每人限购一次」回滚事务 |
| 优惠券重复核销 | 条件更新 | `WHERE status = 0` | 抛异常回滚事务 |
| 余额并发扣款 | 原子条件更新 | `WHERE balance >= ?` | 抛异常回滚 markPaid |
| 余额并发入账 | 原子自增 | `balance = balance + ?` | 无覆盖写 |
| 确认收货 vs 申请退款 | escrow 条件更新 | `WHERE escrow_status = 0` | 只一方成功 |
| 骑手抢单并发 | 条件更新 | `WHERE rider_id = 0 AND status = 2 AND ready_time <> ''` | 返回"手慢了" |
| 商户接单 vs 用户取消 | 状态条件更新 | `WHERE id = ? AND status = ?` | 返回"请刷新后重试" |
| 支付 vs 超时取消 | 条件更新 | `markPaid` / `cancelPending` 各用 `WHERE status=0` | 先到先得 |
| 评价重复提交 | DB 查询 | `existsByOrderGoods` | "该商品已评价" |
| 退款重复提交 | `markRefunding` | `WHERE id = ? AND status = 4 AND escrow_status = 0` | "已有进行中的退款" |
| 缓存击穿（热点 key） | Redis 分布式锁回源 | `SET NX PX` 3s 锁 | 未抢到等待后降级回源 |
| 缓存雪崩 | TTL 随机抖动 | base + `ThreadLocalRandom` 120s | ✅ |

### 3.2 1000 用户场景模拟

#### 场景一：1000 人同时抢同一件库存=10 的商品

```
用户 1~1000 提交下单请求（同一商品，库存=10）
  └─ 每个请求都进入 createOrder 事务
     └─ goodsDao.deductStock(goodsId, 1)
        └─ UPDATE goods SET stock = stock - 1, version = version + 1
           WHERE id = ? AND stock >= 1 AND status = 1
           └─ MySQL InnoDB 行锁串行执行
              └─ 前 10 个成功 → rowcount=1 → 继续
              └─ 第 11 个起 → rowcount=0 → 抛异常回滚 → "库存不足"
```

**结论**：✅ 安全。行锁 + 条件更新保证不超卖。失败方收到明确错误提示。不涉及 Redis 锁（库存扣减走数据库行锁）。

#### 场景二：1000 人同时支付最后一笔余额

```
用户 A（余额=20），同时发起两笔 20 元订单支付
  └─ payOrder(userId, orderId1) 与 payOrder(userId, orderId2) 并发
     └─ userDao.deductBalance(userId, 20)
        └─ UPDATE users SET balance = balance - 20 WHERE id = ? AND balance >= 20
           └─ 第一笔成功 → balance=0 → rowcount=1
           └─ 第二笔失败 → rowcount=0 → 抛异常回滚 markPaid → "余额不足"
```

**结论**：✅ 安全。原子扣款不写负余额，失败回滚整单。

#### 场景三：1000 个骑手抢同一个订单

```
骑手 1~1000 同时调用 riderGrab(orderId=1)
  └─ orderDao.tryAssignRider(orderId, riderId)
     └─ UPDATE orders SET rider_id = ? WHERE id = ? AND rider_id = 0
        AND status = 2 AND ready_time <> ''
        └─ 第一个执行成功 → rider_id 写入 → rowcount=1
        └─ 其余 999 个 → rowcount=0 → "手慢了，该订单已被其他骑手接走"
```

**结论**：✅ 安全。MySQL 行锁保证只一个成功。

#### 场景四：确认收货与申请退款的并发竞态

```
用户同时点「确认收货」和「申请退款」（连点/网络重放）
  └─ confirmOrder → releaseEscrow(orderId) → UPDATE orders SET escrow_status = 1 WHERE escrow_status = 0
  └─ applyRefund  → markRefunding(orderId)  → UPDATE orders SET status = 6 WHERE status = 4 AND escrow_status = 0
     └─ 一方成功，另一方 WHERE 条件不再成立 → rowcount=0 → 抛异常
```

**结论**：✅ 安全。两个操作的条件互斥，绝不同时成功。

#### 场景五：1000 人同时注册

```
1000 个注册请求（同一手机号或同一用户名）
  └─ AuthService.register
     └─ DB UNIQUE 约束：username UNIQUE + phone UNIQUE
        └─ 第一个 INSERT 成功，其余 DUPLICATE KEY → "用户名已存在" / "手机号已注册"
```

**结论**：✅ DB UNIQUE 约束兜底。但**缺前端去重**（注册按钮禁点 + 验证码防刷）。当前有登录/注册限流（Redis 10次/60s login, 5次/h register）。

#### 场景六：1000 人同时领同一张优惠券

```
现状：优惠券是 DataSeeder 直接分配给用户的（coupons.user_id），不存在"领取"接口。
一张券只属于一个用户，不会出现并发领取问题。
```

**结论**：N/A。当前无优惠券领取功能。

#### 场景七：1000 个并发查询首页（缓存场景）

```
热点数据（首页推荐店铺、热销商品等）被 1000 人同时请求
  └─ HotDataCacheService 三级防护：
     1. 缓存穿透：NULL 值占位，短期 TTL 60s
     2. 缓存击穿：Redis SET NX 互斥锁 3s，只一人回源
     3. 缓存雪崩：TTL 基础 300s + 随机抖动 0~120s
  └─ Redis 不可用时：降级回源数据库（无 Redis 锁），靠 MySQL 连接池承受
```

**结论**：✅ 有缓存防护。真实瓶颈在于 DB 连接池耗尽（默认 HikariCP 10 连接），被缓存挡住后才安全。列表分页：`/api/admin/products` 已分页（`LIMIT/OFFSET` + `countForAdmin`），用户/管理端订单与 users/refunds 量小（admin/orders 44 行）暂缓分页——见 §4.3。
